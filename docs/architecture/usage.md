# How files are used: programs, space policies, largest files, duplicates, the content guard

Which programs change and open your files, freeing space from files you don't use, the largest files, and a circuit breaker for edits that look like ransomware. User guide: [the Apps page](../user-guide/settings-window.md#apps), [Files On-Demand](../user-guide/files-on-demand.md) and [the content guard](../user-guide/syncing.md#the-content-guard-ransomware).

All four read or write the store's usage tables (`oneup_store::usage`), which are bounded and indexed so cost follows activity, not the size of the tree:

| Table / index | Holds | Bound |
|---|---|---|
| `app_use (hour, app, kind)` | files and bytes per hour, program and kind (changed / opened) | 90 days (`app_use_prune`) |
| `app_file` | the latest files used: time, program, changed/opened, path relative to the synced folder, size | 5,000 rows |
| `local_used (file_id)` | the last time OneUpDrive downloaded a file for a program | one row per file; rows of files gone from the Local tree are trimmed a thousand at a time |
| index `local_by_age (mtime, file_id)` | placeholders whose content is here, neither pinned nor unpinned | partial index |
| `remote_largest` | a query on the `remote_item_copyable` size index (files ≥ 1 MiB with a hash) | `LIMIT n`; reads the whole table only on a drive with fewer than `n` such files |

## Programs (`oneup_app::apps`)
* **Opened**: each `FETCH_DATA` request carries the requesting process (`CF_CALLBACK_INFO.ProcessInfo`) and the placeholder's file ID (`Fetch::file_id`). On a completed hydration, `oneup_exec::hydrate` adds an `opened` count for the program and sets `local_used` for the file. Exact.
* **Changed**: journal records don't say who wrote. The agent's journal watcher (`oneupd::watch_journal`) parses the records it waits for and hands each file with a content change (`DATA_OVERWRITE | DATA_EXTEND | DATA_TRUNCATION`) to the `Tracker` thread over a bounded channel (`try_send`: a full channel drops the change, never blocks the watcher). Wake-ups go through a separate `journal-wake` thread that keeps the agent's 500 ms gap, so with the tracker on, the watcher reads again after 50 ms (`TRACK_GAP`) and quick writers are still caught. The tracker finds the file where the Local tree has it (by file ID only if it isn't there: a handle opened by ID would make a save by rename fail meanwhile), ignores anything outside the synced folder and in `.oneup`, and identifies the writer from two sources:
  * **Windows' Restart Manager** (`oneup_sys::in_use`, documented, unelevated): which processes have the file open. At most 20 lookups a second; writes are de-duplicated per file for 30 s.
  * **Closes**: the provider registers `CF_CALLBACK_TYPE_NOTIFY_FILE_CLOSE_COMPLETION` (a notification: Windows doesn't wait for it), which names the closing process; `oneup_cfapi::closes` keeps the latest 4 closes per file for 60 s, at most 8,192 files, never our own process. Windows sends these only for placeholders, so a new file isn't covered until it's synced.

  The tracker takes the first program that isn't a usual reader (search indexer, Defender, Explorer) from those with the file open and those that closed it from 2 s before it heard of the write; if there's none, the change waits up to 3 s (`SETTLE`, at most 4,096 waiting) for a close, and is otherwise "not identified". Counts are flushed to the store every 15 s (only when there are some; pruning every 10 minutes).
* **Online-only files are never looked up:** Restart Manager downloads the whole file, even from our own process (`oneup-cfapi` test `what_downloads_an_online_only_file_from_the_providers_process`), and such a "write" is OneUpDrive's own (creating or freeing a placeholder). The watcher drops records whose attributes say online-only, and the tracker checks again by attributes alone (`symlink_metadata`, no data access) just before the lookup.
* **OneUpDrive's own writes aren't a program's.** The writers note the file in `oneup_cfapi::ours` (in memory, 2 minutes, at most 8,192 files): `place_download`, the Files On-Demand effects (`replace_placeholder`, `free_up`, `mark_uploaded`) and the hydration service; the tracker skips noted files. A hydration requested by our own process (keeping a file on this device) is logged as such and not counted as a use.
* When the watcher falls more than 4 MiB of records behind, it skips to the end (the observer reads everything anyway; only attribution is lost).
* `[agent] track_apps` (default on; settings window **Apps**; re-read each flush) turns noting programs off.
* Shown by `oneup apps [--days N]` (`--files [PROGRAM]` lists the latest 100 files) and the settings window's **Apps** page, which reloads every 15 s while shown: stacked columns (hours for a day, days otherwise) for the five busiest programs plus "Others", in a categorical palette validated for light and dark backgrounds, with the legend and table carrying the labels; a program's row lists its latest 50 files. Paths stay on this PC, like the activity log's; never contents.

## Space policies (`oneup_app::space`)
`config.toml` `[space]`: `free_unused_days` (0 = never), `free_when_low`, `low_disk_percent` (default 10). Also `oneup space` and the window's Files page (a folder's details, **Free up space**).
* **Used** = the latest of last write (`mtime`), last access (`std::fs::metadata().accessed()`, meaningful only where the volume keeps access times), and `local_used`.
* After a settled round, `Engine::placement` asks `space::select` for a batch: hourly for "unused for N days"; at every pass while the disk has less than `low_disk_percent` free, then the files unused longest (and unused for at least a day) until it has 5 points more.
* Candidates come from `local_by_age` (oldest first, keyset pages of 256), at most 2,000 looked at and 64 freed per pass, continuing from a saved cursor (`meta space.cursor`) so files skipped as recently used aren't re-read each pass. Empty files never qualify (an empty file looks freed already).
* Each becomes an `Op::Dehydrate` (only with a content hash on record), reviewed by the gate (a paused "this PC" withholds it) and run by the effects layer, which frees a file only after verifying its content under an exclusive handle (data-safety invariant 11). Pinned files never qualify (excluded by the index), nor anything a pin rule matches, pinned yet or not (`select`'s `kept`; [files-on-demand.md § Pin rules](files-on-demand.md#pin-rules)). Logged as an activity-log note.

## Largest files
`settingsapi::largest` (`oneup largest`, and the settings window's `largest` request): the `n` largest files in the mirror, their OneDrive path, and whether each is here, online-only (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`, read with placeholders exposed), not here yet, or outside the synced folder. Never reads content. **Free up space** / **Keep on this PC** are `oneup free` / `oneup pin`.

## Duplicates
`oneup_store::dupes`, `oneup_exec::dupes`, `oneup_app::duplicates` (`oneup duplicates`, the window's Files → **Duplicates**). User guide: [Duplicates](../user-guide/files-on-demand.md#duplicates).

**Grouping.** A group is a content: size and QuickXorHash. Cloud files come from the `remote_item_copyable` index (files of at least 1 MiB with a hash, schema v9; the server-side copy uses it too), so grouping reads that partial index once (`SEARCH remote_item USING INDEX remote_item_copyable (size>?)`) and never the Remote tree; a group's copies are one search of it by size. Files on this PC that aren't in OneDrive join from `local_only_hash` (schema v20, at most 100,000 rows), which holds hashes made on request; a row counts only while the Local tree has the file at the size and last-write time it was hashed at and no Synced record links it, and triggers drop it when the Local tree sees the file anew (another file that took its ID), with another size, time or kind, or gone, and every row when the synced folder is scanned again or is another one. A synced file is one copy, its cloud row. Groups come a page at a time, ordered by the space removing all but one copy frees (keyset on `(saved, size, hash)`); the summary (groups, extra copies, bytes) is one more pass over the same index. `grouping_uses_the_size_index_and_never_scans_a_tree` checks the query plans.

**Not checked: excluded folders' contents.** An excluded folder is one opaque row in each tree, so what's inside it is never compared, and nothing is built to look there. The view, `oneup duplicates` and `--json` (`note`, `excluded_folders_checked: false`) say so.

**Labels.** Each copy says where it is (here and in OneDrive, in OneDrive, on this PC only) and is labelled in a vault's or an extra pair's OneDrive folder, outside the synced folder, or matched by an exclusion rule (a cloud copy in the synced folder that the rules as they are now exclude, synced or not: a synced file a new rule covers stays synced until it's pruned or unticked). A group repeats its copies' labels.

**Hashing local-only files** (`--hash-local`, the view's **Hash**): only on request, in the `oneup` process at background priority (`PROCESS_MODE_BACKGROUND_BEGIN`). It walks the Local tree's primary key from a saved cursor (`meta duplicates.hash_cursor`), a page of 256 at a time, and hashes files of 1 MiB or more with no Synced record and no hash yet, through `oneup_local::verify` (ordinary files only, never a placeholder, unchanged while read). At most 2,000 files or 20 GiB per run; it stops when sync is paused (`agent-pause.json`) or on Ctrl+C, and the next run continues. A new pass first drops the rows that no longer stand.

**Removing** follows `crate::resolve`'s shape and decision 2 of the gate rules ([data-safety.md](data-safety.md), invariants 3 and 8):
1. The preview (`duplicates::prepare`, `oneup_exec::dupes::plan`) checks each chosen copy against the store, names exactly what goes and where by the store's own paths (never the paths a caller sent), and what's left and why, and gives the list's code: the removal stop's fingerprint (`oneup_gate::removal_fingerprint`) for those operations, each keyed with the path its stop's list shows (`sync::removal_path`, the same one `sync::stop_paths` passes the gate), so the stop shows the preview's code when nothing changed.
2. `duplicates::ask` queues the choice in `meta duplicates.remove`, with that code, only while the code is the same (`--expect`) and every synced copy is as it last synced. One choice waits at a time; `cancel` drops it. A backup pair refuses.
3. Each round (`duplicates::for_round`, not while either side is paused) works the choice out again, from one store snapshot (`Store::snapshot`, as the preview is). A cloud copy must still have the eTag, size and hash shown and no Synced record; a synced copy must still be as it last synced, linked on both sides, both there, and where it was synced (folder and name: `dupes::synced_place`), else the whole choice waits while the planner carries the change; a local-only copy must still have its size, last-write time and hash, and no Synced record. Each removal carries its place: `name`, `local_dir`, `remote_dir`, and every folder above them up to the synced folder here and the drive's root in OneDrive, by ID and name (`Up`, `local_up`, `remote_up`). That full path is the one its stop's list shows and its key holds (`sync::removal_path`). If the code it comes to isn't the queued one (a copy changed, or it or a folder above it moved), the choice is dropped and logged: the user chooses again.
4. **The last copy here never goes.** Each content keeps a named survivor (`Keep`): a copy not being removed, in this data folder's own files. A copy in a vault's or another pair's OneDrive folder (`duplicates::separate`) is listed but never the survivor, since its own agent could remove it meanwhile; there's no coordination across pairs. If no survivor is left, none of that content's copies go.
5. Each copy becomes one `Op::RemoveCopy`, carrying its survivor and the chosen hash. The gate (`oneup_gate::is_removal`) holds them as a list of its own (`BreakerKind::Removal`, `SafetyStop.kind = "removal"`), whatever the circuit breakers' limits, until that list is approved (`oneup approve`; the tray's **Review removing duplicates…**, whose question lists the paths from the stop's saved list and isn't asked until that list is saved; the window's **Approve…**, which shows the same list and only answers a removal stop). Like every stop's list ([sync-engine.md § Safety stops](sync-engine.md#safety-stops)) its items are keyed (`ItemKey`, kind `removal`, with the path shown: `oneup_gate::always_stops` covers removals, so the engine reads the paths however small the round), its saved list shows exactly those, the approval lasts item by item until each change runs, and a code answers one raising. A mass list never holds them, so a mass approval never releases them. The rest of the round goes on; a pause of either side holds a synced copy's removal (`oneup_gate::changes`). Once they ran, they count in the agent's 15-minute window by weight, on each side they changed; what they take from this PC is kept in the version store whatever its room.
6. **A round that touches a copy or its survivor runs none of the removal** (`dupes::touched`): if the round's own plan deletes, moves or replaces the survivor, a copy being removed, or a folder above that copy at any depth (a deletion here of the copy that stays, a rename, an edit on its way, a folder above moved), the removal waits for a round that doesn't.
7. **The executor** (`RemoveCopy`, alone), just before acting:
   * checks in the store that the survivor stands and that the copy is linked and where it was shown on both sides, every folder above it included;
   * re-reads a survivor in OneDrive (eTag and hash); reads and hashes a survivor here watched (`LocalFs::witness`, through `win::WatchedFile`: a Read-Handle oplock, so its program can go on saving it, by writing or by renaming over it; never an exclusive handle), and keeps it watched until the removal is done: a save to it from then on stops the removal;
   * reads and hashes the copy here the same way, at its full path by the handle's final path (a folder above it moved or renamed is another path; a placeholder is never read: its identity must vouch for the content);
   * re-reads OneDrive's copy where it was shown, and each folder above it (its name and parent, up to the drive's root), and removes it under `If-Match`, both watches still unbroken. Graph can't make that check and the request one step: a folder above moved by someone else in between changes neither the item's ID nor its eTag, so what goes is still exactly the item approved, into the recycle bin, with the survivor standing (`a_folder_above_moved_in_onedrive_during_the_removal_is_harmless`). Refused there, nothing here is touched, and nothing else carries the removal out later;
   * then removes the copy here under an exclusive handle: same stamp, same full path by the final path, same content hashed through that handle, evidence noted first as for recycling. While that handle is open, no folder above the copy can be moved or renamed, so the path checked is the one it leaves from (`a_folder_above_a_copy_being_removed_cant_move`). The survivor's watch goes into that effect and is checked once the copy has left its place for the version store: saved at any moment until then, the copy goes back through the same handle (never over anything) and nothing is removed, so no save of the survivor goes unseen while the copy is still in its place. A dehydrated placeholder takes the same way, under a hold that keeps any download out, and is deleted from the version store only after that check (it has no content here). For a synced copy, a write-ahead record (`exec.pending`, `removing`) goes down just before OneDrive's copy does: if the copy here is still there when the record is settled (refused now because it or the survivor changed, or the process died meanwhile), the removal is undone: the Synced record goes, so the copy here reads as new and is uploaded again (or paired again, if OneDrive's copy never went). A later ordinary deletion never finishes it without its checks.

   A file's duplicates hash (`local_only_hash`) is also dropped when the change journal reports a write to its data (`DATA_OVERWRITE`, `DATA_EXTEND`, `DATA_TRUNCATION`), whatever its size and time are then.

`everyday_duplicates_chosen_for_removal_go_recoverably_once_approved`, `a_duplicate_changed_after_the_preview_is_skipped_and_its_edit_survives`, `a_removal_whose_survivor_changed_just_before_is_skipped`, `a_removal_waits_while_the_round_deletes_its_survivor`, `a_chosen_copy_renamed_meanwhile_is_left_alone`, `a_copy_rewritten_with_its_old_stamp_is_not_removed`, `a_chosen_copy_moved_meanwhile_under_its_name_is_left_alone`, `a_chosen_copy_whose_folder_above_moved_here_is_left_alone`, `a_chosen_copy_whose_folder_above_moved_in_onedrive_is_left_alone`, `a_refused_removal_never_finishes_without_its_survivor`, `a_removal_whose_survivor_here_was_rewritten_with_its_old_stamp_is_skipped`, `a_removal_whose_copy_here_changes_after_onedrives_went_is_undone`, `a_survivor_saved_just_before_the_copy_here_goes_keeps_the_copy`, `on_demand_a_dehydrated_duplicate_goes_without_downloading`, `a_folder_above_a_copy_being_removed_cant_move`, `a_folder_above_moved_in_onedrive_during_the_removal_is_harmless` and `a_crash_while_removing_duplicates_loses_nothing` (`crates/oneup-exec/tests/sync.rs`) cover it end to end.

## The content guard
A circuit breaker on content, in the gate (`oneup_gate::BreakerKind::Suspicious`, [sync-engine.md § Safety gate](sync-engine.md#safety-gate-and-effects)):
* Planning (`sync::judge_content`) reads the first 4 KiB of each **edited** file about to replace its OneDrive copy (`Op::Upload { replace: Some(_) }`; at most 2,000 per round) through `LocalFs::sample` (read-only, the upload's own identity and placeholder checks), and `oneup_gate::content::looks_wrong` (pure) judges it against its extension: a signature for zip-based Office files, OLE Office files, PDF, RTF, images, audio and video, archives, executables and SQLite; plain text for text and source files (more than 2% control bytes fails; UTF-16 with a byte-order mark passes). Unknown types are never judged, so it can't get in the way of unusual work.
* The gate trips when more than `max_suspicious` (default 20) such uploads come in a round, counting the agent's 15-minute window (`Recent::suspicious`). Only those uploads are withheld (a tripped round runs nothing anyway, unless only a rewind waits), with their own fingerprint, approved like any breaker.
* The tray has its own notification ("Files may have been encrypted") and review text; `SafetyStop.kind = "content"` in the control API.
* Thresholds, including the ordinary breakers': `oneup safety`, the window's **Safety** page (store `meta safety.*`).
* Why only edits: encrypting in place is what ransomware does, and an edit is the only case with an earlier version in OneDrive worth protecting. Ransomware that writes new files and deletes the originals trips the ordinary deletion breaker.
