# Explorer integration

File Explorer shows OneUpDrive's folders in the navigation pane with their status, and offers OneUpDrive's commands on the right-click menu of synced items. User guide: [Explorer](../user-guide/explorer.md).

## Package identity: a sparse package
Explorer's richer integration (navigation pane, status UI, context-menu verbs for cloud files) is only for programs with **package identity**. OneUpDrive gets it as the OneDrive app does: a **sparse** identity package, `OneUpDrive.Sync` (`packaging/identity/AppxManifest.xml`). It holds only a manifest and logos (`uap10:AllowExternalContent`); the programs stay where they're installed, its external location.
* **Which programs have it.** The embedded manifests of `oneup`, `oneup-settings` and `oneup-open` link to the package (`<msix publisher=… packageName="OneUpDrive.Sync" applicationId="OneUpDrive"/>`, written by `bins/oneup/build.rs`); they register folders with the shell and serve Office. While the package isn't registered, Windows ignores the link and nothing changes.
* **The agent (`oneupd`), `oneupd-start` and the tray run without the identity.** Windows ends every process of a package at once, without a word to any of them, and a sync agent must not vanish with a settings window. The agent needs nothing the identity gives: a program without it serves a folder the shell registered with it (`oneup-cfapi` test `a_shell_registered_root_is_served_by_a_program_without_identity`), and it has the CLI refresh its Explorer entry at start (`oneup refresh-explorer-entry`). Our programs start the agent, tray and settings window outside the caller's Windows job where allowed (`CREATE_BREAKAWAY_FROM_JOB`), so ones started by Explorer's COM surrogate (the flyout's buttons, the commands) don't end with its job.
* **Publisher:** must equal the signing certificate's subject exactly. Releases pass it as `ONEUP_PUBLISHER` (the workflow's `SIGNING_SUBJECT`); development builds use `CN=OneUpDrive Development`.
* The package must declare `windows.cloudFiles` (even empty): without it the shell refuses sync-root registration ("Element not found").
* **Write virtualization is off** (`desktop6:RegistryWriteVirtualization` and `FileSystemWriteVirtualization` `disabled`, with the `unvirtualizedResources` capability). Otherwise Windows sends our programs' `HKCU\Software` writes to a private hive that only they read, so "Start at sign-in", the flyout's status key and the Office registration would be invisible to everyone else.

### Registering and updating the package
* **Releases:** the install and update hooks register the signed `OneUpDrive.Sync.msix` shipped next to the programs (`oneup_app::identity::add_installed`, `PackageManager::AddPackageByUriAsync` with the install folder as external location), and uninstalling removes it last.
* **Development:** `oneup dev-identity --register` registers it unsigned (needs Developer Mode), `--remove` removes it, and `oneup dev-identity` says whether this program has identity. An unsigned local install (`build-release.ps1` without signing) can't add its `.msix` ("the app package must be digitally signed"), so it is registered the development way once (the installed `oneup.exe dev-identity --register`, with OneUpDrive closed); after that the install and update hooks re-register it themselves when the installed package's publisher is the development one (`oneup_sys::identity::installed_publisher`).
* **Where the unpacked development package lives:** beside the install folder, in `%LOCALAPPDATA%\OneUpDrive.App.identity`. Installing over an existing copy deletes the whole install folder, and a package whose files vanish makes Windows drop the folder's Files On-Demand registration. Every update also replaces `current`, so the package is never kept there.
* **Updating it only when needed:** since the package only points at the programs' folder, which doesn't move, the hooks leave a development identity alone when the registered one already reads its manifest from that folder and the manifest differs only in its version (`identity::dev_is_current`, `oneup_sys::identity::installed_location`). Updating the package while the agent is stopped can cost the folder's registration; the agent's start-up repair ([files-on-demand.md](files-on-demand.md#keeping-the-registration)) is the safety net.
* **From one of our own programs:** a program running with the identity can't replace the package immediately ("apps need to be closed"; a failed attempt can leave our programs unable to start until the registration completes). Registration therefore uses `DeferRegistrationWhenPackagesAreInUse`: Windows completes it once our programs exit. In Developer Mode, Windows only re-registers a higher version, so `dev-identity --register` raises the revision with time; run from a program that has the identity, it starts a hidden PowerShell that waits until those programs have exited, then registers. Explorer's COM surrogate (`dllhost.exe` serving `oneup_shell.dll`) runs with the package too, so registering stops it first; Explorer starts a new one when it needs it.

## Sync roots registered with the shell
`oneup_app::syncroot` (used by `on-demand on|off`, vault pairs, uninstalling): with identity, a folder is registered through **`StorageProviderSyncRootManager`** (`oneup_cfapi::shell`; ID `OneUpDrive!<user SID>!<token prefix>`, display name "OneUpDrive" or "OneUpDrive vault …", icon from `oneupd.exe`; whole-file hydration, always fully populated, in-sync tracked, personal protection). Without identity, `CfRegisterSyncRoot` with the same policies.
* Cloud Files reports a shell-registered root exactly like the other: provider `OneUpDrive`, identity = the pair token. So the coexistence checks and the effects layer treat both the same.
* Explorer shows the folder in the **navigation pane** with our name and icon, and the **Status** column works.
* **The icon is a program's path**, fixed at registration, so the agent re-registers its folder at start when the stored icon or version isn't the running copy's (`syncroot::refresh`). Registering an existing ID again updates it in place: same navigation entry, new icon, contents and Cloud Files identity unchanged. This must happen **before** the agent connects as the provider ([files-on-demand.md](files-on-demand.md#keeping-the-registration)).
* **Removing must use the shell:** `CfUnregisterSyncRoot` removes the sync root but leaves the navigation entry and the shell's registration behind. `syncroot::unregister` removes the shell registration, and falls back to Cloud Files for roots registered without identity.

## Our commands in the context menu
`crates/oneup-shellext` (`oneup_shell.dll`): a COM in-process server declared in the identity package as a **surrogate server** (`com:SurrogateServer`), so Windows loads it in a separate `dllhost.exe`, never in Explorer, and a `desktop3:CloudFilesContextMenus` verb, which shows only for items inside OneUpDrive's sync roots. It offers one **OneUpDrive** entry (`IExplorerCommand` with sub-commands; the sub-menu is filled only when it opens, so `Shell.Application`'s `Verbs()` doesn't list them):
* **Why does this sync?** and **Sync activity**: the settings window's Files page with the item selected and its *Why* or *Recent activity* section open (`oneup-settings --page itemwhy|itemactivity --item PATH`);
* **Sync this first**: `oneup sync-now` for it;
* **View online**: its page on onedrive.com (Graph's `webUrl`; for a vault, a message instead, since the website shows only encrypted files);
* **Version history** and **Copy share link…**: the settings window's Files page with the item selected and its Versions open (`oneup_app::item`; `oneup history`, `oneup share`). Restoring a version asks the agent's next round to download it and upload it as a new version under `If-Match`, checked by hash, because Graph's `restoreVersion` ignores a stale `If-Match` on OneDrive Personal;
* **Open with AutoSave**: opens a Word, Excel or PowerPoint file from its OneDrive address so Office edits it in OneDrive ([office.md](office.md)).

The DLL does no sync work: it starts `oneup.exe shell-verb VERB PATH` (next to it, without a console) with the first selected item, and `shell-verb` shows a problem in a message box. `oneup` finds the data folder from the path (`oneup_app::datafolders`: agents record their data folders in `HKCU\Software\OneUpDrive\DataFolders` when they start; the default data folder and vault pairs are known anyway; the innermost synced folder wins).

The `CloudFiles` element must also declare thumbnail, extended-property and banners handlers (the schema requires them). They point at reserved IDs the DLL doesn't serve, so Windows keeps its own; the OneDrive app does the same for the ones it doesn't support.

## The status flyout and custom states
* **Flyout** (Windows 11 23H2+, `cloudfiles2:StorageProviderStatusUISourceFactory`): `oneup_shell::status::StatusFactory` → an `IStorageProviderStatusUISource` per sync root. The agent publishes its state per root under `HKCU\Software\OneUpDrive\Status`, the value named by the root's shell ID (`oneup_app::shellstatus`: state, a label and a sentence, the data folder, the kind of pair, the local folder, the account's storage from `GET /me/drive` hourly; no file names), whenever its status revision changes, and removes it when it stops. The DLL reads it on `GetStatusUI` (state, label and icon, a sync-status line that opens the settings window, the storage bar, and a primary button: **View online**, or **Settings** for a vault) and watches the key (`RegNotifyChangeKeyValue` on a thread of its own) to raise `StatusUIChanged` through agile references to Explorer's handlers. Icons are small SVGs written once to `%LOCALAPPDATA%\OneUpDrive\flyout` (Explorer wants file addresses).
* **Custom state** (`desktop3:CustomStateHandler`): `oneup_shell::status::States` (`IStorageProviderItemPropertySource`) gives items inside a vault's folder the state "Encrypted in OneDrive (vault)" with Windows' lock icon. The state's definition is declared when a sync root is registered (`oneup_cfapi::shell::register`).
* **Office handler**: `oneup_shell::office::Handler` (`IStorageProviderHandler`), for the Office registration experiment ([office.md](office.md#the-registration-experiment)).

## Limits
* Thumbnails and extended properties: Windows keeps its own.
* Roots registered without identity keep working, without the navigation entry, until Files On-Demand is turned off and on.
