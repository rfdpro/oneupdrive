# Networks: profiles, intervals and slow links

How the agent decides how much of the network to use. User-facing: [slow-and-metered-networks.md](../user-guide/slow-and-metered-networks.md).

## Which network

`oneup_sys::network` reads the internet connection's profile through WinRT (`NetworkInformation::GetInternetConnectionProfile`): the network's ID from Windows' Network List Manager (`NetworkAdapter.NetworkItem.NetworkId`, the GUID behind Windows' own network profiles), its name, whether it's metered (`ConnectionCost`: fixed or variable cost, roaming, over its limit) and how far it reaches (`GetNetworkConnectivityLevel`). Without an internet profile, the connected profile that reaches furthest stands in, so a captive portal reads as *constrained* rather than as no network. Profiles are keyed by the ID, never by a name: two networks may share a name, and a typed name would be wrong after a rename.

## Profiles (`oneup_app::network`)

Three layers, each setting only what it changes, resolved by the pure `network::active`:

| Layer | Where | Applies |
|---|---|---|
| default | `[agent]` caps, `[sync]` interval | every network; everything transfers |
| metered | `[metered]` | networks Windows says are metered. Paused while `[agent] pause_on_metered` is on (the default); otherwise `[metered] transfer` |
| own | `[networks."{GUID}"]` | that network, over the default (or metered) layer |

A profile carries what transfers, the size limit for "small files", upload and download caps, the sync interval (and `keep_push`) and a monthly budget. The agent resolves it at every wake-up and hands rounds a `network::Policy` through `sync::Controls`; a profile whose transfer is `paused` becomes an automatic pause (`autopause::Conditions::network`). `cap_hours` still limits when caps apply.

## What transfers

`network::Policy` holds the profile's `Transfer` (`everything`, `metadata`, `small`, `opened`, `paused`) and size limit. Only operations that move file contents are ever held (`network::content`): an upload, and a download unless the folder uses Files On-Demand (then it's a placeholder). Names, folders, moves, deletions and placeholders always go; so does hydration, which is the user opening a file and not a sync operation. `opened` lets uploads through and holds background downloads.

Holding is the same mechanism as for files that keep changing or OneDrive being full: after the gate has reviewed the round, `sync::hold_for_network` takes the held operations out of what runs, and their folders keep their dirty marks, so a round on a network that allows them plans them again. Nothing new reaches the gate or the effects layer, and an operation held now is planned from fresh state later; holding a download while the local file changes ends as an ordinary conflict. The follower (new folders' contents in the same round) holds the same way. Files pinned to stay on the device are hydrated only under `everything`.

What waits is kept in `meta` (`net.waiting`, the 500 largest, with the count and bytes) for `oneup status`, `oneup explain` and `oneup network waiting`, and logged once per reason.

**Mid-round:** `control::LivePause` also holds the policy. `round_check` compares it with the policy the round was planned under; once it differs, a content transfer it doesn't allow stops that side for the rest of the round, as a pause does (downloads, whose size isn't known there, stop under a size limit too). The next round plans what waits under the new policy.

## Data budget

`oneup_app::netusage` keeps each profile's use this month in `meta` (`net.usage.<profile>`: month, bytes up and down, bytes allowed on top), so a restart keeps it and a new month starts at zero.

**What counts.** The Graph client counts every request body as it goes (`NetStats::sent`: each attempt, so a fragment sent again after a 429 or a lost answer counts again; JSON and file contents alike), every response body it reads, chunk by chunk as it arrives (a body cut off midway counts what came), every chunk of a download as it arrives, before it's written anywhere (`NetStats::bytes`: a download that fails near its end, or whose file can't be written, still counts), and the push channel's messages each way. Not counted: token refreshes (a few KB an hour, through the sign-in client), HTTP headers, and the bodies of answers it doesn't read (throttling, retried server errors). The update check and download run in the tray and the settings window, not the agent, and aren't counted; the tray's daily check doesn't run on a metered network, one with a data budget, or while working offline (`updates::may_download_by_itself`); its download runs in a process of its own (`oneup updates --fetch`) that the tray ends at once if Windows reports a change to such a network (`updates::run_stoppable`; velopack clears the partial file next time). A check the user asks for always goes and isn't stopped.

**Who it's charged to.** `netusage::Ledger` (the agent's own database connection) samples those counters at every wake-up, on every network change, every 30 s while rounds run, after every pass of rounds and after placement, and once more when an attempt ends however it ends (dropped on a stop, an error or a restart). `netusage::Account` charges the difference to the profile that was in effect while it went: on a change of network what went before is charged to the old profile before the new one takes over, and the meter moves on only once the write succeeded, so a failed write is charged again next time. A process killed outright loses what went since the last sample.

**Enforcement.** The rounds get what's left as `Policy::budget_left`: `hold_for_network` lets transfers through in the round's order while their planned size fits (new folders' contents take from what the round left) and holds the rest. The transport holds the same figure (`oneup_graph::budget::Budget`, set at each sample and on a change of network, `network::apply_profile`) and decides per attempt, right before a body goes: an upload's body waits its slot at the upload cap (a cap changed meanwhile books it again at the new one, `Throttle::take`), then must fit in what's left then, or it isn't sent (`Error::OverBudget`). A download reads only while something is left and is counted as each chunk arrives; a download whose body has all arrived is complete, also when its last chunk went past what was left (it was received and counted anyway), and one of no told length that used the budget up is complete if one more read finds its end. An upload session the budget stopped is kept, like one the network cut off, so once more is allowed it goes on from where it stopped. Near the limit (16 MiB left) budgeted downloads read one at a time (`Budget::before_read`), so downloads side by side pass the budget by one network read in all, not one each (with the limiter's at most 32 requests at once and a read of at most 512 KiB). Tested over loopback: a download dropping at 90% every try, eight of them side by side, an exact fit, a writer that fails, a 429 resend and a switch to a used-up network while a fragment waits for the cap.

**Downloads that aren't stopped.** A program opening an online-only file is the user's own action: the hydration service serves it through an unbudgeted cloud, which doesn't wait for the request limiter's permits either (background transfers may hold them, near the limit while they wait their turn to read) but always waits out a pause the service asked for (`Aimd::unpaused`: 429/503 with `Retry-After`), and its bytes count. OneUpDrive's own hydrations (files set to always stay on this device, which the agent asks for) go through the budgeted cloud; which one is decided from who asked, before anything is downloaded (`Hydrator::with_ours`). Placement asks the live policy before each pinned file and follows network events meanwhile.

When nothing is left the agent pauses itself with that reason; the tray notifies once per month and budget, and offers `allow_data`. `Control` accepts it only while the budget in effect is used up and records it for that profile and month (`set_budget_spot`), and the agent adds each to the profile and month it was asked for, not to whichever network is in effect when it gets to it. A network pause (and working offline) also closes the push channel, at once when it begins mid-round. The count and the budget are the account's: kept in its **main** data folder's store, shared by every agent of the account (its extra pairs and vaults), so three pairs on a 1 GB budget share 1 GB. Each agent takes the budget in reservations of 32 MiB (`netusage::reserve`, one immediate SQLite transaction with the others' reservations; the transport asks for the next one when what it holds runs low, `Budget::set_refill`), charges what it used against its reservation, and gives the rest back when it stops or the network changes; a stopped agent's reservation is dropped by the next one that reserves. Separate accounts keep separate budgets.

## Network changes, by event

`oneup_sys::network::watch` registers for WinRT's `NetworkInformation::NetworkStatusChanged` (another network, a change of cost or connectivity) and pings `network::Events`; the agent reacts at once, each change of a burst read again (what the old network's profile allowed must stop as soon as the new one applies). The agent's wait ends on it (`Woke::Network`), and while rounds run, `watching_auto_pause` reads the network again at once: the new profile's policy reaches `LivePause`, its caps and budget reach the transport (`network::apply_profile`, so a switch from uncapped to capped applies to transfers under way), and a pausing profile becomes an automatic pause, all from the round's next operation or byte on. Windows is asked about the network only at the agent's wake-ups and on these events; the 30 s timer while rounds run only counts data, by the network last read. No timer reads the network; before, a switch could go unnoticed for up to 10 minutes while idle. Tested with an injected event in simulated time (`a_metered_switch_takes_effect_within_10_seconds`). A network change doesn't bring a sync-interval pass forward.

**Waiting for the internet.** A connection Windows reports as constrained (a captive portal) or absent is an automatic pause ("waiting for the internet…", `network::connection_reason`), so the agent waits for the next change instead of collecting errors. A network Windows says reaches only local addresses isn't waited for: a blocked connectivity probe looks the same, and sync may work there; failures are retried as before.

## Work offline

The user's `offline` call (`Control`, kept as the empty file `agent-offline` in the data folder) makes `Policy::offline` true and counts as a pause of OneDrive's side (`control::paused_sides`), so the gate withholds every change to OneDrive and `LivePause` stops them mid-round; `Policy::allows` refuses every transfer of contents, so downloads wait too. Rounds still read the change journal and plan, but don't ask OneDrive anything (no delta read, no room check), the push channel is closed and Explorer's storage figure isn't refreshed. Changes on this PC's side from what was already known still run. What the gate withheld is added to the waiting list (`net.waiting`) with what each would send, so `oneup offline` and `oneup status` show the queue by size. Hydration isn't a sync operation and still serves files the user opens.

## Poor links

After each pass the agent samples the Graph client's counters (requests, retries, the time until answers to bodiless requests began, contents moved and over how long) and `oneup_app::link` judges it: poor when more than 5% of at least 10 requests were retried, when answers took 1.5 s on average, or when at least 1 MiB of contents moved slower than 32 KB/s without a bandwidth cap, over the time transfers were under way (`throttle::Active`: transfers side by side count once; planning and listing don't count). A fragment sent again counts as a retry like any request the client retries. One poor pass marks the link poor; two good ones in a row clear it. The state outlives an error that restarts the agent's rounds, and each attempt sets the transport's caps to match it (`apply_link`). While it's poor, the AIMD limiter is capped at 2 requests at once (`Aimd::set_cap`), upload fragments at 1.25 MiB (`Graph::set_fragment_cap`, read by each session as it sizes a fragment), and the agent's waits before retrying skipped items and after errors are doubled. Requests and uploads under way finish as they are. Status shows `link: poor`; the change is logged in the activity log. An upload cut off by the network goes on from where it ended rather than from its first byte (see [sync-engine.md](sync-engine.md), upload sessions).

## Sync interval (`oneup_app::pace`)

The `Pacer` is pure: the agent tells it what ended its wait (`Woke`) and when a pass began. With an interval, a journal change no longer ends the wait (the observer still reads the journal, so marks and the Local tree stay current), a push notification ends it only with `keep_push`, and the push channel is closed otherwise. The user's calls and a pass that hit `MAX_ROUNDS` run at once; retries and held uploads wait for the next pass. A simulated hour of steady edits at 15 minutes runs 4 passes (`pace::tests`).
