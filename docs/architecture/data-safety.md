# Data safety

Never losing user data comes before every other goal. The rules below are enforced in code and asserted in tests; they are requirements, not guidelines. Code comments refer to them as "invariant N".

## Invariants

1. **No destructive local action without a cloud-verified copy or a local backup.** Before deleting, overwriting or dehydrating local content, either (a) the cloud holds the same content (QuickXorHash match on the current version), or (b) the old content is moved to OneUpDrive's local version store.
   **Exception:** (c) the cloud holds the same content in its **version history or recycle bin**, proved by a QuickXorHash match, read under an exclusive handle, against the last synced version. This is allowed in two cases only. First, a file replaced by a newer cloud version without a conflict: the default, and `keep_replaced` turns it off. Second, files removed because OneDrive reported them deleted (its change feed's `deleted` facet, a deleted folder above, or a rewind's own deletion there), so their content is in its recycle bin, when the user chose to discard them: "discard" for exactly that batch of removed files that doesn't fit in the version store, the setting to discard every such batch, or the setting to keep no copies of removed files at all (`keep_removed` off, which also stops keeping replaced files). A file the user answered "Delete here" for, gone from OneDrive without such a report, is always kept: nothing shows the recycle bin has it. By default a batch that doesn't fit is held untouched until the user decides; the user may instead choose to always keep (store over its limit) or to rotate the oldest kept items out. Duplicates the user removes and a rewind's set-aside files are always kept. Anything not proved stays in the version store. Details: [sync-engine.md § Version-store overflow and replaced files](sync-engine.md#version-store-overflow-and-replaced-files).
2. **No remote delete or overwrite without a precondition.** Every mutation carries `If-Match: <eTag>`; a mismatch means re-plan, never force. One exception, because there is no eTag to send: bringing an item back from OneDrive's recycle bin (`POST /items/{id}/restore`, a rewind's or one asked for). Measured on OneDrive Personal: the item comes back with its ID where it was deleted from, under the name it had, whatever folder and name are asked; an item holding that name is renamed `name(1)` (no 409); nothing is replaced. So the executor restores only when that place is where the step puts the item, and only after checking just before the request that nothing has the name there (`Cloud::name_taken`); otherwise it doesn't restore, and says so. Where it was deleted from is what delta's deletion entry says (`parentReference`), or the mirror's last folder only when the item's last synced record agrees; not known for certain, it isn't restored. What comes back is checked (its ID, folder and name) before anything else acts on it. In the moment between the check and the request, something taking the name would be renamed, not lost. Graph checks an upload session's `If-Match` only when the session starts, not when its last fragment commits, so a large replacement re-reads the eTag just before its last fragment (at most 320 KiB) and cancels the session if it moved on. An edit that lands between that check and the commit is found in the file's version history afterwards and kept as a new file under a conflict name (invariant 9). A record of each such upload is committed durably before it starts and removed only with the kept copy's record (or once the history shows nothing was gone over), so a failure, the process killed or a power cut never drops it: it's tried again at every later round, and waits while the network's settings don't let the version download. A history that never shows what the upload went over is given up after 20 rounds and listed in `oneup problems`. Meanwhile the edit is in the file's version history.
4. **Sync-root identity check.** Volume serial + root file ID + a `.oneup` marker must match before any operation runs. A missing, unmounted or replaced root ⇒ **halt**, never "everything was deleted".
5. **Compare-and-swap execution.** Immediately before acting, open the item by file ID and re-check it on that handle: a file's size and last-write time, or that a folder is still a folder. Any drift ⇒ abort the operation and re-plan.
6. **Verify every transfer.** Downloads are hashed before they're placed; uploads compare the server's QuickXorHash and confirm the file didn't change mid-upload. Reading a file never locks its program out: an upload reads under an oplock instead, which a write, or another program needing the file closed (to save over it, delete it), breaks. A break while the file is being read cancels the upload before it commits; after the last read, the earlier version, read whole and unchanged, may commit, and the saved version goes in a later round.
7. **Crash consistency.** Write-ahead intent records (fsync'd) → do → mark done. Recovery replays or rolls back idempotently. A record written ahead of an effect commits with `synchronous = FULL`, so it is on disk before the effect starts and survives a power cut; the store's other commits use NORMAL ([sync-engine.md § Storage](sync-engine.md#storage-cratesoneup-storesrcsyncedrs)).
8. **Circuit breakers** in both directions. Mass delete/move/overwrite above thresholds (count and percentage) pauses that direction and asks the user, showing a preview. An approval covers exactly the items on that list (and the folders their deletions empty, each deleted with evidence); anything not on it needs a stop of its own. The background agent counts what it carried out in the last 15 minutes on top of each round, and keeps that count across restarts. Removing duplicate copies the user chose always shows a preview and stops for the user to approve exactly that list, whatever the thresholds; it runs as ordinary operations through the gate and the effects layer, never removes the last copy of a content (each removal names a copy that stays, in the same data folder's own files, and is checked against it just before acting, a copy here read and hashed under a Read-Handle oplock that its program's saves break, checked again once the copy here has left its place, which puts it back if the survivor was saved meanwhile), skips any copy that changed or moved since it was shown (its full path, every folder above it included, is checked on both sides, and its content re-hashed under the exclusive handle), never leaves a half-done removal to an ordinary deletion (OneDrive refusing leaves both copies; the copy here refusing afterwards uploads it again), waits while the round's own plan touches a copy or its survivor, and sends what it removes to the version store (this PC) or OneDrive's recycle bin ([usage.md § Duplicates](usage.md#duplicates)). A **rewind** is always a stop, whatever the limits: it runs only what its approval covers, each item only from the state the preview showed (or the rewind's own last step left), and what it replaces or removes goes to OneDrive's version history and recycle bin or the version store.
9. **Conflicts keep both copies.** No last-writer-wins on content, ever.
10. **Safe defaults.** The first sync shows a preview before anything changes; `--dry-run` everywhere; `oneup panic` stops all destructive operations at once.

### Files On-Demand

These come from experiments with the Windows Cloud Files API that reproduced real data loss in the raw API.

11. **Never call plain `CfDehydratePlaceholder`.** Dehydrate only by (a) opening the file with an **exclusive** handle (share-none, which blocks every other writer), (b) verifying content against the cloud hash and our database under that handle, then (c) calling `CfUpdatePlaceholder(DEHYDRATE | VERIFY_IN_SYNC)` **through that same handle**.
12. **The platform's in-sync bit is advisory, not truth.** Windows ignores writes made by any process running the provider's executable (so the bit stays "in sync" after such a write). The agent never writes user content in the sync root except through Cloud Files transfer operations. User-facing tools (`oneup.exe`, the tray, the settings window) are **separate executables** from the provider (`oneupd.exe`).
13. **Hydration validates versions.** Each placeholder's file identity encodes (item ID, eTag, size, QuickXorHash). `FETCH_DATA` fails the request if the cloud's current version or the placeholder's size differs, then re-plans. It never serves bytes from a different version into a placeholder (doing so silently produces zero-filled files).
14. `CfUpdatePlaceholder`'s `UpdateUsn` precondition does not behave as a usable compare-and-swap (the call itself changes the USN before comparing), so it is **not** used as a safety mechanism.
15. **A Files On-Demand folder that stops being ours halts.** If OneUpDrive's sync-root registration disappears without OneUpDrive removing it (another program unregistered the folder), Windows will have removed the online-only placeholders. The folder then fails its identity check, so those removals are never sent to OneDrive as deletions.
16. **Another program's sync root is released only through the gate.** Finishing a stalled unlinking of the OneDrive app (`oneup migrate finish-unlink`) unregisters the app's root, which removes its online-only placeholders. It runs only with the gate's `release` token: a fresh scan and listing show every online-only item in OneDrive, the app is stopped and has removed its account, its choices are recorded, and the person agreed. The effect re-checks the registration and the app's processes immediately before acting.

### Databases

17. **A database is sent only in a consistent state and replaced only while closed** ([databases.md](databases.md)). SQLite, whatever the settings say: no changes outside the file (`-wal` empty, `-journal` not in a transaction), its `-wal` and `-journal` watched with it while it's read. Other formats: no other program has it open (the user may turn that waiting off). When Windows can't say who has a file open, it counts as busy, never as closed. A SQLite database (by content, name or pattern; an encrypted one has no signature) is never replaced, moved or recycled away from changes beside it, nor moved or placed beside changes that didn't come with it, judged on the actual names right before the change. Only "not found" means absent: anything that can't be told waits. A SQLite database with changes beside it in a `-wal` or `-journal` is never replaced, checked again under the replacement's exclusive handle. A file named `<X>-wal`, `<X>-shm` or `<X>-journal` beside `<X>` never syncs, whatever `<X>` is, and is never moved, recycled or replaced here.

### Hooks
18. **A change in the cloud never becomes code that runs.** A hook's program, and any script it runs, must be outside every folder OneUpDrive syncs (every data folder's pairs and vaults) and every folder another sync app registered or manages, compared case-insensitively as written, resolved, and across every hard link; if that set can't be listed in full, every hook is refused. A cloud-controlled value (a shared file's name, an error detail) reaches the program only as data — environment variables (`ONEUPHOOK_*`) and a JSON line on standard input — never on the command line of a program that re-parses it: a template argument is allowed only for a real `.exe` that isn't a known interpreter, and refused otherwise. Checks run when the hooks load and again, against folders read fresh, immediately before each start, with the program (and script) opened denying writers/deleters and checked for a swap. Hooks start contained — in a job, at below-normal priority, with `ONEUP_*` out of the environment and synced folders off `PATH` — and OneUpDrive's control pipe serves a client only while it is running and not one of the hook processes, so a hook can't approve a safety stop. Hooks change nothing through OneUpDrive: their file changes are ordinary changes, like any program's ([hooks.md](hooks.md)).

## Recovery

A bounded, configurable local version store (`oneup versions`, `oneup restore`), the activity log (`oneup activity`), plus OneDrive's own version history and recycle bin. The Synced tree's history lets a folder be rewound to an earlier moment, through the gate and always after the user's approval; deleted items it recorded come back from OneDrive's recycle bin by ID; a conflict's copy not kept goes to the version store and the recycle bin ([sync-engine.md § Rewinding a folder](sync-engine.md#rewinding-a-folder-cratesoneup-syncsrcrewindrs)). The settings window's **Recovery** page has all of it.

## Code structure

* Destructive filesystem and network calls live in **one** crate (`oneup-effects`), behind typed tokens that the safety gate (`oneup-gate`) issues. The planner can't call them, and nothing else can create the tokens.
* Changing who can open an item (removing a sharing link or people's access, setting its expiry) never touches content but changes OneDrive for others, so it takes the same path: the gate's `sharing::PermissionChange` token, issued only for the permission exactly as the user saw it, and `oneup_effects::sharing`, which re-reads it and sends the request with `If-Match` (invariant 2). The change is recorded ahead and its outcome judged by reading OneDrive back, then, or on a later run (invariant 7). See [remote-mirror.md § Sharing](remote-mirror.md#sharing).
* The planner and the safety gate are pure (no I/O), so they are deterministic and run under simulation ([sync-engine.md § Simulation](sync-engine.md#simulation-cratesoneup-synctestssimrs)).
* Changes to the safety gate or the effects layer need two reviews: the maintainer's and, while there is one maintainer, an independent model review recorded in the PR ([CONTRIBUTING.md](../../CONTRIBUTING.md#what-we-look-for-in-a-pr)). No release ships with an open data-safety issue.
