# Instant search

`crates/oneup-store/src/search.rs` (the index), `bins/oneup/src/search.rs` (results and their placement), `oneup find`, the settings window's Files search, the tray's hotkey. User guide: [Finding files](../user-guide/search.md).

The Remote tree already holds every name in OneDrive, kept current by the change feed ([remote-mirror.md](remote-mirror.md)). Search is an index over those names, so it needs no network, downloads nothing, and finds online-only files, which Windows Search can't without downloading them.

## The index
`remote_name` is an FTS5 table with the **trigram** tokenizer (SQLite's bundled build has FTS5): every run of three characters of a name is a term, so any substring of three or more characters finds the name, in any case. Each name is indexed between two marks, `U+0001` before and `U+0002` after (no name holds a control character), so a query can also ask for names that start with the needle, or are exactly it (below). Chosen for size, measured on a synthetic drive of mixed names (photos, code, documents, media, cache-like names; 21 characters on average) at 1M and 3M items:

| Design | Bytes per item |
|---|---|
| Trigram table storing names and IDs (the default FTS5 table) | 134 |
| Contentless, with column sizes and delete-by-key | 76 to 102 |
| **Contentless, no positions, no column sizes, packed ID** (this one) | **37 to 41** with numeric IDs, **50 to 54** with `s<GUID>` IDs, plus about 2.4 for the marks and 3 to 5 for the item number |
| The trigram terms alone (a floor) | 29 |

* **Contentless** (`content=''`): names stay in `remote_item` only.
* **No positions** (`detail=none`): a query can't ask for adjacent trigrams, so it asks for items holding *all* the needle's trigrams. That can over-match (`abc` and `bcd` don't make `abcd`), so every candidate is checked against its stored name (`oneup_sync::fold`, as names are compared everywhere else). Over-matching is rare: a few extra reads per 50 results.
* **No column sizes** (`columnsize=0`): they only serve ranking. FTS5 then can't delete an entry by its key alone, so removing one gives the exact name it was made with (below).
* **Packed ID** (`contentless_unindexed=1`, one stored column): an entry keeps only what follows the drive's prefix (`<16 hex digits>!`, the same for every item, read from the root's ID), as an integer for OneDrive's numeric IDs and as 16 bytes for its `s<32 hex digits>` IDs; anything else whole. Unpacking can't be wrong for a stored item: an ID that doesn't come back finds no row, and a hit is checked by name anyway.
* **Item number** `remote_item.sk`: an entry's key. FTS5 needs an integer key, and `remote_item` is keyed by its text ID. A number from a sequence that never repeats (the queue's, below), so an old entry is never mistaken for a new item's.

**Budgets:** a substring search under 100 ms over 3M items, and at most 64 bytes per item for the index. `crates/oneup-store/tests/search_scale.rs` measures both through the store's own writes and search (ignored by default; `SEARCH_SCALE_ITEMS`, `SEARCH_SCALE_IDS=guid`). At 3M items: 42.5 bytes per item in all with numeric IDs; 57.5 with `s<GUID>` IDs (measured at 1M, where the size per item is the same): the trigram terms take 29 and a 16-byte ID with its row about 25. The budget is set to fit GUID IDs, since no mapping from entries back to items measured smaller. The slowest search took 31 ms from a fresh connection with a 4 MiB cache, common substrings 1 to 28 ms, for every needle measured (common, rare, exact names, multi-word, none found). A scan of the names takes about a second.

## Keeping it current
Triggers on `remote_item` see every insert, rename and deletion, whoever makes it (the same reasoning as the dirty marks, `dirty.rs`). They don't write the index: FTS5 flushes its pending writes at every statement inside a trigger, which made each stored item cost about 45 µs instead of 5. The triggers queue the change in `search_queue` (an insert numbers the item from the queue's sequence), and every write path (`Store::write`, `try_write`, the executor's non-waiting `try_write_now`) ends in one commit helper that applies the queue just before it commits, in the same transaction: about 20 to 30 µs per new item in all (5 µs without the index), a minute or so over a 3M-item first listing, nothing for items that don't change.

Applying is defensive, because a wrong removal is the one thing FTS5 punishes: removing an entry that isn't there fails with "database disk image is malformed". So each queued change is applied only if the entry is (for a removal) or isn't (for an addition) there, which also makes repeats harmless. If applying fails anyway, the queue is dropped and the index marked broken, and the caller's write commits as if nothing happened: a broken index costs search, never sync. A full disk or a lock still fails the write, as it would without the index. A broken index is emptied and built again (below). Listing OneDrive from scratch (`clear_remote`) empties the index in one statement, with a flag in `meta` (`search.clearing`) that the delete trigger checks, so the millions of rows it deletes queue nothing.

## Building it once
A store from before the index has items without a number. `Store::search_build` numbers and indexes them in steps of 20,000 items, each its own short transaction, walking `remote_item` by key from where the last step stopped (`meta` `search.build_after`), so other programs' writes wait a fraction of a second at most: 10 s for 1M items, 56 s for 3M. The agent does it when it starts, before its first round; before every step (the first included) it checks that it isn't paused in both directions or stopping, and stops there if it is; a search made before it's done finishes the build first (the window shows the count). Items added meanwhile are indexed by the triggers already.

After the build, index upkeep reads only the changes. An indexed search uses the index and looks up each candidate by key. `index_upkeep_and_search_never_scan_the_tree` checks the query plans. `once_built_upkeep_reads_no_whole_table` and the mirror's `an_update_reads_no_whole_table` record the queries and check for scans of tables that grow with the drive.

## Results
**Ranking** (`Ops::search_names`): exact names first, then names starting with the needle, then the rest, the latest added to the index first within each. Three queries in that order: the needle between both marks, after the start mark, and alone. The first two are selective (a name must start, and end, with the needle's letters), so every exact name comes first however many newer names merely contain the needle. Each query stops once enough are found (50 by default, and one more to know there are more), so a common needle costs what it lists. A query reads at most 20,000 candidates; one that stops there without enough says so ("Too many matches. Type more.") rather than "Nothing found", since later candidates may hold real matches. Reading every candidate and ranking the best instead took 100 to 130 ms for common needles at 3M items.

**Limit of the ranking:** without positions, the exact and prefix queries check the needle's trigrams and the marks but not their order, so they can over-match (`bu-00001-budget-et` holds every trigram of `<start>budget<end>`). Over-matches are dropped by the name check, but they count toward the query's 20,000-candidate cap: with more than 20,000 such names newer than an exact `Budget`, the exact query stops first, says so (*too many*), and `Budget` may then come only among the later matches, or not at all. It takes deliberately adversarial names; real drives don't have them. Fixing it would need positions (about 30 B/item more) or an index of folded names (an ID per item more).

`oneup_app::search::find` turns hits into results: the item's path in OneDrive (`path_of`) and its **placement**: *in OneDrive* for a package (a OneNote notebook, the Personal Vault), which is never synced ([planner.md](planner.md)) and has only **Open in OneDrive** (its web page, `open_in_onedrive`); *excluded* for an excluded folder or a path the rules leave out; *not synced* outside the synced folder; otherwise from the item's attributes on this PC (*online-only* by the recall-on-data-access attribute, *here*, or *not here yet* when it's absent). Attributes only, after `expose_placeholders`, so looking never downloads a file. Items with no copy on this PC (in OneDrive, excluded, not synced) offer **Open in OneDrive**.

**All words** splits the query on whitespace. OneDrive scope intersects the trigrams from every term of at least three characters, then checks every term against each folded candidate name, including shorter terms. At least one term must supply trigrams. Matches follow index insertion order, newest first, with the same candidate cap as contains-text search. Regex search streams names on explicit submit and stops at the result limit.

**Synced folder** combines matches from the selected pair's Local and Remote trees. The remote query starts at the paired folder's stored ID and follows the parent index. It applies the result limit to matches within that subtree. The result list merges matching relative paths from both trees and includes local files that are waiting to upload.

### Path and metadata search

`oneup_app::search::browse` handles folder scope, path words, metadata filters, and alternate sorts. These searches run on submit. A folder scope checks the listed IDs and their stored paths before walking the subtree. The walk reads the Local and Remote trees through their parent indexes in one SQLite snapshot. It uses the local row for duplicated paths in a synced pair. OneDrive scope keeps cloud metadata and uses the stored local row for availability filters. Search uses stored metadata and reads no file contents.

The search retains the best requested results and one extra match in a bounded heap. **Load more** requests a longer prefix in steps of 50, with a 500-result limit. A submitted one-word search can suggest a filename word one edit away, including an adjacent transposition. It uses the same scope and metadata filters.

Saved searches live in the window's state database under `ui.saved_searches`. Adding, replacing, and removing a preset each use one transaction. Running a saved search uses the current snapshot.

## OneDrive's search inside files
Opt-in, because it sends the search text to Microsoft: Graph's documented `search(q='…')` below the drive's root, one page of up to 200 results. For an extra pair the client is scoped like the pair's agent (`oneup_app::search::graph`, `pairs::scoped`): the search covers the pair's OneDrive folder only, in another person's drive for a shared folder, and **Open in OneDrive** asks that drive for the item's page. The settings window calls it only on **Search** or Enter, and its handler refuses unless `[search] onedrive` is on; `oneup find --onedrive` is the person's choice for that one search. Results the mirror holds get their path and placement from it; the others (inside an excluded folder, or newer than the last check) are placed by the path OneDrive gives and the rules, like any other result (*not here yet* when OneDrive gives no path). The request is labelled: its errors and log lines name it "OneDrive search", never its URL (which holds the text), errors leave out OneDrive's reply (which may repeat it), and it isn't retried after a network error, whose log line would otherwise carry the URL.

## The hotkey
`[search] hotkey` (none by default; `oneup search --hotkey`, the Files search). The tray holds it (`RegisterHotKey` on its hidden window, `oneup_sys::tray::Tray::set_hotkey`) and opens the settings window's Files search when it's pressed. Changing the setting raises a named event the tray waits on, so it takes up the new keys without polling. Keys another program holds are refused by Windows; the tray says so in a notification.

## Limits
* **Excluded subtrees** are one opaque row in the mirror, never listed, so nothing inside them is found; every result list says so. The excluded folder itself is found.
* **Synced folder** searches its Local tree directly. Files waiting to upload appear in Synced folder and in indexed local drive results.
* **Folding:** FTS5 folds case its own way (Unicode lower case) and results are checked with `oneup_sync::fold` (simple upper case per character). Where they disagree (the Kelvin sign, say) a name may not be found; diacritics count (`cafe` doesn't find `café`).
* **Order:** by how recently an item entered the index, not by when it changed: an upgraded store's existing items all count as newer than ones added before the build reached them.
* Dropping a `contentless_unindexed` FTS5 table leaves its `_content` table behind; a schema change that removes the index must drop that too.

## Local volume catalog

The opt-in worker maintains a database for each fixed NTFS or ReFS drive with an accessible USN journal. A drive letter, volume serial, and root file ID identify the catalog. The database lives under the profile's drive-index directory and never supplies sync state.

The metadata scanner takes a journal bookmark before its first pass. Between listing steps it applies the journal to the folders it has listed and moves the bookmark up (`Scan::follow_journal`), since a whole drive can take longer to list than its journal keeps history: 32 MiB by default, which a system drive can turn over in a few hours, or in minutes during a build. Without this, every scan of such a drive would end with a lost bookmark and start over. The journal is read for the scan, its name index and its compaction by a thread of its own (`JournalPump`, from the scan's bookmark), which queues every record it reads (up to a number set by the memory profile, 262,144 to 4,194,304, about 100 bytes each) and keeps up with any burst of changes: installing a Python environment wrote 300,000 records in a minute (measured), enough to turn the journal over between two steps that each write a large catalog for a minute or more. What it read is applied between steps (`Scan::follow_pumped`), then by the observer (`Observer::catch_up_pumped`): each call applies at most what was queued when it began, 4,096 records per transaction, every chunk checked to start at the tree's position. Journal loss shows only as the thread finding records gone. Its reads wait at most 5 s, so a dropped pump's thread ends soon even on a quiet drive. Applying only works if it outpaces the disk: a step lists for at most 10 s (`Config::list_budget`) before it writes and the journal is read again, and a folder with many changes in one batch is read from one listing ([local-tree.md § Keeping it current](local-tree.md#keeping-it-current-the-change-journal-observer)), which follows a build's churn at about 3 MiB of journal a second at background priority (measured; it was about 0.3 MiB/s, which a build could outrun until the journal wrapped and the scan started over, every few hours, without end). If the journal loses records during a scan anyway (a reset, or a scan paused for long), the scan starts over at once instead of finishing a tree it can't bring up to date. A scan from scratch after journal loss, an older scanner or changed rules gets a new, empty catalog file (`start_over`), and the scan checks the volume at the drive's root is the one the catalog is named for: emptying a large drive's rows one by one took 8 to 15 minutes, every row firing the catalog's triggers, and wrote the table out again through the WAL. The old file is moved aside first, which Windows refuses while a search has it open; then it's emptied in place instead, and its -shm and then its -wal only go once it has, so a new database never meets the old WAL, and one put back keeps it. Once the scan ends, the observer applies later journal records in bounded batches. The worker scans one drive at a time, and a first scan can take hours, while a busy system drive turns its journal over in minutes: so between a scan's steps, every 30 s or as often as their journals need, it also catches up the other drives' ready catalogs from their journals (`Others`, opened only once a scan runs), for at most 10 s each time and starting with a different drive, so the scanned drive's own journal is read again soon. A catalog that can't be followed then (not ready, or its journal lost records) is left for its own turn. The worker waits on a settings-change event between catch-ups: a minute, or a quarter of the shortest time a drive's journal reaches back (the age of its oldest record), at least 5 s. A system drive's 32 MiB can hold only a minute or two: test runs in its temp folder wrote 3,800 records a second (measured). Nothing long may leave a catalog's journal unread: building the name index after a scan reads the drive's journal every 10 s and follows the other drives' between its batches. Queries check the bookmark against the live journal before and after reading results. An unreadable journal, a changed journal ID, or a cursor outside the retained range hides the catalog. Lost journal history calls for a fresh scan. Search settings control pause, and the worker uses the configured agent priority. The status file names the drive being scanned as indexing while the scan runs. The worker writes to `drive-index.log` in the profile (the previous run's in `drive-index.log.1`): why a drive scans again, each drive failure once until it changes or clears, and every 5 minutes of a scan (and at its end) the entries listed, the rate since the last line, and the seconds spent listing, writing and following the journal (`ScanLog`).

Triggers record changed file IDs in a durable queue. The worker uses set-based SQLite writes to apply bounded batches to a contentless trigram index, with a separate row-number mapping for 128-bit file IDs. Search verifies each indexed name against the current row and rechecks the live file identity and parent directory access before displaying a result. The scanner skips protected roots by ID and skips unpopulated Cloud Files folders. The query refuses catalogs built with an old protected-root set.

**Exclusions.** A catalog follows the profile's exclusion rules where they mean the same on every drive: the presets and the unanchored lines of `[rules] exclude`. A line with a `/` before its end is anchored to the synced folder, and doesn't apply to a drive. The scan leaves out folders those rules exclude by name (`RuleSet::pruning`), with the built-in `.oneup`, `$Recycle.Bin` and `System Volume Information`. The rest (file patterns such as `*.log`, and folder rules `pruning` leaves out because a `!` line could re-include them) hide results when a search shows them. Changed rules, or a protected root added or gone, adjust a finished catalog in place (`reapply_rules`, by name and by folder ID): an excluded folder's rows go, and an included folder is listed by itself, without a new scan.

**Write cost.** A scan writes millions of rows keyed by file ID, so the order of the keys and the page cache decide most of its database time. A catalog stores file IDs as `KeyOrder::Ordered` keys: big-endian, an NTFS reference's 48-bit record number ahead of its sequence number. Neighbouring MFT records (a folder's files, made together) then fall on the same B-tree pages, where native little-endian keys sort by the record number's lowest byte and spread every folder over the whole table. Sync databases keep native keys: their initial choices name items by those bytes. While a scan runs, the store's page cache is raised to 8 times the memory profile's, from 32 MiB to 512 MiB (`oneup_local::scan_cache_kib`), and put back afterwards; sync scans get the same. The catalog worker uses the scanner's default steps (4,096 folders or 32,768 entries per transaction). `oneup-store`'s `scan_order_cost` benchmark measures the database's share of a scan (no listing). For 5 million entries (a 1 GB catalog) in a release build:

| Keys | Cache | Folders per step | Records | Scan | Rows/s | Compacted |
|---|---|---|---|---|---|---|
| native | 4 MiB | 256 | clustered | 657 s | 7,600 | 1,009 → 920 MiB |
| native | 128 MiB | 4,096 | clustered | 383 s | 13,100 | 1,010 → 920 MiB |
| ordered | 128 MiB | 4,096 | clustered | 156 s | 32,100 | 1,099 → 914 MiB |
| native | 128 MiB | 4,096 | random | 372 s | 13,500 | 1,011 → 921 MiB |
| ordered | 128 MiB | 4,096 | random | 385 s | 13,000 | 1,010 → 921 MiB |

`clustered` gives a folder's entries a run of nearby MFT records, a fifth of them reused from anywhere; `random` puts every entry anywhere, the worst case for ordered keys, where they cost the same as native ones. Compaction after the scan frees 9% (native) to 17% (ordered) of pages left part full as they split.

**Format.** A catalog's file name carries its format (`.v2.db`, ordered keys). The worker removes catalogs of an earlier format and scans those drives again, which happens once after an update that changes the format.

**Compaction.** A catalog is compacted (`VACUUM`) once its first scan, or any later full scan, finishes: pages that a scan fills out of order are left part empty. Settings (**Compact**, next to the index size) and `oneup search --compact-index` compact all catalogs on request. With the worker running, it compacts each ready catalog after its next update; with indexing paused, the request is carried out by the caller. Compaction is skipped, and logged, when the disk lacks room for twice the catalog. Settings shows the catalogs' size on disk and what compacting frees at least: their free pages, read from each catalog without opening it for writing (`Store::peek_space`). Compacting rewrites the whole catalog, minutes for a gigabyte, on a thread of its own while the worker follows the other drives' journals; the catalog's own journal goes unread meanwhile, so a catalog is compacted only if its drive's journal reaches back at least 30 minutes (`compaction_fits`), and otherwise left as it is, with a line in `drive-index.log`.

## Mapped network shares

A separate opt-in setting discovers the current Windows session's mapped UNC targets. Each mapping has its own name catalog under the profile's share-index directory. It is keyed by drive letter and UNC target. The worker opens a subtree notification watch before scanning and applies changes collected during the scan before marking the catalog available. A disk-backed queue bounds folder traversal. The worker handles changed names and security notifications by rechecking the named entry or subtree. The catalog stores paths and names. Results check folder access and read current file metadata from the share.

Queries require a live watch-session marker for the current root identity. A disconnect, remap, pause, worker restart, or lost notification stream invalidates the session. Reconnecting starts a new snapshot because the share has no replayable journal. The scanner skips reparse points, recall-on-access entries, and protected local roots identified through the share. Servers must supply extended directory metadata, file IDs, and Windows subtree notifications. [Windows subtree notifications](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)

Everywhere interleaves results from local volumes, mapped shares, and configured OneDrive mirrors. It collapses copies with the same local path and repeated remote IDs. Each OneDrive result retains the pair needed to open it.
