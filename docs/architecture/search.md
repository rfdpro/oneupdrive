# Instant search

`crates/oneup-store/src/search.rs` (the index), `bins/oneup/src/search.rs` (results and their placement), `oneup find`, the settings window's Search page, the tray's hotkey. User guide: [Finding files](../user-guide/search.md).

The Remote tree already holds every name in OneDrive, kept current by the change feed ([remote-mirror.md](remote-mirror.md)). Search is an index over those names, so it needs no network, downloads nothing, and finds online-only files, which Windows Search can't without downloading them.

## The index
`remote_name` is an FTS5 table with the **trigram** tokenizer (SQLite's bundled build has FTS5): every run of three characters of a name is a term, so any substring of three or more characters finds the name, in any case. Each name is indexed between two marks, `U+0001` before and `U+0002` after (no name holds a control character), so a query can also ask for names that start with the needle, or are exactly it (below). Chosen for size, measured on a synthetic drive of mixed names (photos, code, documents, media, cache-like names; 21 characters on average) at 1M and 3M items:

| Design | Bytes per item |
|---|---|
| Trigram table storing names and IDs (the default FTS5 table) | 134 |
| Contentless, with column sizes and delete-by-key | 76 to 102 |
| **Contentless, no positions, no column sizes, packed ID** (this one) | **37 to 41** with numeric IDs, **50 to 54** with `s<GUID>` IDs, plus about 2.4 for the marks and 3 to 5 for the item number |
| The trigram terms alone (a floor) | 29 |

* **Contentless** (`content=''`): names stay in `remote_item` only.
* **No positions** (`detail=none`): a query can't ask for adjacent trigrams, so it asks for items holding *all* the needle's trigrams. That can over-match (`abc` and `bcd` don't make `abcd`), so every candidate is checked against its stored name (`oneup_sync::fold`, as names are compared everywhere else). Over-matching is rare: a few extra reads per 50 results.
* **No column sizes** (`columnsize=0`): they only serve ranking. FTS5 then can't delete an entry by its key alone, so removing one gives the exact name it was made with (below).
* **Packed ID** (`contentless_unindexed=1`, one stored column): an entry keeps only what follows the drive's prefix (`<16 hex digits>!`, the same for every item, read from the root's ID), as an integer for OneDrive's numeric IDs and as 16 bytes for its `s<32 hex digits>` IDs; anything else whole. Unpacking can't be wrong for a stored item: an ID that doesn't come back finds no row, and a hit is checked by name anyway.
* **Item number** `remote_item.sk`: an entry's key. FTS5 needs an integer key, and `remote_item` is keyed by its text ID. A number from a sequence that never repeats (the queue's, below), so an old entry is never mistaken for a new item's.

**Budgets:** a substring search under 100 ms over 3M items, and at most 64 bytes per item for the index. `crates/oneup-store/tests/search_scale.rs` measures both through the store's own writes and search (ignored by default; `SEARCH_SCALE_ITEMS`, `SEARCH_SCALE_IDS=guid`). At 3M items: 42.5 bytes per item in all with numeric IDs; 57.5 with `s<GUID>` IDs (measured at 1M, where the size per item is the same): the trigram terms take 29 and a 16-byte ID with its row about 25. The budget is set to fit GUID IDs, since no mapping from entries back to items measured smaller. The slowest search took 31 ms from a fresh connection with a 4 MiB cache, common substrings 1 to 28 ms, for every needle measured (common, rare, exact names, multi-word, none found). A scan of the names takes about a second.

## Keeping it current
Triggers on `remote_item` see every insert, rename and deletion, whoever makes it (the same reasoning as the dirty marks, `dirty.rs`). They don't write the index: FTS5 flushes its pending writes at every statement inside a trigger, which made each stored item cost about 45 µs instead of 5. The triggers queue the change in `search_queue` (an insert numbers the item from the queue's sequence), and every write path (`Store::write`, `try_write`, the executor's non-waiting `try_write_now`) ends in one commit helper that applies the queue just before it commits, in the same transaction: about 20 to 30 µs per new item in all (5 µs without the index), a minute or so over a 3M-item first listing, nothing for items that don't change.

Applying is defensive, because a wrong removal is the one thing FTS5 punishes: removing an entry that isn't there fails with "database disk image is malformed". So each queued change is applied only if the entry is (for a removal) or isn't (for an addition) there, which also makes repeats harmless. If applying fails anyway, the queue is dropped and the index marked broken, and the caller's write commits as if nothing happened: a broken index costs search, never sync. A full disk or a lock still fails the write, as it would without the index. A broken index is emptied and built again (below). Listing OneDrive from scratch (`clear_remote`) empties the index in one statement, with a flag in `meta` (`search.clearing`) that the delete trigger checks, so the millions of rows it deletes queue nothing.

## Building it once
A store from before the index has items without a number. `Store::search_build` numbers and indexes them in steps of 20,000 items, each its own short transaction, walking `remote_item` by key from where the last step stopped (`meta` `search.build_after`), so other programs' writes wait a fraction of a second at most: 10 s for 1M items, 56 s for 3M. The agent does it when it starts, before its first round; before every step (the first included) it checks that it isn't paused in both directions or stopping, and stops there if it is; a search made before it's done finishes the build first (the window shows the count). Items added meanwhile are indexed by the triggers already.

After that, nothing reads the whole tree: upkeep costs what changes, and a search costs the index lookup plus one lookup by key per candidate. `index_upkeep_and_search_never_scan_the_tree` checks the query plan of every statement the index runs; `once_built_upkeep_reads_no_whole_table` and the mirror's `an_update_reads_no_whole_table` record what runs and check none of it scans a table that grows with the drive.

## Results
**Ranking** (`Ops::search_names`): exact names first, then names starting with the needle, then the rest, the latest added to the index first within each. Three queries in that order: the needle between both marks, after the start mark, and alone. The first two are selective (a name must start, and end, with the needle's letters), so every exact name comes first however many newer names merely contain the needle. Each query stops once enough are found (50 by default, and one more to know there are more), so a common needle costs what it lists. A query reads at most 20,000 candidates; one that stops there without enough says so ("Too many matches. Type more.") rather than "Nothing found", since later candidates may hold real matches. Reading every candidate and ranking the best instead took 100 to 130 ms for common needles at 3M items.

**Limit of the ranking:** without positions, the exact and prefix queries check the needle's trigrams and the marks but not their order, so they can over-match (`bu-00001-budget-et` holds every trigram of `<start>budget<end>`). Over-matches are dropped by the name check, but they count toward the query's 20,000-candidate cap: with more than 20,000 such names newer than an exact `Budget`, the exact query stops first, says so (*too many*), and `Budget` may then come only among the later matches, or not at all. It takes deliberately adversarial names; real drives don't have them. Fixing it would need positions (about 30 B/item more) or an index of folded names (an ID per item more).

`oneup_app::search::find` turns hits into results: the item's path in OneDrive (`path_of`) and its **placement**: *in OneDrive* for a package (a OneNote notebook, the Personal Vault), which is never synced ([planner.md](planner.md)) and has only **Open in OneDrive** (its web page, `open_in_onedrive`); *excluded* for an excluded folder or a path the rules leave out; *not synced* outside the synced folder; otherwise from the item's attributes on this PC (*online-only* by the recall-on-data-access attribute, *here*, or *not here yet* when it's absent). Attributes only, after `expose_placeholders`, so looking never downloads a file. Items with no copy on this PC (in OneDrive, excluded, not synced) offer **Open in OneDrive**.

The needle must have three characters: the trigram tokenizer gives a shorter query no terms, and a scan of every name would take about a second at 3M items, too slow to run as someone types.

## OneDrive's search inside files
Opt-in, because it sends the search text to Microsoft: Graph's documented `search(q='…')` below the drive's root, one page of up to 200 results. For an extra pair the client is scoped like the pair's agent (`oneup_app::search::graph`, `pairs::scoped`): the search covers the pair's OneDrive folder only, in another person's drive for a shared folder, and **Open in OneDrive** asks that drive for the item's page. The settings window calls it only on **Search** or Enter, and its handler refuses unless `[search] onedrive` is on; `oneup find --onedrive` is the person's choice for that one search. Results the mirror holds get their path and placement from it; the others (inside an excluded folder, or newer than the last check) are placed by the path OneDrive gives and the rules, like any other result (*not here yet* when OneDrive gives no path). The request is labelled: its errors and log lines name it "OneDrive search", never its URL (which holds the text), errors leave out OneDrive's reply (which may repeat it), and it isn't retried after a network error, whose log line would otherwise carry the URL.

## The hotkey
`[search] hotkey` (none by default; `oneup search --hotkey`, the Search page). The tray holds it (`RegisterHotKey` on its hidden window, `oneup_sys::tray::Tray::set_hotkey`) and opens the settings window's Search page when it's pressed. Changing the setting raises a named event the tray waits on, so it takes up the new keys without polling. Keys another program holds are refused by Windows; the tray says so in a notification.

## Limits
* **Excluded subtrees** are one opaque row in the mirror, never listed, so nothing inside them is found; every result list says so. The excluded folder itself is found.
* **Only the Remote tree** is indexed: a file on this PC that hasn't been uploaded yet isn't found.
* **Folding:** FTS5 folds case its own way (Unicode lower case) and results are checked with `oneup_sync::fold` (simple upper case per character). Where they disagree (the Kelvin sign, say) a name may not be found; diacritics count (`cafe` doesn't find `café`).
* **Order:** by how recently an item entered the index, not by when it changed: an upgraded store's existing items all count as newer than ones added before the build reached them.
* Dropping a `contentless_unindexed` FTS5 table leaves its `_content` table behind; a schema change that removes the index must drop that too.
