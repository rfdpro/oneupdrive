# The sync engine

How OneUpDrive decides what to do once it has a **Synced tree** (the record of what both sides last agreed on), and how it carries it out. The reconciler (`crates/oneup-sync`) only *proposes* operations: it has no I/O and can't touch user content. Everything destructive goes through the safety gate (`crates/oneup-gate`) and the effects layer (`crates/oneup-effects`), run by the executor (`crates/oneup-exec`). The first-run case without a Synced tree is [planner.md](planner.md).

## Three trees
| Tree | Keyed by | Kept current by |
|---|---|---|
| **Local** (`local_item`) | 128-bit NTFS file ID | the scan, then the change-journal observer ([local-tree.md](local-tree.md)) |
| **Remote** (`remote_item`) | drive item ID | the mirror and `/delta` ([remote-mirror.md](remote-mirror.md)) |
| **Synced** (`synced_item`) | our own integer `sid` | the executor, after each operation succeeds |

A Synced row links one local file ID and one remote item ID. It also holds the agreed location (parent `sid` + name) and content (size, QuickXorHash), plus the stamps each side had at that moment (local last-write time, remote eTag). Comparing each side to its Synced row says **which side changed**. Timestamps are never compared across sides.

## Deletion needs evidence
Each side reports one of three states for an item it used to have:

* **Present**: the item still exists, possibly moved or changed.
* **Deleted**: there is *explicit evidence*. That's a USN delete record, a delta `deleted` facet, the item's path in the user's Recycle Bin, an ancestor deleted with such evidence, or our own executor having removed or detached it.
* **Missing**: the item is gone with no evidence, e.g. after a journal loss and rescan, or a mirror rebuild. **Missing never causes a deletion.** The item is held and reported (data-safety invariant 3).

## Merge rules (one Synced item)
Changes are found per side by comparing against the Synced row. *Moved* means a different parent or a different name, including case-only renames. *Changed* means different content. Locally that's a new file ID at the same path, or a different size or last-write time, unless a fresh hash proves the content is unchanged ("touched"). In the cloud it's a different QuickXorHash or size.

| Local \ Cloud | unchanged | changed | moved | deleted |
|---|---|---|---|---|
| **unchanged** | — | download (replace) | move locally | recycle locally (folders: once empty) |
| **changed** | upload (replace) | equal hash → record; unknown → hash first; else **conflict: keep both** | move first, content next round | **re-create in the cloud** |
| **moved** | move in the cloud | move first, content next round | same place → record; else the cloud's location wins (a move, not a loss) | **re-create in the cloud** |
| **deleted** | delete in the cloud (to its recycle bin; folders: once empty) | **re-create locally** | **re-create locally** | forget |

Missing on either side, with the other side present, means **hold**: report it, don't act.

Principles behind the table:
* **A change beats a deletion.** Deleting is only propagated for content the deleting side had last seen.
* **Conflicts keep both copies.** The local copy is renamed to `name (conflict N).ext` and detached from the Synced item. The next round uploads the renamed copy and downloads the cloud version to the original name. Nothing is overwritten.
* **One operation per item per round.** A move and a content change are separate rounds, so every operation's preconditions are about the state the planner saw.
* **Replaced local content is in the cloud's version history.** Downloads only replace a local file whose stamp still matches what was last synced (both sides changed is a conflict, which keeps both), so its content is a version OneDrive already has. By default no local copy is kept, but only after the effects layer has proved it by hashing the file under its exclusive handle; otherwise, or with `keep_replaced` on, the old copy goes to the local version store ([below](#version-store-overflow-and-replaced-files)).

## New items
* **One side only:** upload or download (folders: create). Children of a new folder wait until the folder is synced.
* **Both sides, same name:** two folders are paired. Two files are paired only if they have the same size and the same hash; otherwise the hash is computed first. Anything else (different content, file vs folder) is a conflict, and the local item is renamed. This is also how the **first sync** adopts an existing folder: nothing is deleted or overwritten.
* **Atomic saves** (write a temp file, rename it over the original; the file ID changes): a Synced file whose local ID was deleted, plus a new local file with the same name in the same folder, is treated as an *edit* of the Synced file. The cloud item keeps its ID and version history.

## Folders
* A folder is deleted on the other side only **once it is empty there and no Synced rows remain under it**: children are deleted first, each under its own preconditions. Graph would delete a non-empty folder's unknown contents along with it. Dropping a folder's row early would orphan its children's rows, which would then never be planned again.
* If a folder was deleted on one side but something must now go into it there (a new or changed file, an item moved into it), the folder is **re-created** ("resurrected") first. If its parent was deleted too, the walk goes up to the highest deleted ancestor, and later rounds work back down. Unchanged children still follow the deletion.
* Moves that would put a folder inside itself (moved into each other on the two sides) are undone: one side's move is reverted rather than looping.
* **A OneDrive folder that isn't empty when deleted.** The Remote tree doesn't list what the rules leave out by name (`__pycache__`, `node_modules`…), so a folder holding only those looks empty to the planner and isn't to Graph. Graph's refusal is `CloudError::NotEmpty` → `Skip::NotEmpty`, which waits for a change (something new in the folder marks it), and the folder is listed in `oneup unsynced` (`Why::NotEmpty`) with `oneup cloud prune` as the way to clear such leftovers.

## Name collisions
After each item is decided, a resolve pass checks every operation that needs a free name, e.g. "create `b` in folder X", "move to `b`":
* If the name is being vacated this round, or another operation already claimed it:
  * a **new** item waits a round (nothing waits for a new item, so this can't deadlock);
  * a **move** goes to a temporary **staging name** (`name.oneup-staging-N`) and is renamed next round. Waiting could deadlock on swaps and rotations; staging breaks them without special cases.
* If it's taken by an item that stays, the **local** item involved is renamed to a conflict name. Local renames are cheap and lose nothing.
* At most one operation per item per round.
* **Self-healing:** if both sides end up agreeing on a staging name, the local item is renamed back to the real name (or a conflict name if that's taken), and the next round propagates it. This happens if the item was deleted on the side that held the real name and then re-created from the other side, or if a crash interrupted the round. As a result, a user's own file named like `x.oneup-staging-1` would be renamed to `x`.

## Operations and preconditions
Every operation carries the state it was planned against:
* local: file ID, plus size and last-write time for files;
* remote: item ID and eTag.

The executor re-checks these immediately before acting (data-safety invariant 5) and sends `If-Match` for remote changes. A mismatch skips the operation, and the next round re-plans from fresh state. Operations: `Pair`, `Record`, `Forget` and `Hash` (bookkeeping only); `Upload`, `Download`, `MkdirRemote`, `MkdirLocal`; `MoveRemote`, `MoveLocal`; `RenameLocal`, `RenameRemote` (one-way pairs only), `ConflictCopy`; `DeleteRemote`, `RecycleLocal`; `Dehydrate` (freeing space, [files-on-demand.md](files-on-demand.md#pinning-and-freeing-space)); `PruneRemote` (cloud cleanup, [rules.md](rules.md#cloud-cleanup)); and `Hold`.

**One-way pairs:** `plan_flow(…, Flow::Backup)` plans a backup (this PC → OneDrive; deletions here never reach the cloud, nothing changes this PC). The rules, `RenameRemote` and the final check that turns anything changing this PC into a `HoldReason::OneWay` hold are in [pairs.md § Backups](pairs.md#backups-one-way-flow-oneup_syncflowbackup).

**A move that renews the item's ID**: OneDrive moves keep IDs, but a vault entry whose stored name changes shape is rebuilt, and the decrypted item gets a new ID ([vaults.md](vaults.md#creating-vaults-the-recovery-key-passwords-windows-hello-long-names)). `MoveRemote`'s bookkeeping then points the Synced row at the new ID and renews an online-only file's identity without downloading it (`LocalFs::renew_identity`).

## Safety gate and effects
**The gate** (`crates/oneup-gate`) is pure. It reviews one round's operations and issues an `Approved` token for each one it lets through. Only the gate can create these tokens, and the effects layer accepts nothing else. It withholds operations when:
* the user hit **panic** (everything stops);
* the side the operation would change is **paused**;
* the operation is **malformed** (e.g. an upload or a replacing download without a local stamp to re-check);
* the operation is a planner **hold**;
* a **circuit breaker** has tripped. The breaker counts the round's mass-sensitive operations per side: recycles and deletes, replacing transfers, and moves. It trips when they are more than `max_count` (default 200), or more than `min_count` (20) and also more than `max_percent` (10%) of the Synced tree (`max_count` and `max_percent` are user settings: `oneup safety`, the window's **Safety** page). A second kind, the **content guard**, trips on more than `max_suspicious` (20) edited files whose new content doesn't look like their type ([usage.md](usage.md#the-content-guard)). The user approves a tripped batch by its **fingerprint**, a hash of exactly those operations, so the approval can't carry over to a different batch;
* the operation belongs to a **version-store overflow** batch awaiting the user's decision (below).

Each token also carries an `OldCopy` (`Keep` or `DropIfSynced`): what happens to the old content of a file the operation removes or replaces.

### Version-store overflow and replaced files
Data-safety invariant 1 allows, in exactly two cases, relying on OneDrive's version history or recycle bin instead of a local copy.

**Replaced files.** A file replaced by a newer cloud version (`Download { replace }`) isn't kept by default (`Policy::keep_replaced = false`; `oneup versions --set-keep-replaced on` brings it back). The planner emits a replacement only for a file unchanged since the last sync, so its content is the Synced row's version, which OneDrive keeps in its version history. The gate marks the token `DropIfSynced`. The effects layer keeps its usual order (open exclusively, check stamp and location, move the old file into a version slot, place the new one, move the old one back if that fails) and adds one step. *Before* moving anything, it hashes the old file through the exclusive handle and compares the hash with the Synced row's QuickXorHash, which the executor passes in. Only if size and hash match is the old copy deleted, through the same handle (`FileDispositionInfoEx`, `DELETE | IGNORE_READONLY_ATTRIBUTE`), once the new file is in place. Without a recorded hash, or with different content (an edit that kept the size and time), it stays in the store, and the run says so (`Report::kept_instead`).

**Overflow.** The files a round would move into the store (recycled files; replaced files too with `keep_replaced`) form one batch. Folders take no room and aren't counted. If their stamped sizes exceed the store's **room**, the gate reports an `Overflow` with its own fingerprint, distinct from breaker codes. Room is worked out by the caller (`Trim::room`: the cap minus slots younger than `min_age_days`, or the whole cap with rotation), and only when the plan would add bytes, so the store is listed only then. Then:
* `OverflowPolicy::Hold` (default): the batch is withheld (`Withheld::Overflow`) and everything else runs. It isn't a stop. The round leaves its dirty marks in place so the batch is planned again, and the user's answer finds it.
* `OverflowPolicy::Keep` (`--set-overflow keep`): approved as usual, and the user is told.
* A `Decision` with the batch's fingerprint (`--keep CODE` / `--discard CODE` on `oneup sync` and `oneupd`, or the control API): `Keep` approves it as usual. `Discard` approves it with `DropIfSynced`, so each file is deleted by handle only if it hashes to its Synced row's version (which OneDrive's recycle bin holds), and otherwise kept.

No decision is taken while local changes can't run (panic, paused, or a tripped local breaker).

**Rotation** (`Trim::rotate`, `--set-rotate on`, off by default): after the review, the caller removes the oldest slots, whatever their age, until the bytes the approved operations will keep (`Review::store_bytes`) fit under the cap (`LocalFs::make_room`). It never runs for a batch larger than the whole cap, and the after-sync trim still protects recent slots, so a batch the user chose to keep is never rotated away.

### The effects layer
`crates/oneup-effects` is the only code that changes user content. Every effect re-checks its preconditions on the very handle it then acts through:
* **The item is opened by file ID.** Files are opened exclusively, so nobody can write, rename or delete them between the check and the change, and a file another program has open is reported as *busy*. Handle-based renames need a path-opened handle (NTFS rejects renames through handles opened by ID), so the item is located by ID, opened by path, and its ID compared again.
* **Size and last-write time must still match the planned stamp.** Links and other reparse points are never touched; placeholders only through the Files On-Demand effects.
* **Destination folders are pinned.** They're opened without delete sharing, so they can't be moved away while something is placed in them.
* **Paths stay inside the sync folder, outside `.oneup`.** Names are checked: no separators, `..`, device names, or trailing dots or spaces.
* **Renames never replace.** `FILE_RENAME_INFO` is sent with `ReplaceIfExists = false`, so a taken name fails with *name taken* and nothing changes.
* **Downloads are written to `.oneup\staging` and then renamed into place.** That's the same volume, so placing a download is a rename. Replacing a file first moves the old one into the version store, and moves it back if placing the new one fails. A `DropIfSynced` old copy is then deleted through its handle, if it was proved to be the synced version (above).
* **Recycling moves, it doesn't delete.** The item moves to `.oneup\versions\<time>-<n>\<name>`, with an `origin.txt` giving its former path, for `oneup restore`. Using our own version store rather than the Windows Recycle Bin keeps the move atomic and checked; the Recycle Bin API works by path and can race. The one exception is a file in a batch the user chose to discard, deleted by handle once proved to be the synced version.

`.oneup` directly in the sync folder also holds `root.marker`, the folder's identity token (data-safety invariant 4). The folder must still have the recorded volume serial and file ID *and* carry the marker, or everything halts. Both trees exclude `.oneup` at the top level: the scanner and observer classify it as excluded, and the mirror treats a drive-root folder of that name as excluded. A deeper folder of that name is ordinary.

### The version store
`oneup versions` (list), `oneup restore` (moves an item back by handle, never replacing: a taken name gets ` (restored N)`) and explicit pruning (`versions --older-than-days/--max-gib`, a preview unless `--yes`), all in the effects layer (`LocalFs::versions/restore/prune_versions`). **Automatic trimming** (`oneup_effects::versions::Trim`) runs after a settled round, never during one. Items younger than 30 days are never removed. Older ones go oldest first, and only while the store exceeds the smaller of 5 GiB and 2% of the disk. Settings live in the data folder's `meta` table (`versions.*`, also `rotate`, `overflow`, `keep_replaced`); both size limits at 0 turn it off. Trimming, rotation and the two `DropIfSynced` cases are the only places OneUpDrive permanently deletes user content, which is why their rules are pure and unit-tested on their own.

## Executor (`crates/oneup-exec`)
The executor runs one round's approved operations in the planner's order:
* **Local changes** go through the effects layer.
* **Cloud changes** go through a `Cloud` trait: Graph (`GraphCloud`, below), a vault (`VaultCloud`, [vaults.md](vaults.md)), an in-memory fake in tests. Every cloud change is conditional: changes to an existing item carry its planned eTag (`If-Match`), and creations fail rather than replace when the name is taken.
* **Bookkeeping** (`Pair`, `Record`, `Forget`) re-checks its preconditions against the store.

After each effect, the executor writes the rows it changed in one transaction: the Local, Remote and Synced trees, plus hashes. So the next round plans from the new state, and when the journal or delta later reports the same change, applying it again changes nothing.

Content is verified in passing:
* **Uploads** are hashed while they're read. The file is open with writers excluded, and the cloud's reported QuickXorHash must match before the item counts as synced.
* **Downloads** are hashed while they're written to staging. They must match the Remote tree's size and hash for that eTag before anything local changes.

**Crash safety.** Most operations recover on their own if the process dies between an effect and its record: the next round finds both sides agreeing and pairs or records them. Three operations take an item out of the tree in a way the change journal only sees as a move *out* (into the version store), which would otherwise be "missing without evidence" and held forever. Their records are written **ahead**:
* recycling and replacing note deletion evidence first;
* a conflict copy detaches its Synced row first, so the renamed copy can never be mistaken for a rename of the synced item.

The same transaction saves which record is pending (`exec.pending` in `meta`; operations run one at a time, so there's at most one), and the operation's final record clears it. A record left over, because the operation failed or the process died, is settled right after the operation, or at the start of the next run after a restart. If the folder itself shows the effect didn't happen, the record is undone: the evidence is withdrawn (the item is still in the folder), or the Synced row is linked again (the item still has its old name). Otherwise it stands, and the change journal reports the rest. The folder is checked directly, because the journal can lag.

**Crash-injection test.** With the test-only `crash-test` feature, `Executor::crash_after(n)` stops a round at its n-th crash point, as if the process had been killed. The crash points are after every effect (before its record) and after every write-ahead record (before its effect). `a_crash_at_any_point_of_a_round_loses_nothing` (`tests/sync.rs`) takes a round with one change of every kind on both sides (uploads, new and replacing downloads, folders, moves both ways, deletions both ways and a conflict copy), crashes it at each of its points in turn, reopens the database from disk and syncs to the end. It checks that no pending record survives the first run after the restart, that the store's invariants hold (including: no item is both present and noted deleted), that both sides agree, that every content is still somewhere (the folder, the version store, or OneDrive's recycle bin and version history), and that deletions stay deleted.

**Outcomes.** A failed precondition (changed, busy, name taken, folder not empty, content mismatch) **skips** the operation, and the next round re-plans it. A failed identity check of the sync folder, or a database error, **halts** the round.

## Cloud over Graph (`oneup-exec/src/graph.rs`, `oneup-graph`)
`GraphCloud` implements `Cloud` with these Graph calls:
* **Download:** read the item's eTag and pre-authenticated download URL. OneDrive Personal may name the URL `@content.downloadUrl` instead of `@microsoft.graph.downloadUrl`, and `$select` doesn't always return it, so the client falls back to the full item. A mismatched eTag means *changed*. The URL is then fetched **without** the bearer token. It serves whatever is current, so a change after the eTag check is caught by the executor's hash check against the planned version.
* **Upload:** a single PUT up to 4 MiB, an upload session above that (fragments sent in order, without the bearer token). Above 4 MiB a session is faster per byte than a single request, which goes through Graph itself. Fragment sizes adapt to the connection (`oneup_graph::fragment::Sizer`): from 10 MiB up to the memory profile's limit (`minimal` 10 MiB, `balanced` 40 MiB, `performance` 59.69 MiB), sized so per-request overhead stays near 10% and one fragment takes at most 30 s; on a test line, large uploads ran about twice as fast as with fixed 10 MiB fragments. New items use `@microsoft.graph.conflictBehavior=fail`; replacements send `If-Match` (for a session, on `createUploadSession`). The answer must carry the QuickXorHash, which Graph computes asynchronously, so the item is re-read a few times if it's missing. Failed sessions are cancelled.
* **Server-side copy instead of upload:** for a **new** file of at least 1 MiB, the executor looks for cloud files of exactly its size (the partial index `remote_item_copyable`; only files ≥ 1 MiB with a hash). Only if there is one does it hash the open file (no writers meanwhile) and rewind it. On a hash match, `Cloud::copy` re-reads the source and requires the planned eTag and the same hash, then `POST /items/{id}/copy?conflictBehavior=fail` and follows the monitor URL (pre-authenticated, never logged; up to ~2 min). The new item must come back with the same size and hash, as an upload's must. If its content differs (the source changed in between), the item just made is deleted again (`If-Match`, into OneDrive's recycle bin) and the file is uploaded. Any other failure, or a copy still running after the wait, falls back to an upload, which fails harmlessly as *name taken* if the copy lands after all. The activity log says the content was copied in OneDrive and nothing was sent. Copying a 300 MiB file takes 2–3 s, against 17–36 s to upload it on a test line.
* **Create folder:** POST to `children` with `conflictBehavior=fail`.
* **Move/rename:** PATCH `parentReference` + `name`, with `If-Match`. OneDrive refuses to move or rename a folder with more than its list view threshold (5,000) of items below it: **422 `notSupported`, inner code `tooManyResources`** (`CloudError::TooManyItems`). The executor then moves it in parts (`Executor::rebuild`): it checks the folder's eTag, creates a new folder at the destination (`conflictBehavior=fail`), moves the contents into it a page (`Cloud::children`, up to 1,000) and a batch (20) at a time (a subfolder that is itself too large the same way), and finally deletes the original, re-read for its current eTag, only if OneDrive confirms it empty. The new folder stands for the old one from then on: a new ID, with everything inside it keeping its own. Each step is recorded as it happens, so the store always matches the cloud. The Synced row follows the new folder as soon as it exists, so an interruption leaves what wasn't moved yet in the original folder, which the next round treats as a folder of its own (the move, done in part). Nothing is lost at any point (`a_crash_while_moving_a_large_folder_in_parts_loses_nothing`). An item a batched move reports as changed but that is already in the new folder (the answer was lost and the request resent) is recorded as moved. The original's stored rows are removed without deletion evidence: anything still stored below it was moved elsewhere meanwhile, not deleted, and reads as missing until the next listing places it (`an_item_moved_away_while_a_large_folder_is_moved_in_parts_is_not_deleted`). A change of case alone can't be done in parts (OneDrive compares names ignoring case, so the new folder can't sit next to the original), and is reported as failed. A vault can't list folders this way and reports the move as failed.
* **Delete:** DELETE with `If-Match`, after re-reading the item: Graph deletes a folder *with its contents*, so a folder with any child is refused (`NotEmpty`).
* **Batches** (`$batch`): the executor sends a run of consecutive cloud metadata changes (create folder, move/rename, delete) as one JSON batch of up to 20 (`exec.rs` `batchable`, `Cloud::batch`). Each keeps its own `If-Match` and its own outcome, and is recorded one by one afterwards in plan order, with the same crash points as alone. The group is cut conservatively before any change that depends on an earlier one in it: the same item twice, an item whose folder the group changes, a destination folder moved or deleted in it, a name freed and then taken (e.g. a swap), or a folder deleted after something in the group came out of it. Requests in a batch run concurrently on OneDrive's side. Deletions re-read their items first (one batch of GETs) for the eTag and emptiness check. Throttled or failed requests inside a batch are sent again after `Retry-After` (which pauses every other request too), a bounded number of times.
* **Restoring a version** downloads it and uploads it as a new version under `If-Match`, checked by hash, because Graph's `restoreVersion` ignores `If-Match` on OneDrive Personal.

Status mapping: 412 and 404 → *changed*, 409 → *name taken*, except that OneDrive's error code wins where there is one: in a batch, a stale eTag comes back as **409 `resourceModified`**, which must read as *changed*. Both make the executor skip and re-plan. **A new folder's eTag changes moments after it's created** (`…,1` then `…,2`): changes are planned from the cloud listing, which has the later one. Pre-authenticated URLs carry a session token, so errors label them ("upload session fragment", "download") instead of printing the URL. A refused request's error keeps at most 2 KiB of its body, so a proxy's page can't overflow problem reports or the control pipe.

**Dead connections.** Every HTTP client starts from `oneup_graph::client::http_builder`: a 20 s connect timeout, 120 s per metadata request, and TCP keepalive (15 s), so a connection that died without closing (sleep and resume, a NAT dropping it) fails. A transfer may take up to 6 hours, so a download is also abandoned after 60 s without receiving a byte; each read restarts that clock, so a slow line that keeps moving is never cut off. There's no client-wide read timeout: reqwest's also bounds the wait for the response headers, which for an upload includes sending the whole fragment. **A failed token refresh** is retried like a failed request (backoff, the token endpoint's `Retry-After`, a bounded number of attempts) when the network failed or the endpoint answered 429/5xx or something that isn't an OAuth error; only a real OAuth refusal (`invalid_grant` and the like) asks the person to sign in again. After a 401, the cached token is dropped only if it's still the one that got the 401, so a burst of 401s causes one refresh.

**Live check.** `oneup cloud-check` (hidden, developers only) refuses any data folder without the test-account marker, and any sign-in whose drive differs from the marker or matches the default folder's drive. It works inside a new `/oneup-cloud-check-<random>` folder and removes it afterwards, checking: create and refuse a taken name; small and fragmented uploads with hash and size verified; download byte for byte and refuse a stale eTag; replace by single PUT and by upload session (same item ID), refusing stale eTags; move/rename, refusing stale eTags and taken names; delete, refusing a non-empty folder and a stale eTag; server-side copy; batched create, rename and delete.

## Parking (`oneup-plan/src/park.rs`)
`Parked` wraps the store's `Trees` and hides items a sync must not transfer:
* **Problem items**, local only: names OneDrive refuses (`names::is_invalid`: forbidden characters, reserved names, leading or trailing spaces, trailing dots) and files over 250 GB. They're collected (`Parked::problems`) so the user can be told and can fix them.
* **Local-by-nature files**, on both sides: `desktop.ini`, Office lock files (`~$…`), `*.tmp` and the OneDrive app's marker file. The official client doesn't sync these either. They're also hidden in the cloud, so a stray cloud copy isn't downloaded onto the local one every round. They're skipped silently.
* **The user's rules** ([rules.md](rules.md#where-rules-apply)).

A hidden item reads as **Missing** (the `Trees` contract). So a synced file that *becomes* parked, say renamed to `report.tmp`, is held on both sides and never deleted in the cloud. The store's own filtering (links, excluded folders, lossy names, packages) is separate; parking is a pure layer, so the rule list lives with the planner's other OneDrive limits.

## Purity and scale
The reconciler reads the three trees through a small `Trees` trait: lookups by ID and children of one folder. The simulation backs it with an in-memory world, and production backs it with the indexed SQLite store. It never writes, and its output depends only on what it reads, which keeps it deterministic. It plans per **folder context**: one Synced folder, its Synced children, and the current children on both sides. Each item is decided exactly once: Synced items in their *agreed* parent's context (so moves are seen there), new items in their current parent's. In steady state only *dirty* folder contexts are planned (below), so cost follows the number of changes.

## Storage (`crates/oneup-store/src/synced.rs`)
* `synced_item(sid, parent_sid, name, kind, size, qxh, local_id, local_mtime, remote_id, remote_etag)`, indexed by parent, and with **unique** indexes on `local_id` and `remote_id`, so no item can be linked twice. Writes are upserts on `sid` alone: linking an already linked item fails instead of silently replacing the other row. Sids are never reused (the largest ever allocated is kept in `meta`), so a stale plan can't address a newer row.
* **Deletion evidence:** `local_gone(file_id)` and `remote_gone(id)`. They're written by the observer, by the Recycle Bin check ([local-tree.md](local-tree.md#the-recycle-bin-is-evidence)), and by the mirror when delta reports `deleted`: `delete_subtree` records every Synced item in the deleted subtree, because a deleted folder is evidence for its contents. Evidence is kept only for IDs a Synced row links to, the only ones the reconciler asks about, so these tables are never larger than the Synced tree. They're dropped when their row is removed or relinked, and when the item is back in its tree (triggers on `local_item` and `remote_item`: a file restored from either recycle bin, or a child delta reports moved out of a folder after the folder's deletion). Evidence for an item that is still there would turn its later disappearance without evidence into a deletion, so the consistency check refuses it on both sides. A mirror rebuild and a rescan never write evidence, and leave the Synced tree and evidence alone.
* **Forgetting a folder takes its records along.** `Ops::synced_remove` removes a folder's whole subtree of Synced records with their evidence (dropping records never deletes content), so a record whose parent is gone can't be left behind; the store's consistency check refuses such orphans.
* **Hashes:** `local_hash(file_id, size, mtime, qxh)`. A hash counts only while the file still has that exact size and mtime.
* **What the reconciler sees** (`impl Trees for Ops`): local files and folders whose contents were listed and whose names are valid Unicode; cloud files, folders and the root that aren't excluded. Links, excluded/unreadable folders, lossy names and packages are filtered out and read as **Missing** when asked for by ID, so a Synced item that becomes unsyncable is held rather than taken for a deletion. Folder sizes and times are zeroed: OneDrive reports a folder's total size, and a local folder's mtime changes with its children.
* Every lookup is one indexed query, and a folder's children are one query per side, so a round costs what its folders contain. Subtree queries use `IN` lookups and a test (`subtree_queries_never_scan`) checks the bundled SQLite's query plans, since without table statistics SQLite can pick a full scan of a multi-million-row table.
* The reconciler sorts every children list itself, so its plans don't depend on the order a backend returns rows in.
* **Write transactions are `IMMEDIATE`**, with a 60 s busy wait (`oneup_store::BUSY_WAIT`): in WAL mode a deferred write transaction fails at once when another connection (the hydration service, the window, a command) committed meanwhile.

## Activity log (`crates/oneup-store/src/activity.rs`)
The rounds `oneup sync` and `oneupd` share (`sync::Engine::rounds`) append one entry per operation that did something, was skipped or failed: time, outcome, action, path relative to the synced folders, and detail (the line the run prints). Bookkeeping, first-sync pairing and hashing aren't logged. Sync's own events are logged too: safety stops and overflow batches (once each, not every round they stand), trimming and rotation (what was removed for good), rescans, rule changes, problems, and halts. A skip or failure identical to the item's last entry isn't added again, so a file held open for hours doesn't flood the log. The table keeps the latest 50,000 entries (pruned by sequence number on every insert; about 100 B each). Paths compare case-insensitively (`COLLATE NOCASE`), and a path query covers a folder's contents through an index range. `oneup activity [PATH]` and the settings window read it straight from the database, with or without the agent. It holds names, never contents.

## Dirty folders (`crates/oneup-store/src/dirty.rs`)
Which Synced folders need planning again is recorded **by SQLite triggers** on `local_item`, `remote_item`, `synced_item` and `local_hash`, not by the code that writes those tables. The scanner, observer, mirror and executor all write them. A forgotten "report what you touched" call in any of them would leave a change unplanned, and triggers rule that out by construction, inside the same transaction.
* **Marked:** for every row that appears, disappears or changes, its parent before and after, and the row itself if it is a folder (its contents may now need planning). Removing a Synced row also marks the folder above its parent, since whether an emptied folder can now be deleted is decided when *its* parent is planned. Updates that change no column mark nothing, so echoes of our own writes and repeated delta entries keep a quiet folder quiet. When in doubt a trigger marks: over-marking costs a plan, under-marking would delay a change.
* **Only while syncing:** the local and remote triggers fire only once a Synced tree exists, so a first scan of millions of items pays nothing.
* **Scope:** `dirty_scope()` maps marks (local ID, cloud ID or sid) to Synced folders, with one indexed join per side. A mark that maps to nothing (a new local folder) is dropped. Its parent was marked too, planning the parent creates the folder on the other side, and linking it marks the new Synced row, whose contents the next round plans. Each marked folder also brings in the Synced parents of its children that are decided elsewhere: an item moved into a folder not synced yet waits under its *old* folder, with nothing to plan, and what happens next (the new folder created on the other side and linked, or the waiting item renamed or edited) marks only the new folder, whose planning passes over it. Without this, a move into a new folder waited for the next full pass. It costs one indexed lookup per child of a marked folder, which planning that folder reads anyway (`the_scope_never_scans_a_tree`).
* **Clearing:** marks carry an `AUTOINCREMENT` number, and re-marking deletes and re-inserts, so the number is new. A round reads the high-water number *before* planning and clears up to it once it has run (not after a halt, nor when the gate put work off). Marks made during the round, including the executor's own, survive. After a skip (say, a file held open elsewhere, which changes nothing that would mark it again) only the folders of the skipped and failed operations are marked again (`Ops::dirty_clear_except`, `sync::Touched`), so one busy file never makes every round plan the whole tree. Skips that only a change to the item can end don't hold the marks (`sync::settle`): a **refused** item (a hard link, a name Windows can't use), a **taken name** (held by something not synced, such as a symbolic link) and a OneDrive folder that **isn't empty**. Changing the item marks its folder again. `dirty_last()` reads the high-water number, which only grows; the agent uses it to tell new changes from marks waiting for a retry.
* **Checked:** store unit tests, and every end-to-end scenario in `oneup-exec/tests/sync.rs` plans *only* dirty folders and asserts at the end that a full plan finds nothing left.

`oneup sync` plans every folder in its first round, then only dirty ones. `oneupd` does the same only until a round planning every folder has finished with its version (`sync::start_scope`, `meta` `plan.full_pass_version`): a new version may plan differently. Otherwise it starts from the marks, which include what changed while nothing ran (marked as the journal and OneDrive's changes are read at start). Changed rules still plan every folder. A full pass over a 360k-item synced tree takes about 20 s in a release build (`oneup-plan`'s ignored test `plan_speed`); rule matching folds a name's case once per check, not once per pattern (`NameGlob::matches_folded`). The agent logs how long each full plan and the cloud-cleanup walk take (`planned`, `looked for excluded items still in OneDrive`).

## The background agent (`bins/oneup/src/bin/oneupd.rs`)
`oneupd` runs the same rounds as `oneup sync`. The shared code lives in a library target of the `oneup` package (`oneup_app`). It's a separate executable because Windows ignores changes the Cloud Files provider's own executable makes (data-safety invariant 12), so user tools must not be the agent.
* **Waking:** a thread blocks in `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL` with `BytesToWaitFor = 1` (zero CPU) and pings the agent at most every 500 ms. The agent waits 1 s for a burst to finish, runs the observer and checks `dirty_last()`. Only a new mark starts a round, so activity elsewhere on the volume never costs a Graph request.
* **Files that keep changing** (`oneup_app::busy`): the journal watcher reads every record (skipping ahead only when far behind) and hands each file written, other than by OneUpDrive itself, to an in-memory `Busy` (at most 4,096 files; those written longest ago and not busy are forgotten first). Records less than a second apart are one change, since one save leaves several. A file changed `busy_changes` times within `busy_window_s` is busy: a round leaves its `Upload` and `Hash` operations out after the gate approved them, keeps its folder's marks like a skipped operation's, and notes it in the activity log (`waiting`, once per stretch). The round still counts as settled; the agent's next wait ends when the earliest held file has gone `busy_quiet_s` without a change, or `busy_max_s` after it became busy, whichever comes first, so a file that never stops is still sent about every `busy_max_s`. It only delays uploads: nothing is deleted or overwritten, and the executor still checks the file's state before sending it. The safety gate sees the held operations in the round that approved them and again when they run. `oneup sync` doesn't hold anything.
* **Push** (`oneup-graph/src/push.rs`): a task asks for `subscriptions/socketIo` and speaks the needed subset of Engine.IO v4 / Socket.IO v5 over `tokio-tungstenite`. TLS uses rustls with Windows' certificate store (`rustls-native-certs`). It joins the namespace, answers the server's pings (every 30 s), and treats a server that stays silent past `pingInterval + pingTimeout` as dead. The `notificationUrl` doesn't match Graph's documented shape on OneDrive Personal, so it's parsed generically (path → namespace, query → passthrough). A notification only pings the agent. After 2 s the agent runs a round, whose delta read finds the change. A dropped channel also pings, because a notification may have been missed. Reconnects back off from 5 s to 10 min. The `notificationUrl` holds a token, so it's never logged; `Endpoint`'s `Debug` and every error message leave it out. While push is live, the timed delta check runs every 10 minutes as a safety net; otherwise it runs every `--poll-seconds` (default 60). `--no-push` turns push off.
* **Control** ([control-api.md](control-api.md)): a named pipe only the user can open. Calls change in-memory state (`oneup_app::control`) and wake the loop. While both directions are paused, no rounds run.
* **Overflow:** a held version-store batch doesn't stop the agent. It's shown once per fingerprint (and again when its outcome changes), everything else keeps syncing, and it takes `oneup keep/discard CODE`, or `--keep/--discard` at start.
* **Outcomes:** settled (refused items, taken names and non-empty folders count as settled, above) → trim the version store (not while changes to this PC are paused), run the placement pass, wait. Other skips/failures → retry after 30 s, doubling to 15 min. A skip because the item changed meanwhile gets a new round at once, but after 3 rounds in a row that did nothing else it's retried like the others, so one that a new round doesn't clear can't keep asking OneDrive for changes. Still busy after 20 rounds → again in 5 s. A **safety stop** changes nothing and waits for `oneup approve CODE`. An executor **halt** (`sync::Halted`: identity check failed) or an observer **NeedsRescan** end the agent, except journal loss (below), saving the reason for the tray ([control-api.md § Problems](control-api.md#problems)). A busy database is retried after 10 s without showing an error. Every other error (network, service) restarts the round from the database after 60 s, doubling to 30 min; the pause starts over at 60 s when the failed attempt had finished a sequence of rounds or ran longer than 30 min.
* **Safety window:** the gate's breakers count a round's batch *plus* the mass-sensitive operations the agent carried out in the last 15 minutes (`oneup_gate::Recent`, `Context::recent` of `review_in`). Otherwise a mass deletion trickling in over many wake-ups could pass in batches under the limits. The window lives in memory for as long as the agent runs, across its retries after errors; an operation counts as soon as its round ran it, even if that call of `rounds` then fails. A restart of the process forgets it; that restart's first round still plans everything that changed while the agent was away at once, from the marks, so a mass change is counted in one batch.
* **Database:** at normal priority (`[agent] background = false`), the agent's own connection maps up to four times its page cache of the file into memory (`Store::map_memory`, so `minimal` 16 MiB, `balanced` 64 MiB, `performance` 256 MiB): a page read is then a memory access instead of a system call, and a walk of a large tree measured no read calls and a fifth less time. At background priority (the default) it doesn't map: Windows keeps a background process's working set small, so mapped pages were trimmed and faulted back in one at a time (a full pass of a 340k-item tree measured 372 s and 220 million page faults, against 47 s reading normally). Other connections (the tray, the settings window, the CLI, the agent's hydration service and program tracker) don't map: Windows can't shrink a file another process has mapped. A disk error in a mapped page ends the agent instead of failing a query. At start, before its other connections open, the agent compacts a database that is mostly free pages (`Space::worth_compacting`: at least 64 MiB and a quarter of the file free), which deleted rows leave behind, if the disk has room for twice the database's files (SQLite's documented need; `[agent] compact_database`, default on; `oneup settings --compact-database`). The activity log says how large the file was before and after. If another connection was reading, the rewrite stays in the WAL and the file shrinks at a later checkpoint; if another program had it mapped, the file keeps its size and SQLite reuses the space. A failure is retried at the next start.
* **Threads:** `oneupd` runs tokio with 2 workers (default: one per core): about 10 idle threads instead of 44 on a 32-core PC, and less private memory, at no cost to a round.
* **One process per data folder:** `sync.lock` in the data folder, opened with no sharing. `oneup sync/versions/restore` take it too. Windows releases it when the process ends, however it ends.
* **Windows' close, sign-out, shutdown and Ctrl+Break** are logged and end the agent cleanly, so a stop can always be told apart from a crash.
* **Starting and stopping** (`bins/oneup/src/launch.rs`): `oneup start` launches `oneupd.exe` from its own folder with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` (so the terminal's Ctrl+C and closing don't reach it), outside the caller's job where allowed, stdin null and stdout/stderr to `oneupd.log` in the data folder (the previous run's kept as `oneupd.log.1`), and returns once the control pipe answers, or shows the log if the agent ended. Before spawning, `oneup` clears the inherit flag on its own standard handles (`oneup_sys::inherit`): Windows gives a child *every* inheritable handle, so the agent would otherwise hold the terminal's output pipe and a caller reading that pipe would wait for the agent to end. `oneup stop` is the `stop` control call: the loop finishes its round and exits, like Ctrl+C.
* **Start at sign-in** is opt-in (`oneup autostart on|off`, or a setup choice): one `REG_SZ` value per data folder, named `OneUpDrive agent (<data folder name>)`, under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. Per user, no admin rights, and visible and switchable in Task Manager's Startup apps. Chosen over a scheduled task because it needs no COM/XML and Windows already lists it for the user. The value runs `oneupd-start.exe`, a Windows-subsystem launcher (no console flashes) that does nothing if the agent answers already, and otherwise calls the same `start_agent`; a launch failure goes to `oneupd.log`. Two launchers racing are harmless: the second agent can't take `sync.lock` and ends.
* **Measured** (test account, debug build): a local edit is uploaded within seconds; a cloud change arrives about 30 s after it was made with push (OneDrive's notification takes most of that), or at the next timed check without. Idle cost is about 0.1 s of CPU per minute (the delta checks plus journal wake-ups from other programs writing to the volume), with a few MiB of private memory.

### Journal loss
When `catch_up` finds the journal wrapped or replaced (expected after the PC or the agent was off for a while: a volume's journal can hold as little as tens of MiB of history), `sync::observe` (used by `oneupd` and `oneup sync`) rescans the folder at once instead of stopping. Only if `Scan::open` reports `Replaced(Finished)`, i.e. the same folder (volume serial + folder ID) with the same rules; anything else halts. The Synced tree and recorded evidence are untouched; the Local tree is rebuilt, so a synced item the rescan doesn't find is **Missing** and held, never deleted. The rescan takes the journal position first and catches up afterwards, and it adds a `rescan` note to the activity log.

## Simulation (`crates/oneup-sync/tests/sim.rs`)
An in-memory model of a local disk (file IDs, atomic saves, recycle bin, version store) and of OneDrive (item IDs, eTags, version history, recycle bin). A seeded scheduler interleaves random user edits on both sides with sync rounds, including **between** an operation being planned and executed, so preconditions fail realistically. The executor enforces preconditions as the real one must. Checked:
1. **Convergence:** once users stop, a bounded number of rounds makes both sides identical (paths, kinds, contents) with nothing held, and the Synced tree matches both.
2. **No lost edits:** every content version that was new or changed when users stopped is present on **both** sides at the end.
3. **Invariant 1:** whenever local content is replaced or recycled, the cloud already holds that content (current version or history).
4. **The store plans like the model:** every round is also planned from an in-memory SQLite store holding a copy of the world (rows, Synced tree, hashes, evidence written the way production writes them). The two plans must be identical, and the store's invariants must hold.

Seeds: `SIM_SEEDS=N` (default 200), `SIM_SEED=n` to replay one, `SIM_DEBUG=1` to print every round's operations and the final state, `SIM_STORE=0` to skip check 4 on long runs (building a database every round makes runs about 80× slower). Each seed is 25 rounds of random edits on both sides, using a small set of names with case variants so that collisions are frequent, followed by settling. Hundreds of thousands of seeds pass (300,000 in about 90 s in a release build without check 4; 20,000 with it). The same simulation covers one-way backups (`backups_send_this_pc_and_never_change_it`).

Scenario tests pin the headline behaviours: first-sync adoption (identical files paired, different ones both kept); an atomic save updates the same cloud item (version history continues); a swap of two names renames rather than re-uploads; an edit beats a deletion; "missing without evidence" is held, never deleted; a missing sync folder halts everything; a folder deleted in the cloud survives for a new local file; folders moved into each other don't loop.

## End-to-end tests (`crates/oneup-exec/tests/sync.rs`)
A real temp folder goes through the real scanner, observer, planner, gate, effects and executor, with a fake cloud that enforces eTags and name conflicts. Rounds run until both sides are identical and a round changes nothing, and the store's invariants must hold. Besides the first sync, edits, deletions, renames, conflicts, the version store, busy files and parking, the `everyday_` tests take one scenario per thing people do in File Explorer and on the web.

## Limits
* The simulation doesn't model a stale Remote tree (delta lag) or crashes in the middle of an effect: for example, between a replacing download moving the old file into the version store and renaming the new one into place. The old file is safe in the version store then, but whether the next rounds restore the new one cleanly is untested.
* OneDrive's 400-character path limit isn't parked (checking it needs the whole path). An upload that exceeds it fails and is reported.
* Folders another sync app manages are refused (Files On-Demand is OneUpDrive's own: [files-on-demand.md](files-on-demand.md)).
