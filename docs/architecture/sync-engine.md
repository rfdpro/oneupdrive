# The sync engine

How OneUpDrive decides what to do once it has a **Synced tree** (the record of what both sides last agreed on), and how it carries it out. The reconciler (`crates/oneup-sync`) only *proposes* operations: it has no I/O and can't touch user content. Everything destructive goes through the safety gate (`crates/oneup-gate`) and the effects layer (`crates/oneup-effects`), run by the executor (`crates/oneup-exec`). The first-run case without a Synced tree is [planner.md](planner.md).

## Three trees
| Tree | Keyed by | Kept current by |
|---|---|---|
| **Local** (`local_item`) | 128-bit NTFS file ID | the scan, then the change-journal observer ([local-tree.md](local-tree.md)) |
| **Remote** (`remote_item`) | drive item ID | the mirror and `/delta` ([remote-mirror.md](remote-mirror.md)) |
| **Synced** (`synced_item`) | our own integer `sid` | the executor, after each operation succeeds |

A Synced row links one local file ID and one remote item ID. It also holds the agreed location (parent `sid` + name) and content (size, QuickXorHash), plus the stamps each side had at that moment (local last-write time, remote eTag). Comparing each side to its Synced row says **which side changed**. Timestamps are never compared across sides.

## Deletion needs evidence
Each side reports one of three states for an item it used to have:

* **Present**: the item still exists, possibly moved or changed.
* **Deleted**: there is *explicit evidence*. That's a USN delete record, a delta `deleted` facet, the item's path in the user's Recycle Bin, the user's answer for the held item ([below](#answering-held-items)), an ancestor deleted with such evidence, or our own executor having removed or detached it.
* **Missing**: the item is gone with no evidence, e.g. after a journal loss and rescan, or a mirror rebuild. **Missing never causes a deletion.** The item is held and reported (data-safety invariant 3).

## Merge rules (one Synced item)
Changes are found per side by comparing against the Synced row. *Moved* means a different parent or a different name, including case-only renames. *Changed* means different content. Locally that's a new file ID at the same path, or a different size or last-write time, unless a fresh hash proves the content is unchanged ("touched"). In the cloud it's a different QuickXorHash or size.

| Local \ Cloud | unchanged | changed | moved | deleted |
|---|---|---|---|---|
| **unchanged** | — | download (replace) | move locally | recycle locally (folders: once empty) |
| **changed** | upload (replace) | equal hash → record; unknown → hash first; else **conflict: keep both** | move first, content next round | **re-create in the cloud** |
| **moved** | move in the cloud | move first, content next round | same place → record; else the cloud's location wins (a move, not a loss) | **re-create in the cloud** |
| **deleted** | delete in the cloud (to its recycle bin; folders: once empty) | **re-create locally** | **re-create locally** | forget the record (folders: once the records below are gone) |

Missing on either side, with the other side present, means **hold**: report it, don't act. Missing on one side with the other deleted or missing too means **keep the record** and plan nothing: there is nothing to act on, and an item that reappears is matched with its history instead of looking new (a deletion on the other side then follows the table, so a change or a move made meanwhile still wins). Only deleted on both sides forgets a record.

Principles behind the table:
* **A change beats a deletion.** Deleting is only propagated for content the deleting side had last seen.
* **Conflicts keep both copies.** The local copy is renamed to `name (conflict N).ext` and detached from the Synced item. The next round uploads the renamed copy and downloads the cloud version to the original name. Nothing is overwritten.
* **One operation per item per round.** A move and a content change are separate rounds, so every operation's preconditions are about the state the planner saw.
* **Replaced local content is in the cloud's version history.** Downloads only replace a local file whose stamp still matches what was last synced (both sides changed is a conflict, which keeps both), so its content is a version OneDrive already has. By default no local copy is kept, but only after the effects layer has proved it by hashing the file under its exclusive handle; otherwise, or with `keep_replaced` on, the old copy goes to the local version store ([below](#version-store-overflow-and-replaced-files)).

## New items
* **One side only:** upload or download (folders: create). Children of a new folder are planned once the folder is synced, in the same round ([below](#executor-cratesoneup-exec)).
* **Both sides, same name:** two folders are paired. Two files are paired only if they have the same size and the same hash; otherwise the hash is computed first. Anything else (different content, file vs folder) is a conflict, and the local item is renamed. This is also how the **first sync** adopts an existing folder: nothing is deleted or overwritten.
* **Atomic saves** (write a temp file, rename it over the original; the file ID changes): a Synced file whose local ID was deleted, plus a new local file with the same name in the same folder, is treated as an *edit* of the Synced file. The cloud item keeps its ID and version history.

## Folders
* A folder is deleted on the other side only **once it is empty there and no Synced rows remain under it**: children are deleted first, each under its own preconditions. Graph would delete a non-empty folder's unknown contents along with it. Dropping a folder's row early would orphan its children's rows, which would then never be planned again.
* If a folder was deleted on one side but something must now go into it there (a new or changed file, an item moved into it), the folder is **re-created** ("resurrected") first. If its parent was deleted too, the walk goes up to the highest deleted ancestor, and later rounds work back down. Unchanged children still follow the deletion.
* Moves that would put a folder inside itself (moved into each other on the two sides) are undone: one side's move is reverted rather than looping.
* **A folder is never recorded below itself in the Synced tree.** The two trees can put a folder inside one that the Synced tree still has below it, when that one's own move isn't recorded yet (refused this round, or held): here `A` moved to the top and `C` into `A`, while the Synced tree still has `A` in `C`. Recording `C` in `A` then would make a loop that no plan from the top reaches again (full passes walk the Synced tree from its root), so the move or record waits until `A`'s is recorded (`merge::base_within`). The same holds for a folder made again on one side at the other side's place (deleted here but moved there, or the other way round, or re-created because something must go into it).
* **A OneDrive folder that isn't empty when deleted.** The Remote tree doesn't list what the rules leave out by name (`__pycache__`, `node_modules`…), so a folder holding only those looks empty to the planner and isn't to Graph. Graph's refusal is `CloudError::NotEmpty` → `Skip::NotEmpty`, which waits for a change (something new in the folder marks it), and the folder is listed in `oneup unsynced` (`Why::NotEmpty`) with `oneup cloud prune` as the way to clear such leftovers.

## Answering held items
What can't sync until the user acts (`oneup_app::unsynced`) can be answered from the settings window or `oneup unsynced resolve`. The answer is queued in `meta` (`unsynced.resolve`, at most 1,000) and the agent nudged; the next round takes the queue before it plans (`oneup_app::resolve::apply_queued`), each answer checked against the state then, in its own transaction, and logged to the activity log (*Note* "resolve", or *Failed* with why). None of it touches user content: `oneup_exec::resolve` only changes what the planner reads, so what follows is planned, reviewed by the gate (circuit breakers included) and run with the usual preconditions.

| Held as | Choice | What it changes | Then |
|---|---|---|---|
| Gone from this PC | Delete in OneDrive | local deletion noted for it and everything under it still gone (`local_gone`), folders marked | `DeleteRemote` with `If-Match`; a cloud edit since wins and comes back here |
| | Restore | its Synced record and those under it dropped | the cloud item reads as new: downloaded |
| | Keep in OneDrive (backup pairs) | local deletion noted | nothing: a backup keeps what this PC deletes |
| Gone from OneDrive | Delete here | cloud deletion noted (`remote_gone`) | `RecycleLocal` into the version store; a local edit since is uploaded instead |
| | Upload | Synced records dropped | the local item reads as new: uploaded |
| Refused name, names differing by case | Rename | an `Op::RenameLocal` added to the round (after planning, before the gate) | renamed by ID, stamp checked, never over a name; then uploaded |
| Too large, special item, name taken | Exclude | a rule (`filetree::set_sync`, as the Files page) | left out |

A dropped record deletes nothing: the side that has the item sends it as new, and a name taken meanwhile is paired by content or kept as both. Each choice is refused if it no longer fits: the item came back, is gone from the other side too, or the folder it would go into is gone too (restore or upload that folder first). An answer is bound to exactly what it concerned when chosen, not to a path: a fingerprint (SHA-256) of every record it concerns, by sid and both linked IDs, or for a rename the file ID, size, last-write time, folder and new name (`Change::fingerprint`). The agent works the answer out again and refuses it if the fingerprint differs: another item at that path since, a file changed since, or a folder that would now take more (or other) items than were shown. A folder's records are walked one folder at a time, and one answer concerns at most 100,000 records (`resolve::MAX_ITEMS`), which bounds the walk, the IDs a deletion keeps until it's written and the write transaction that holds the store meanwhile. Whether a local item still opens in the sync folder is asked with `LocalFs::presence`: only "no such ID" or "outside the sync folder" counts as gone, and anything that can't be told (access denied) counts as here, so nothing is noted gone on a doubt. The queue holds at most 1,000 answers and refuses more instead of dropping any. Evidence is noted only for the chosen item and those under it that are gone from the chosen side and still on the other: gone from this PC means gone from the Local tree and not opening by its ID in the sync folder (`LocalFs::is_present`); gone from OneDrive, not in the mirror. Evidence noted stays as the planner's own does: it goes when the item comes back on that side (the tables' triggers), and an edit on the other side wins over it. A rename stays queued until a round runs it, since a round can end before running anything and a rename isn't planned again from marks; one that would meet what the round plans (the same item, or a name the plan needs in that folder) waits for a later round (`sync::add_extra`). Answered items leave the record with what was held below them (`unsynced::answered`). A folder held as not empty has no choice: its contents are listed from the trees (`resolve::inside`), and its leftovers are the user's to look at.

## Rewinding a folder (`crates/oneup-sync/src/rewind.rs`)
Puts a folder back the way it was at a moment the user picks: the Recovery page, `oneup rewind`, and the content guard's stop. Everything it does is planned operations, through the gate and the effects layer.

**The history** (`synced_history`, `oneup_store::history`). For each change to a Synced row, what the row agreed on until then and when: its folder, name, kind, size, hash and OneDrive ID, or that it was created then. Not its local stamps or eTag, which change without anything a user would rewind. Written by triggers on `synced_item`, like the dirty marks, so every writer is covered; an update that changes none of those columns writes nothing. It's kept from the end of a folder's first sync (`Ops::history_start`, when a sequence of rounds first settles; after the upgrade that adds it too, since the upgrade can come in the middle of a first sync): a first sync's records are of items that were there before it, and a large folder's would fill the history at once. Bounded (`Ops::history_prune_some`, every round, a bounded number of rows at a time, never what a rewind under way reads): 30 days by default (as long as OneDrive Personal keeps deleted items) and at most 1,000,000 rows; `oneup rewind --set-history-days/--set-history-changes`, in `meta`; 0 turns it off and drops it. Coverage starts at `history.since`: the start, or the newest row pruned; a rewind can't go further back. At 3 million synced items, a change costs about 165 bytes of row and indexes and about 100 µs more on its write (a quarter more than the record's own, on a synthetic store with a 64 MiB cache); an item's first change after a moment, or a folder's past contents, is one index probe (`crates/oneup-store/tests/history_cost.rs`, ignored by default).

**The plan** (`rewind::plan`, pure, over `Trees` and `History`). An item's state at moment T is what its first change after T says it was, or what its record says now if nothing changed since; a folder's contents at T are its children now and every item recorded in it after T, each checked against its state at T. Only an item the history has changing after T, or one that differs from its record now (a change not synced yet), can differ from how it was: so the plan reads those records only. The second come from item marks (`synced_unsettled`, `History::unsettled`): triggers on the Local, Remote and Synced trees mark the record linked to an item that appears, changes or goes, one probe of the link's unique index each; the rewind reads the marked records that still differ, and each round drops (bounded) the marks of records that agree again (`Ops::history_settle_marks`); kept, like the history, once a first sync has finished. It reads them (`History::changed_after`, through the index on the time, at most `read_limit`: four times the change limit, beyond which the rewind is refused and says to pick a later moment), and places each by walking up from it, at T and now, remembering the folders above it (`Place`). An item counts as in the folder now if it, or a folder above it, is in it now or was in it at T (it goes back with what it holds). The cost follows the changes since T, not the size of the folder: one change in a folder of 50,000 files reads fewer than 100 records (`crates/oneup-store/tests/rewind_cost.rs`). Finding the folder at T reads only the children with its name (through an index on folder and name, `Trees::base_named`) and those the history has changing. One unsynced edit among 50,000 files in the same folder also reads fewer than 100 records, and none of its statements reads a whole table that grows with the tree (the store's statement log). For each item:
* **deleted since**: `Step::Restore`, from OneDrive's recycle bin by its recorded ID (`POST /items/{id}/restore`, with the documented `parentReference` and `name`: into its folder then, under its name then). What comes back is checked, not assumed: the answer's ID, folder and name are compared with what was asked; back elsewhere (another name or folder), the next round moves it from where it is, under the gate; back as another item, the step fails and says so, and the item comes to this PC as a new one. A taken name is taken to be refused (409), not replaced; that, and that a restored item keeps its ID, are for a live check, and its content of then from its version history if it was edited before it went, only over what went into the recycle bin (an item someone else restored and changed meanwhile is left as they made it);
* **moved or edited since**: `Step::Reset`, its place first (a move with `If-Match`), then its content of then, downloaded from its version history into the staging folder, checked by hash, and uploaded as a new version with `If-Match` (Graph's `restoreVersion` ignores `If-Match` on OneDrive Personal); the version it replaces stays in the history;
* **created since**: `Step::Remove`, into OneDrive's recycle bin (an emptied folder only from where the approval saw it: moved since, it stays), but only what's surely new: a record made since isn't proof the item was (a file a rule left out was there before it synced), so a file last written before the moment is left alone (`Skip::ExistedBefore`), and so is a folder holding anything left alone (`Skip::Keeps`); a file whose OneDrive item was replaced since (deleted there and sent again from this PC) gets both: the item since removed, the item then restored, so its version history comes back with it;
* **changed on this PC and not synced** (an edit the content guard holds): `Step::SetAside` moves this PC's copy into the version store and forgets its record, so OneDrive's copy (as the rewind leaves it) comes back as a new file; one deleted here only has its record forgotten (`Step::Forget`).

Items moved in since go back where they were at T; items moved out since come back with what's in them now. An item whose OneDrive side changed and isn't synced yet, one held as missing, a folder moved on this PC, or one whose folder then is gone is skipped and listed (`rewind::Skip`). Steps act on OneDrive and leave the Synced tree alone, so the next rounds see OneDrive changed and bring this PC along like any change from OneDrive.

**Order and several rounds.** Names are freed before they're taken and folders made before what goes into them: copies set aside, files removed, restores from the top down, moves (ordered so a move goes after the one that frees its name), then folders removed from the bottom up. A cycle of moves (names swapped since) sends one through a temporary name (`name.oneup-rewind-SID`, which the planner's self-healing leaves alone); so does a restore or move into a name held by an item that leaves later (a folder to remove once emptied, perhaps of that very item). A folder is removed only once every record in it goes too, this round or before (`Rewind::later`): an item moved out of it in OneDrive and not yet on this PC would otherwise have this PC's copy of the folder made again in OneDrive to hold it. So a rewind takes several rounds, each planning again from what's there; what's done no longer shows.

**The approval** (`rewind::Job`). The first round's plan is the preview: its steps and the folders it removes later are one stop, shown and keyed like the others (`Context::pending`), with the paths the plan names (where each item was at T). While it waits, only its own steps are held: unlike any other stop, a rewind's doesn't halt the round, so the rest syncs, the folder included (the planner's operations on the rewind's items too). Every round plans it again, and its code is the fingerprint of the list as planned (`rewind_fingerprint`), so any change in the folder gives a new list and a new code. An approval is taken only for the list planned at the answer: `oneup rewind --approve CODE` (the window's **Approve**) plans it again and refuses, showing the new list, if the code differs; the agent takes a code only while it shows that stop (`Control`), and the round takes it for the rewind only if the list it plans then has that code. A rewind stop's code approves none of its items by itself (`Stops::approve`): a changed list runs nothing. The user approves its code; the approval is kept item by item, by what each step acts on (a OneDrive item, a copy here, a record) and the state the preview showed it in (`rewind::Mark`: its folder, name, size and hash, or that it's absent). It also keeps what each step does (`rewind::Effect`: where it puts the item and with what content, the folders it removes it from under, the place here it sets a copy aside from), and a later round runs a step only if it does that, or what's left of it after the rewind's own steps (content already put back, the move on from a temporary name, folders above a removal that only the rewind moved, each where its own last step left it): a destination folder replaced since, or a folder above moved by someone else, isn't covered. Each step checks its place again right before it acts: a removal from OneDrive re-reads the item and every folder above it up to the drive's root (`Step::Remove::up`; a move above an item keeps its eTag), and a copy set aside here is moved only from the path the approval named, compared on the handle that moves it (`Step::SetAside::at`; a rename keeps its ID, size and last-write time). A later round runs an item's steps only if each is from the state the preview showed, or the state the rewind's own last step left it in (`Job::ran`, read back from the store, `oneup_exec::rewind_mark`), and passes their keys as approved (`oneup_gate::rewind_keys`; a rewind step's key leaves out the eTag, which its own steps change). An item changed after the approval on either side is left alone whole (`Job::take`), and so is what the planner would do to it: once approved, a round drops the planner's own operations on a rewind's items. The rewind ends once nothing it approved is left to run, or after 3 rounds in a row in which its steps all failed or were skipped; the activity log says how many ran, were left alone or couldn't be done.

**This PC following it.** The follow-ups (a reverted file downloaded over the copy here, a moved one moved, a removed one recycled) would trip the circuit breakers on a large rewind. The user approved them with it, so while a rewind runs, and until the rounds after it settle, the gate doesn't count follow-ups of the items it changed (`Context::rewound`, `oneup_gate::follows_rewind`: a replacing download, a local move or a recycling of exactly those Synced items). They still run under their own preconditions and keep what they replace as any download or recycling does, and the safety window still counts them.

**The job** (`oneup_app::rewind`) is kept in `meta` (`rewind.job`), so a restart goes on with it: the folder, the moment, the approval and its marks. `oneup rewind FOLDER --to TIME` previews (read-only) and gives the code the stop will have; `--start` saves it and nudges the agent; `--cancel` drops it (what it did stays done). One at a time; never in a backup pair or a vault. The content guard's stop offers a rewind to just before its batch (`--before-stop CODE`): the folder all its items are in, to a second before the first suspicious upload the safety window counted, or before the stop was raised. Its scrambled files, not yet sent, are set aside; any that went out are reverted from their version history.

**Crash safety.** Setting a copy aside writes ahead (`exec.pending`, `Pending::Aside`): settled after a crash, the record is forgotten if the copy left the folder and kept if not. Every OneDrive step is conditional, and one that ran but wasn't recorded leaves OneDrive changed and unsynced: the rounds bring this PC along, and the rewind's next plan finds nothing left for it (`a_crash_at_any_point_of_a_rewind_loses_nothing`).

**Conflicts** (`oneup_exec::recover`, `oneup_app::conflicts`): a file and its `name (conflict N).ext` beside it, both synced, listed side by side with which is newer. The answer queues in `meta` (`conflicts.answer`); the next round adds `Step::Discard` for the copy not kept (into the version store as a deletion made here, its record kept with the deletion noted, so the next round deletes OneDrive's copy into its recycle bin) and, to keep the conflict copy, a `RenameLocal` to the file's name once freed. The answer approves the discarding step (its key, as a rewind's); each step runs under the stamps listed, so a copy changed since is left alone and the answer dropped.

**Restoring one item** is a planned step too (`oneup_exec::recover`, `oneup_app::restores`): the request is queued in `meta` (`recovery.restore`) as the exact step, bound to what the user saw, and the agent's next round adds it to its plan, approved by the request's key (`rewind_keys`) and run by the executor; without that key the gate stops it like a rewind's step. A kept copy (`Step::RestoreKept`) is bound to the kept item by its file ID and stamp (size and last-write time) and to the destination folder by its file ID (`LocalFs::kept_target`); the effects layer opens the item by ID, checks on that handle that it's still in its slot and unchanged, pins the folder by ID, and moves it in, never over anything (` (restored N)` if taken). The next round sends it. A OneDrive version (`Step::RevertTo`) is downloaded into the staging folder and sent as a new version under `If-Match` with the eTag the request saw, checked by hash: a file changed since is skipped. A deleted item (`Step::Restore`) comes back by its ID under a name free when asked (` (restored N)` if taken); a name taken meanwhile is refused by OneDrive and the step fails. One that comes back elsewhere (another folder or name) isn't done: its move to where it was asked (`recover::follow_up`, a `Step::Reset` bound to the item's eTag, place and content as it came back) takes its place in the queue and goes through the gate the same way. A step that's skipped or fails leaves the queue and the activity log says why; one that didn't run (a stop, a pause) waits. OneDrive Personal's recycle bin can't be listed through documented Graph (the `recycleBin` resource is SharePoint's, and a drive has no such relationship), so the deleted items listed are those the history recorded with their OneDrive IDs and OneDrive no longer lists (`Ops::history_removed`).

## Name collisions
After each item is decided, a resolve pass checks every operation that needs a free name, e.g. "create `b` in folder X", "move to `b`":
* If the name is being vacated this round, or another operation already claimed it:
  * a **new** item waits a round (nothing waits for a new item, so this can't deadlock);
  * a **move** goes to a temporary **staging name** (`name.oneup-staging-N`) and is renamed next round. Waiting could deadlock on swaps and rotations; staging breaks them without special cases.
* If it's taken by an item that stays, the **local** item involved is renamed to a conflict name. Local renames are cheap and lose nothing.
* At most one operation per item per round.
* **Self-healing:** if both sides end up agreeing on a staging name, the local item is renamed back to the real name (or a conflict name if that's taken), and the next round propagates it. This happens if the item was deleted on the side that held the real name and then re-created from the other side, or if a crash interrupted the round. As a result, a user's own file named like `x.oneup-staging-1` would be renamed to `x`. An item still under a staging name never gets a second staging suffix, and its conflict name is made from its real name: `report (conflict 1).docx`, not `report.docx (conflict 1)` once the suffix is dropped, which Windows would no longer open as a document.

## Operations and preconditions
Every operation carries the state it was planned against:
* local: file ID, plus size and last-write time for files;
* remote: item ID and eTag.

The executor re-checks these immediately before acting (data-safety invariant 5) and sends `If-Match` for remote changes. A mismatch skips the operation, and the next round re-plans from fresh state. A `MoveLocal` follows the cloud: it takes the item where the listing has it in OneDrive. The listing can be behind OneDrive (delta lag) and show an item where it was before a move of ours, and following that would undo a move made here since. So the executor first asks OneDrive whether the item is still there (`Cloud::is_at`: one GET per such move; a vault reads the item's encrypted entry, [vaults.md](vaults.md#vault-pairs)), and skips the move as *changed* if not. Operations: `Pair`, `Record`, `Forget` and `Hash` (bookkeeping only); `Upload`, `Download`, `MkdirRemote`, `MkdirLocal`; `MoveRemote`, `MoveLocal`; `RenameLocal`, `RenameRemote` (one-way pairs only), `ConflictCopy`; `DeleteRemote`, `RecycleLocal`; `Dehydrate` (freeing space, [files-on-demand.md](files-on-demand.md#pinning-and-freeing-space)); `PruneRemote` (cloud cleanup, [rules.md](rules.md#cloud-cleanup)); `RemoveCopy` (a duplicate the user chose, only where it was shown, by its full path: OneDrive's copy to its recycle bin, then the copy here to the version store, while a named copy that stays still stands, [usage.md](usage.md#duplicates)); `Rewind` (a rewind's steps and the copy an answered conflict doesn't keep, [below](#rewinding-a-folder-cratesoneup-syncsrcrewindrs)); and `Hold`.

**One-way pairs:** `plan_flow(…, Flow::Backup)` plans a backup (this PC → OneDrive; deletions here never reach the cloud, nothing changes this PC). The rules, `RenameRemote` and the final check that turns anything changing this PC into a `HoldReason::OneWay` hold are in [pairs.md § Backups](pairs.md#backups-one-way-flow-oneup_syncflowbackup).

**A move that renews the item's ID**: OneDrive moves keep IDs, but a vault entry whose stored name changes shape is rebuilt, and the decrypted item gets a new ID ([vaults.md](vaults.md#creating-vaults-the-recovery-key-passwords-windows-hello-long-names)). `MoveRemote`'s bookkeeping then points the Synced row at the new ID and renews an online-only file's identity without downloading it (`LocalFs::renew_identity`). For a cloud whose moves can do this (`Cloud::moves_keep_ids` is `false`: a vault), the move is written ahead, durably (`exec.moving.<sid>`: the Synced item, its old ID, the destination and name), and the bookkeeping clears it. A crash between the move and its bookkeeping would otherwise leave the Synced row on the old ID, whose removal the next listing reports as a deletion: the plan would then duplicate the item, or recycle a folder here while undoing its move. One left over is settled once the listing is current and before the plan (`Executor::settle_moves`, in the agent's rounds): the old item still listed means the move didn't happen (the record goes, the plan makes it again); otherwise the Synced row goes to the item where the move took it only if that is proved to be the one moved, looked up by name through the parent index (`Ops::remote_named`, every name that folds alike): for a file, exactly one such file linked to nothing with the Synced row's size and hash, and no such file whose hash isn't listed; for a folder, exactly one such folder and none of that name linked (a vault folder can hold names that differ only in case, so a name alone proves nothing). A file relinked gets the new item's placeholder identity, as the move's bookkeeping gives it: an online-only file named by the old ID could never be opened again. Short of proof, the old ID's deletion evidence is withdrawn, so the item is held: with no candidate the record goes and the hold stays for the user; with several, or one whose hash isn't listed, the record waits for the next listing (`a_vault_move_cut_short_by_a_crash_is_recorded_where_it_went`, `an_online_only_file_whose_vault_move_a_crash_cut_short_still_opens`).

## Safety gate and effects
**The gate** (`crates/oneup-gate`) is pure. It reviews one round's operations and issues an `Approved` token for each one it lets through. Only the gate can create these tokens, and the effects layer accepts nothing else. It withholds operations when:
* the user hit **panic** (everything stops);
* the side the operation would change is **paused**;
* the operation is **malformed** (e.g. an upload or a replacing download without a local stamp to re-check);
* the operation is a planner **hold**;
* a **circuit breaker** has tripped. The breaker counts the round's mass-sensitive operations per side: recycles and deletes, replacing transfers, and moves. It trips when they are more than `max_count` (default 200), or more than `min_count` (20) and also more than `max_percent` (10%) of the Synced tree (`max_count` and `max_percent` are user settings: `oneup safety`, the window's **Safety** page). A second kind, the **content guard**, trips on more than `max_suspicious` (20) edited files whose new content doesn't look like their type ([usage.md](usage.md#the-content-guard)). The user approves a tripped batch (its **list**) by its **fingerprint**, so the approval can't carry over to a different list (see [Safety stops](#safety-stops) below);
* the operation removes a **duplicate the user chose** (every `RemoveCopy`): these always form a stop of their own (`BreakerKind::Removal`), whatever the limits, keyed, listed and approved item by item like the others (below), but never on a mass list nor released by a mass list's approval; they don't hold the rest of the round back, count in the safety window by weight once they ran, and what they take from this PC is always kept (`OldCopy::Keep`, outside the overflow batch) ([usage.md](usage.md#duplicates));
* the operation belongs to a **version-store overflow** batch awaiting the user's decision (below);
* the operation is a **rewind** step (`Op::Rewind`) that no approval covers: every one is on a stop of its own (`BreakerKind::Rewind`), whatever the limits, even one step with the breakers off ([below](#rewinding-a-folder-cratesoneup-syncsrcrewindrs)).

Each token also carries an `OldCopy` (`Keep` or `DropIfSynced`): what happens to the old content of a file the operation removes or replaces.

### Safety stops
* **The list and its code.** A tripped breaker's list holds the round's operations on that side that no approved list covers, and the folders they will empty (below). Each item has a key (`oneup_gate::ItemKey`: SHA-256 cut to 128 bits, since an approval runs whatever matches one): the kind of stop, the operation, the item's IDs, where it goes, the **path the list shows** for it, and its precondition, except an **upload's content stamp**. A deletion names only IDs, so without the path an approval for `/old/file` would still match the same item after a folder above it moved to `/critical`. The engine reads the paths as the list describes them (`sync::stop_paths`, passed as `Context::paths`; the gate stays pure), and only when something in the round could trip a stop or a list is approved (`oneup_gate::may_stop`, built on the same rule the gate uses for what always stops, `oneup_gate::always_stops`: a folder of unknown size, or the removal of a duplicate the user chose). An upload over a file keeps the old version in OneDrive's version history, and a file an app rewrites every few seconds would otherwise change the code between `oneup status` and `oneup approve`. Deletions and local replacements keep their stamp: approving them approves removing exactly that content. The code (`Fingerprint`) is a hash of the sorted keys, so a full pass and a round over marked folders, which plan in different orders, give the same code.
* **Approving runs the whole list.** An approval is kept item by item (`Context::approved`), not as one code to match: later rounds run whatever of the list they plan, and anything else is judged on its own, counted on top of the approved items, and needs a stop of its own (`Breaker::recent` then includes them). When a stop trips, the agent marks the Synced folders of everything on the list for planning (`Breaker::sids`, `Ops::dirty_mark_synced`), so every round while it stands, and the round after the answer, plans all of it. Without this, a stop raised by a full pass (the agent's first round) shrank to what the marks covered once the next round planned marked folders only: a new code, or a part small enough to run, and the rest waited for the next full pass. The engine remembers the last 8 stops it raised (`sync::Stops`), so an answer to one that a later round replaced still counts. **An approved item lasts until its change runs:** the gate reports each round's operations on approved lists with the keys they matched (`Review::listed`); a key goes once its operation ran, and when a sequence of rounds settles only the keys of operations that still wait stay (a file that keeps changing, a pause, a version-store decision, a retry). One that's no longer planned (the file was restored) goes then too. **A code answers one raising of a stop:** once the rounds take its list in, it isn't taken again in that call, and the agent drops it from its answers afterwards (`Engine::spent_answers`, `Control::forget_approvals`); an answer the rounds never took in is dropped once its stop no longer shows (`Control::record`). So the same items coming back later (a file restored, then rewritten suspiciously again, has the same key) need a new approval, and a new raising of the same stop can be approved again. `oneup sync --approve CODE` matches the code against the first round's list instead (`Review::answered`) and keeps its items the same way.
* **Each stop's list is exactly what its code approves.** With a mass stop and a content-guard stop standing together, an upload can be on one list and not the other (approved earlier under one kind). The gate reports which held operations are on each stop's list (`Review::lists`), and the saved list (`safety-stops\CODE.txt`) shows exactly those, with the folders still to come.
* **Counts never wrap, and a pruned folder is all it holds** (one never listed in full, of unknown size, always trips a stop and counts as over the limit: [rules.md § Cloud cleanup](rules.md#cloud-cleanup)). Every count the stops and the window keep goes through `Recent::add_op` and `oneup_gate::weight`, saturating: a pruned folder counts as everything in it in the window, in a round's reservation, and in deciding whether a round needs the paths its lists show.
* **One stop per tree.** A folder is deleted only once empty, so a deleted tree goes a level per round, and each level used to be judged on top of the window that the level before had filled: one stop per level. The planner names the folders a round's deletions will empty (`oneup_sync::pending_deletes`): every folder above a deletion that is deleted on the same side with evidence, still where it was agreed on the other side, and holding nothing but what the round and those folders remove. What a folder holds is read from the store **unfiltered**, not through the planner's view: an item the rules exclude, or one that never syncs by nature (`desktop.ini`, an Office lock file), keeps the folder from being named. A folder without a recorded deletion, one that keeps anything (a held item, something new on the other side), one the other side moved, and anything above such a folder are never named. The gate counts the named folders with the round's batch and lists them (`Breaker::later`, shown with the note "once empty"), so one answer covers every level. A cloud folder's eTag changes as its contents go, so a named cloud folder is keyed without it; such keys only ever come from named folders, and a file's deletion still matches with its eTag only. Just before deleting a folder, the executor still checks that OneDrive reports it empty and its eTag is the one planned; on this PC, the effects layer lists the folder on disk through its handle and refuses one that isn't empty (`Error::NotEmpty`), so nothing inside (an item never listed, such as one skipped by a name rule) is recycled with it.

### Version-store overflow and replaced files
Data-safety invariant 1 allows, in exactly two cases, relying on OneDrive's version history or recycle bin instead of a local copy.

**Replaced files.** A file replaced by a newer cloud version (`Download { replace }`) isn't kept by default (`Policy::keep_replaced = false`; `oneup versions --set-keep-replaced on` brings it back). The planner emits a replacement only for a file unchanged since the last sync, so its content is the Synced row's version, which OneDrive keeps in its version history. The gate marks the token `DropIfSynced`. The effects layer keeps its usual order (open exclusively, check stamp and location, move the old file into a version slot, place the new one, move the old one back if that fails) and adds one step. *Before* moving anything, it hashes the old file through the exclusive handle and compares the hash with the Synced row's QuickXorHash, which the executor passes in. Only if size and hash match is the old copy deleted, through the same handle (`FileDispositionInfoEx`, `DELETE | IGNORE_READONLY_ATTRIBUTE`), once the new file is in place. Without a recorded hash, or with different content (an edit that kept the size and time), it stays in the store, and the run says so (`Report::kept_instead`).

**Overflow.** The files a round would move into the store (recycled files; replaced files too with `keep_replaced`) form one batch. Folders take no room and aren't counted. If their stamped sizes exceed the store's **room**, the gate reports an `Overflow` with its own fingerprint, distinct from breaker codes. Room is worked out by the caller (`Trim::room`: the cap minus slots younger than `min_age_days`, or the whole cap with rotation), and only when the plan would add bytes, so the store is listed only then. Then:
* `OverflowPolicy::Hold` (default): the batch is withheld (`Withheld::Overflow`) and everything else runs. It isn't a stop. The round leaves its dirty marks in place so the batch is planned again, and the user's answer finds it.
* `OverflowPolicy::Keep` (`--set-overflow keep`): approved as usual, and the user is told.
* A `Decision` with the batch's fingerprint (`--keep CODE` / `--discard CODE` on `oneup sync` and `oneupd`, or the control API): `Keep` approves it as usual. `Discard` approves it with `DropIfSynced`, so each file is deleted by handle only if it hashes to its Synced row's version (which OneDrive's recycle bin holds), and otherwise kept.

No decision is taken while local changes can't run (panic, paused, or a tripped local breaker).

**Rotation** (`Trim::rotate`, `--set-rotate on`, off by default): after the review, the caller removes the oldest slots, whatever their age, until the bytes the approved operations will keep (`Review::store_bytes`) fit under the cap (`LocalFs::make_room`). It never runs for a batch larger than the whole cap, and the after-sync trim still protects recent slots, so a batch the user chose to keep is never rotated away.

### The effects layer
`crates/oneup-effects` is the only code that changes user content. Every effect re-checks its preconditions on the very handle it then acts through:
* **The item is opened by path and verified by file ID.** It's opened where the Local tree last saw it, and used only if its file ID is the planned item's (by ID only when that path is out of date: a handle opened by ID makes another program's rename-over save fail). Files are opened exclusively, so nobody can write, rename or delete them between the check and the change, and a file another program has open is reported as *busy*. Handle-based renames need a path-opened handle (NTFS rejects renames through handles opened by ID), so the item is opened by path, where the Local tree last saw it (or, if it isn't there, where its ID leads), and its ID compared again.
* **Size and last-write time must still match the planned stamp.** Links and other reparse points are never touched; placeholders only through the Files On-Demand effects.
* **Destination folders are pinned.** They're opened without delete sharing, so they can't be moved away while something is placed in them.
* **Paths stay inside the sync folder, outside `.oneup`.** Names are checked: no separators, `..`, device names, or trailing dots or spaces.
* **Renames never replace.** `FILE_RENAME_INFO` is sent with `ReplaceIfExists = false`, so a taken name fails with *name taken* and nothing changes.
* **Downloads are written to `.oneup\staging` and then renamed into place.** That's the same volume, so placing a download is a rename. Replacing a file first moves the old one into the version store, and moves it back if placing the new one fails. A `DropIfSynced` old copy is then deleted through its handle, if it was proved to be the synced version (above).
* **Recycling moves, it doesn't delete.** The item moves to `.oneup\versions\<time>-<n>\<name>`, with an `origin.txt` giving its former path, for `oneup restore`. Using our own version store rather than the Windows Recycle Bin keeps the move atomic and checked; the Recycle Bin API works by path and can race. The one exception is a file in a batch the user chose to discard, deleted by handle once proved to be the synced version.

`.oneup` directly in the sync folder also holds `root.marker`, the folder's identity token (data-safety invariant 4). The folder must still have the recorded volume serial and file ID *and* carry the marker, or everything halts. Both trees exclude `.oneup` at the top level: the scanner and observer classify it as excluded, and the mirror treats a drive-root folder of that name as excluded. A deeper folder of that name is ordinary.

### The version store
`oneup versions` (list), `oneup restore` (asks the agent's next round to move an item back by handle, `Step::RestoreKept`, never replacing: a taken name gets ` (restored N)`) and explicit pruning (`versions --older-than-days/--max-gib`, a preview unless `--yes`), all in the effects layer (`LocalFs::versions/restore/prune_versions`). **Automatic trimming** (`oneup_effects::versions::Trim`) runs after a settled round, never during one. Items younger than 30 days are never removed. Older ones go oldest first, and only while the store exceeds the smaller of 5 GiB and 2% of the disk. Settings live in the data folder's `meta` table (`versions.*`, also `rotate`, `overflow`, `keep_replaced`); both size limits at 0 turn it off. Trimming, rotation and the two `DropIfSynced` cases are the only places OneUpDrive permanently deletes user content, which is why their rules are pure and unit-tested on their own.

**Listing the store** (each settled round trims, and each round that keeps something asks how much room is left) reads `.oneup\versions` once and takes each slot's name, origin and size from `.oneup\versions.cache`, so a round doesn't measure every kept folder again. A slot is filled once (its item moved or copied in, then `origin.txt` written) and never changed, so a cache entry holds while a slot folder with the same creation time is there. A slot that isn't in the cache, has another creation time, or has no `origin.txt` yet is measured; the listing decides which slots exist. The cache is OneUpDrive's own file, replaced atomically, and a missing or damaged one is rebuilt. A slot that another `oneup` (a restore, a trim) removes during a listing or trim is skipped.

## Executor (`crates/oneup-exec`)
The executor runs one round's approved operations: side by side where they're independent, in the planner's order where one depends on another (below).
* **Local changes** go through the effects layer.
* **Cloud changes** go through a `Cloud` trait: Graph (`GraphCloud`, below), a vault (`VaultCloud`, [vaults.md](vaults.md)), an in-memory fake in tests. Every cloud change is conditional: changes to an existing item carry its planned eTag (`If-Match`), and creations fail rather than replace when the name is taken.
* **Bookkeeping** (`Pair`, `Record`, `Forget`) re-checks its preconditions against the store.

After each effect, the executor writes the rows it changed in one transaction: the Local, Remote and Synced trees, plus hashes. So the next round plans from the new state, and when the journal or delta later reports the same change, applying it again changes nothing.

**Running operations side by side** (`exec.rs` `run_checked`, `schedule.rs`). One at a time, a round of small files waits on one network round trip after another. So each operation, or `$batch` group, claims what it touches, and starts once nothing earlier that hasn't finished conflicts with it:
* **Items** it creates, changes, moves or removes (its Synced row, local file ID, cloud ID): exclusive.
* **Folders** it puts something into or takes something out of: shared, so many transfers run in one folder at once, but nothing changes the folder meanwhile.
* **Names** it takes or frees, as (folder, folded name): exclusive, so a name freed by one operation and taken by another (a swap, a conflict copy and the download that follows it) keeps its order.
* **Moves, renames and removals of folders**, and cloud prunes, reach everything below them, so they run **alone**: they wait for everything before them, and nothing starts until they're done. A `$batch` may still hold a folder's change together with changes to other items, deeper inside it too, under the same claims (below): each names its item by ID with its own eTag, so none depends on where another's item is.
* **Reading a file, however large, doesn't run alone** (below): hashing it, checking an old copy before it's dropped or replaced, checking content before it's freed, hashing a new file whose content OneDrive may already have, and an upload's fragments.

The item's current folder and name come from the store (one indexed lookup) for operations that move, rename or remove it; an item the store doesn't have runs alone. The executor takes in up to 256 operations from the oldest not yet finished, in the planner's order, so behind one slow transfer the rest go at most that far ahead and what's held for the report stays bounded: an operation never starts before an earlier one it conflicts with, waiting or not, so whatever depends on an earlier operation runs after it and checks its own preconditions then. Claims only decide *when*: every effect still re-checks its preconditions where it acts (data-safety invariants 2 and 5), so a claim read from state that changed meanwhile can turn an operation into a skip, never into a wrong change. Recording a transfer re-checks, in the same transaction, that its folder's Synced row is still there.

The memory profile sets the limits (`Parallel::for_profile`): operations under way at once `minimal` 4, `balanced` 8, `performance` 16, of which uploads above 4 MiB (each holds a fragment in memory) 1, 2 and 4. `[agent]` can set each on its own (`operations_at_once`, `large_uploads_at_once`; [rules.md § User controls](rules.md#user-controls)). The Graph client's limit on requests in flight follows it (`Parallel::requests`): it starts at the profile's operation count and grows, while OneDrive answers, to twice that (at most 32), so every operation under way can have its request out next to the round's listing and checks; it still halves when OneDrive throttles, and the bandwidth caps are shared by every transfer. **Disk work runs off the executor's task** (`oneup_exec::blocking`). The operations under way share one task, so anything that blocks it stalls them all, and a download gives up after 60 s without a byte. So whatever reads a file runs on a blocking thread (`spawn_blocking`) while the task goes on: an upload's fragments, read through `Source::fill` (the `Cloud` trait's upload source; GraphCloud reads every fragment that way), the hash of a new file that OneDrive may have a copy of, and the effects that may read a whole file (hashing, recycling and replacing, which check an old copy before dropping it, and freeing up space). Hashing to compare a file here with OneDrive's (`Op::Hash`, as on a first sync over a copy) has a limit of its own on top of the operations': at most `Parallel::hashes` at once (`[agent] hash_files_at_once`, default 1: on a spinning disk, more seek against each other), counted in the scheduler's claims (`Claims::hash`, `Held::has_room`), so one waiting for room isn't started at all and a round that halts has only the ones under way to wait for (`everyday_same_files_on_both_sides_are_hashed_side_by_side_and_paired` checks the limit with each hash held on its thread). An upload's file is opened on the task and read on blocking threads; its oplock request outlives the thread that made it (its handle is bound to a completion port, and Windows cancels a thread's pending requests when it ends only for handles that aren't: measured, `a_watched_file_outlives_the_thread_that_opened_it`), and each read fails with `ChangedMeanwhile` on whatever thread it runs. Writes to the store don't wait inside SQLite for another connection's write (`Store::try_write_now`): `Db::write` tries again after a pause that doubles from 1 ms to 100 ms, for up to `BUSY_WAIT` (60 s), and the task goes on meanwhile; reads don't wait for writers (WAL). **A vault reads its uploads in place**, on the task, through the source's `Read` side: its encryption (`oneup_vault::content::Encryptor`) wraps a synchronous reader. That holds nothing else up, because a vault runs one operation at a time (`Cloud::concurrent`), so no other operation shares the task. Placing a downloaded file goes through a blocking thread too (`LocalFs::place_download`: a replacement reads the old copy first), and so does replacing a placeholder. Creating a new placeholder or folder, cloud metadata changes and the transactions themselves still run on the task: they're short. Tests: `a_long_read_doesnt_hold_up_the_rest_of_the_round` holds a hash on its thread until the round's upload and download are done; `a_round_waits_for_a_busy_database_without_blocking_its_task` has another connection hold the database for 500 ms while the round's task keeps running. A vault runs one at a time (`Cloud::concurrent`): a new file's storage folder is found or made in several requests, which two uploads into one folder could interleave. A pause or a full OneDrive is checked as each operation starts: one refused then isn't sent, and those already under way finish (a full OneDrive refuses them too). Operations finish, and are reported, in any order. Measured on a test account, 200 files of 2 KB: uploading them took 30 s with `balanced` (22 s with `performance`) instead of 147 s one at a time, and downloading them 23 s (16 s) instead of 243 s. **Where the time goes** (`oneup_exec::timing`): after each round that did something, the agent logs at debug level how long each kind of operation, and each kind of request behind it, took (count, average, longest), e.g. `RUST_LOG=oneup_exec::timing=debug`. On that run a small upload was one request of about 750 ms, and a download 520 ms for the item and its link and 120 ms for the content. With the in-memory cloud and 20 ms per request, 100 uploads and 100 downloads took 1.5 s instead of 6.5 s (`timing_one_at_a_time_and_side_by_side`).

**A new folder's contents go in the same round** (`Executor::run_following`, `sync::Follower`). The reconciler plans Synced folders only, so a new folder's contents can't be planned with the folder: their destination doesn't exist on the other side yet. Left to the next round, a new tree took a round per level, each paying a round's start (the change journal, the cloud listing, planning, the gate) and running one level's operations without the next's. So once an operation that made a folder is recorded (`MkdirRemote` or `MkdirLocal` of a new item, or `Pair` of two new folders), the executor asks the caller for the folder's contents: the same planner, over the store as it is then; the gate, with the round's policy, answers and safety window; and the round's holds after it (files that keep changing, a full OneDrive, failures waiting their turn). They're taken in after everything taken in before, so the claims order them after the folder, and they run beside the rest of the round; the folders they make are followed the same way. A new folder's contents are mostly new items, so such a plan rarely removes, replaces or moves anything (a one-way pair joining two new folders of the same name does: it replaces OneDrive's differing files). One that does is left whole to the next round (`oneup_gate::may_follow`, the rule the engine and the test harness both apply), where the breakers, the content guard and the version store's room weigh it with everything else; so the gate here only withholds what a pause, a panic or a planner's hold does. A folder whose creation was skipped or failed brings nothing. At most `FOLLOW_MAX` (20,000) operations a round are taken in this way, each folder's plan cut to what's left, which bounds what a round holds for its report (a first sync adopting a large tree goes on in the next rounds). Whatever is left out is in a new folder, whose Synced row was marked when it was linked, after the round's high-water number, so the next round plans it; that round plans the followed folders again too, and finds nothing left. On a test account, 200 files of 2 KB spread over 5 nested new folders took 2 rounds instead of 7: uploading them 32 s instead of 39-40 s, downloading them 16 s instead of 41-48 s. With the in-memory cloud and 100 ms per request, the same tree took 8.7 s over 8 rounds, a level a round, and 7.5 s over 2 rounds followed in the round, as long as one new folder (`timing_new_folder_trees`). `oneup sync --dry-run` lists the first plan only.

Content is verified in passing:
* **Uploads** are hashed while they're read, and the cloud's reported QuickXorHash must match before the item counts as synced. **Reading never stops a program from saving:** a save that fails because a sync app has the file open is the worst thing a sync app can do to someone mid-work. So the file isn't opened with writers excluded, and it's read through a single handle holding a **Read-Handle oplock** (`win::WatchedFile`, `Volume::open_watched`), taken before its stamp is checked. The file is opened at the path the Local tree gives, with the oplock requested as part of the open (`FILE_FLAG_OPEN_REQUIRING_OPLOCK`), and its file ID checked on that handle afterwards: no other handle on it is opened. If that path holds another item now (busy or not), the item is found by ID and opened where it is. Windows breaks it when anyone writes the file, truncates it or maps it for writing (the writer doesn't wait), and when another program needs every handle on the file closed: a save that renames a new file over it, a delete, an open that doesn't share reading, a rename of a folder above it. That program waits until the handle closes, then goes ahead. One thread of OneUpDrive's own (the acknowledger, `oneup-oplock-ack`) takes the breaks off a completion port the handles are bound to and closes the handle, never the reader: the reader may be blocked on other work. It never waits for a file: if the handle is in use (a read being started, a metadata query), a thread of the break's own closes it once it's free, so a file held up there keeps no other file's save waiting (`a_held_up_file_keeps_no_other_save_waiting`). Reads are waited for without holding the handle, and closing it cancels one under way. Each oplock request belongs to a table under its handle's completion key, which is never reused, until its own completion (key and `OVERLAPPED`) comes off the port; anything else there is ignored (`only_a_requests_own_completion_touches_it`). One that finishes at once with a status that may still queue its completion (a warning or informational one) is kept until that comes, 16 at most; past that, files aren't opened to be read (*busy*, logged once) rather than the table growing (`requests_kept_for_a_completion_are_bounded`). A save over a file being read waits a few milliseconds longer than it would otherwise (measured with a 64 MiB file: 6 to 11 ms instead of 0.4 to 6 ms, `a_save_waits_only_briefly_for_a_read_under_way`). Every read of the upload's source checks it (`UploadSource`, `ChangedMeanwhile`), so a read that a write or replacement overlaps fails, and the upload is cancelled before it commits (a one-request upload is read whole before it's sent; a session cancels on a read error); the operation is skipped as *changed* and the next round sends the saved version (`everyday_a_save_by_rename_during_an_upload_goes_through_and_the_saved_version_is_sent`). The check can't miss a write the bytes already read include: Windows queues the break on the acknowledger's completion port before the write changes anything, and the check waits until the acknowledger has handled everything queued up to then (`a_write_is_seen_as_soon_as_it_is_made`). A save that lands after the last bytes were read, while the request is under way, leaves a consistent upload of the version before it; the file is then recorded without its stamp (and without a cached hash, and on demand not marked in sync), so the next round hashes it and sends the new version even if the save kept the size and time (`a_save_after_an_uploads_last_read_that_keeps_the_stamp_is_still_sent`). Measured (`a_watched_file_sees_writes_and_keeps_no_program_waiting`): the oplock is granted while another program has the file open, for writing too, and that program's later writes break it; it isn't granted while the file is mapped for writing (writes through an existing mapping wouldn't break it), which counts as *busy*. Hashing a file, sampling it for the content guard and `oneup plan --verify` read the same way. Cloud Files queries on the file (is all its content here, does its identity vouch for it) go through the same handle: it's set to skip the completion port when a call succeeds at once (`FILE_SKIP_COMPLETION_PORT_ON_SUCCESS`), so they queue nothing there (`on_demand_reads_hold_one_handle_and_saves_go_through`). Whether a Files On-Demand file is dehydrated is read from its folder's listing first (`Volume::listed_at`), since opening one with data access downloads it. That leaves a window between the listing and the open: a file dehydrated, or turned into another provider's placeholder, in it would be downloaded by the open itself. OneUpDrive's own dehydration runs only as a planned effect, never on an item being read, so the worst case is an unneeded download, never lost content. Whatever the open finds is checked on its handle before any byte is read (attributes and reparse tag, then on demand whether all its content is here): anything not an ordinary file or one of our fully present placeholders is refused (`a_file_that_became_offline_since_planning_is_refused_before_reading`, and for `--verify`, `verify_hashes_only_unchanged_ordinary_files`). A save whose rename runs at the very moment of the open can still fail: a rename over a file fails if a new handle on it appears meanwhile, whoever opens it. Measured with 1,000 saves a second against an open every 8 ms, it happens as often as when a program just opens and closes the file (`timing_saves_racing_opens`); holding the file afterwards adds nothing. **Saving by renaming a new file over the old one** depends on the handles we hold on it (measured, `a_rename_over_save_and_the_handles_we_hold`). While any handle on the file is opened **by ID**, even attribute-only and sharing everything, every such save fails with *access denied*. Through a handle opened **by path**, a rename with POSIX semantics goes through; a classic rename (`MoveFileEx`, which `cmd`'s `move /y`, .NET, Node, Python and Go use) fails while *any* handle on the file is open, unless that handle is the only one and holds a Read-Handle oplock, whose break closes it. `ReplaceFile` goes through in every case. Folder handles, by ID or by path, stop no save inside them. So the effects never open a file by ID when they can avoid it: the agent gives `LocalFs` a locator (`LocalFs::set_locator`, its own connection to the state database) that says where the Local tree last saw an item; the item is opened there by path, attribute-only first, and used only if its file ID is the planned one. Only when that path no longer leads to it (renamed or moved since the observer last ran) is it found by ID, for the one call. `Volume::opened_by_id` counts those opens (`everyday_syncing_opens_no_file_by_id`).
* **Downloads** are hashed while they're written to staging. They must match the Remote tree's size and hash for that eTag before anything local changes.

**Crash safety.** Most operations recover on their own if the process dies between an effect and its record: the next round finds both sides agreeing and pairs or records them. Three operations take an item out of the tree in a way the change journal only sees as a move *out* (into the version store), which would otherwise be "missing without evidence" and held forever. Their records are written **ahead**:
* recycling and replacing note deletion evidence first;
* a conflict copy detaches its Synced row first, so the renamed copy can never be mistaken for a rename of the synced item. A detached row's cloud file is then downloaded back to its name, even if it turns out unchanged (a conflict planned from a listing behind the cloud): the file here was renamed aside, not deleted, so it's never deleted in OneDrive.

The same transaction saves which record is pending (in `meta`, under `exec.pending.<local file ID>`: one per item, so operations under way at once each have their own), and the operation's final record clears it. A record left over, because the operation failed or the process died, is settled right after the operation, before it releases its claims (so nothing that touches the same item or name runs first), or at the start of the next run after a restart (every `exec.pending.*` record, and one under `exec.pending` itself, where versions that ran one operation at a time kept theirs). A halt stops the round at once: operations still under way are dropped where they wait, which leaves them as a crash would. Work they handed to a blocking thread runs to its end first, and the round waits for it (`Jobs::settled`): an effect still running would otherwise change the folder behind the next round, while it settles these records (`a_halted_round_ends_only_after_the_work_it_handed_to_a_blocking_thread`). A round dropped under way (its caller stopped waiting) waits too, blocking the dropping thread (`blocking::Settle`); that can't deadlock, even on a current-thread runtime, because the work runs on the blocking pool and never waits for the runtime (`a_round_dropped_while_it_recycles_a_file_waits_for_the_recycling`). If the folder itself shows the effect didn't happen, the record is undone: the evidence is withdrawn (the item is still in the folder), or the Synced row is linked again (the item still has its old name). Otherwise it stands, and the change journal reports the rest. The folder is checked directly, because the journal can lag.

**Crash-injection test.** With the test-only `crash-test` feature, `Executor::crash_after(n)` stops a round at its n-th crash point, as if the process had been killed. The in-memory cloud lets other operations run before and after each request, so operations under way at once interleave, and a crash drops the others mid-request. The crash points are after every effect (before its record), after every write-ahead record (before its effect), and between the steps of effects that take several, counted by the effects layer (`LocalFs::crash_after`): keeping an item in the version store (after its slot is made, after the item is moved in, before its `origin.txt`), replacing a file by a download (between moving the old file out and the new one in, and once the new one is in place), and dropping a `DropIfSynced` old copy (after it's deleted, before its slot goes). A slot left empty or with only its `origin.txt` is skipped by the store's listing. While a crash is armed, an effect the executor would hand to a blocking thread runs on the round's task instead, so the effects' crash points count in the same order every run and crash point n is always the same place. `a_crash_at_any_point_of_a_round_loses_nothing` (`tests/sync.rs`) takes a round with one change of every kind on both sides (uploads, new and replacing downloads, new folders two levels deep, whose contents go in the same round, moves both ways, deletions both ways and a conflict copy), crashes it at each of its points in turn, reopens the database from disk and syncs to the end. It checks that no pending record survives the first run after the restart, that the store's invariants hold (including: no item is both present and noted deleted), that both sides agree, that every content is still somewhere (the folder, the version store, or OneDrive's recycle bin and version history), and that deletions stay deleted. `a_crash_inside_a_replacing_download_loses_nothing` crashes a replacing download at each of its steps, with and without keeping replaced files: between the two renames the name is free and the old version is only in the version store; after a restart the new version is downloaded again, the old one is in the version store or OneDrive's history, and nothing is left in staging.

**Databases** ([databases.md](databases.md)) are sent only in a consistent state and replaced only while closed: an upload reads the file's first bytes through its watched handle, and a SQLite database's `-wal` and `-journal` are watched with it; a database not ready (or a replacement over one) is skipped as `Skip::Database`, with why and which program in `Report::databases`.

**Outcomes.** A failed precondition (changed, busy, name taken, folder not empty, content mismatch, a database not ready) **skips** the operation, and the next round re-plans it. A failed identity check of the sync folder, or a database error, **halts** the round.

## Cloud over Graph (`oneup-exec/src/graph.rs`, `oneup-graph`)
`GraphCloud` implements `Cloud` with these Graph calls:
* **Download:** read the item's eTag and pre-authenticated download URL, from the full item. Links are read ahead, 20 in one `$batch` (`graph.rs` `Links`): the executor names the downloads it takes in (`Cloud::upcoming`), and a download whose link isn't there yet reads it together with the next ones', while one whose link is being read waits for that batch, so downloads starting together send one batch. As downloads use them, the next links are read while content arrives, up to 60 in hand and at most two batches at once, so a download rarely waits for its link. Only files whose OneDrive hash is known are named: a link serves whatever the file holds when it's used, and only the hash tells another content of the same size from the planned one. A link read ahead is used within a minute (they're short-lived), only once, and only if the answer is about the item asked for; one that no longer works is read again on its own. Downloads named but not reached within 5 minutes are dropped. On a test account this took a small download from 650 ms to 250 ms (the content itself is about 150 ms), and 200 small downloads from 23 s to 13.5 s. OneDrive Personal may name the URL `@content.downloadUrl` instead of `@microsoft.graph.downloadUrl`, and leaves it out of a `$select`ed answer (measured: every time), which used to cost a second request per download. A mismatched eTag means *changed*. The URL is then fetched **without** the bearer token. It serves whatever is current, so a change after the eTag check is caught by the executor's hash check against the planned version.
* **Upload:** a single PUT up to 4 MiB, an upload session above that (fragments sent in order, without the bearer token). Above 4 MiB a session is faster per byte than a single request, which goes through Graph itself. Fragment sizes adapt to the connection (`oneup_graph::fragment::Sizer`): from 10 MiB up to the memory profile's limit (`minimal` 10 MiB, `balanced` 40 MiB, `performance` 59.69 MiB), sized so per-request overhead stays near 10% and one fragment takes at most 30 s; on a test line, large uploads ran about twice as fast as with fixed 10 MiB fragments. New items use `@microsoft.graph.conflictBehavior=fail`; replacements send `If-Match` (for a session, on `createUploadSession`). The answer must carry the QuickXorHash, which Graph computes asynchronously, so the item is re-read a few times if it's missing. Failed sessions are cancelled.
* **Replacing by upload session:** Graph checks `If-Match` when the session starts, not when the last fragment commits it. So the last fragment of a replacement is at most one 320 KiB unit, and right before it the item's eTag is read again: if it moved on, the session is cancelled and the upload is *changed* (the next round plans the conflict, as for a one-request upload's 412). That leaves the moment between this check and the commit. Before the upload, `Cloud::version_mark` reads the newest entry of the file's version history (then the eTag, which shows nothing was saved since); after it, `Cloud::replaced_other` finds ours in the history again, by its version ID: the cTag of the commit's answer gives it (`Cloud::uploaded_version`; without one, the file is read once, and only if it still has the eTag the upload left). It goes into the rescue record durably as soon as the upload's answer is in, before anything else; a record without it (the process killed in between) never takes the file's current version instead, which a later save may have replaced, so it keeps nothing and waits to be given up and listed. On OneDrive Personal the cTag (`c:{…},3`) counts content versions as the history numbers them (`3.0`), and the newest entry is listed at once with the item's size and time, to the second; the eTag counts renames too, and a rename moves the current version's time, so neither identifies it (measured). Without a cTag, ours is found by time and size. The entry right below ours should be the planned one, matched by ID and its time and size, or by time and size alone. Ours not listed (the history lags behind a commit, and its newest entry may be the very edit gone over) is `Replaced::Unknown`, never "as planned". If another entry sits in between, an edit landed in that moment and ours went over it: the executor downloads that version (`Cloud::download_version`, into the staging folder) and uploads it next to the file under a conflict name free on both sides (each candidate looked up by name in the store, so a folder's other items are never loaded; `conflictBehavior=fail` stays the final say), and the activity log names it. The next round brings it to this PC like any new file in OneDrive. Keeping it is never dropped. Before the upload starts, a record of it goes into `meta` (`exec.rescue.<item>.<version>`), committed durably (`Db::write_ahead`); it's updated with the version once found, and removed only when the history shows the upload went over the planned version, or in the transaction that records the kept copy. So the process killed, or a power cut, anywhere from the upload to the copy leaves the record, and the start of every later round tries it again (`Executor::retry_rescues`, `Report::kept_later`). A record whose upload never committed (OneDrive still has the eTag it was to replace) is removed. If the history doesn't show what the upload went over (the planned version not listed, or nothing after it yet: the history can lag behind a commit), nothing is guessed (`Replaced::Unknown`) and the record waits for the next round; after `RESCUE_TRIES` (20) such rounds it's given up: no longer asked for, reported (`Report::rescues_given_up`, a failed entry in the activity log) and listed by `oneup problems` (`edit_not_found`) for 14 days. The edit's download and upload follow the network's policy as the agent's does mid-round (`Executor::set_may_fetch`): working offline, or on a network that moves only names, only small files or only the files the user opens, the record waits until it lets them through; a download under way is asked again before each write and stops there. The upload counts as done either way: a version not kept yet (its download failed or waits, no free name, a copy that didn't match) is reported on its own (`Report::theirs_not_kept`, a failed entry in the activity log naming the file), not as a failed upload, which would leave it out of the round's safety-stop count and back it off. With a data budget, a replacement over 4 MiB starts only when the budget has room for three times its size (the upload, and the edit's version down and up again). A vault does the same on its encrypted contents.
* **A lost fragment answer:** a fragment whose answer never arrived (the network or the server failed) or whose send found its bytes already received (416) doesn't restart the upload. The executor asks the session where it is (`GET` on the upload URL, `nextExpectedRanges`) and goes on from there, after a pause that grows each time, with one budget per fragment: at most 5 sends in all. The Graph client sends a fragment once (it retries other requests itself, so a fragment would otherwise be sent up to 8 times per send); it still waits out throttling (`Retry-After`), which isn't a send of its own. Only the fragment in flight is still in memory, so a session missing anything else, or gone (404: expired, or completed by the lost answer), ends the upload, and the next round plans again from what OneDrive then has. A session asked about while the network is down is asked again after the same growing pause. **An upload the network cut off** isn't cancelled: `GraphCloud` keeps its session in memory (at most 16, the URL never logged or written down), with the bytes it was known to have and the QuickXorHash of those bytes as they were read, and the same for the end of the fragment in flight. The next try of the same upload (same folder, name, size and planned eTag) asks the session where it is. Only if it's exactly at one of those two points does it go on: it reads the file from its start again (the executor hashes all of it, as for any upload), checks that every byte already sent (all of them, not a sample) hashes as it did, and sends only the rest; a file changed since is cancelled and sent from its start at the next round. Anywhere else, or gone, it starts a new session. The executor's own checks are unchanged: the write watch covers this try's reads, and the server's hash of the whole file must match what was read. A vault's uploads never resume (`Source::resumable`): their encryption differs every time. Tested over a simulated link of 256 kbit/s, 600 ms round trips, 1% lost answers, short drops and a four-minute outage (`a_slow_dropping_link_finishes_an_upload_without_starting_it_again`).
* **Server-side copy instead of upload:** for a **new** file of at least 1 MiB, the executor looks for cloud files of exactly its size (the partial index `remote_item_copyable`; only files ≥ 1 MiB with a hash). Only if there is one does it hash the open file and rewind it (a write meanwhile skips it as *changed*, as for an upload). On a hash match, `Cloud::copy` re-reads the source and requires the planned eTag and the same hash, then `POST /items/{id}/copy?conflictBehavior=fail` and follows the monitor URL (pre-authenticated, never logged; up to ~2 min). The new item must come back with the same size and hash, as an upload's must. If its content differs (the source changed in between), the item just made is deleted again (`If-Match`, into OneDrive's recycle bin) and the file is uploaded. Any other failure, or a copy still running after the wait, falls back to an upload, which fails harmlessly as *name taken* if the copy lands after all. The activity log says the content was copied in OneDrive and nothing was sent. Copying a 300 MiB file takes 2–3 s, against 17–36 s to upload it on a test line.
* **Create folder:** POST to `children` with `conflictBehavior=fail`.
* **Move/rename:** PATCH `parentReference` + `name`, with `If-Match`. OneDrive refuses to move or rename a folder with more than its list view threshold (5,000) of items below it: **422 `notSupported`, inner code `tooManyResources`** (`CloudError::TooManyItems`). The executor then moves it in parts (`Executor::rebuild`): it checks the folder's eTag, creates a new folder at the destination (`conflictBehavior=fail`), moves the contents into it a page (`Cloud::children`, up to 1,000) and a batch (20) at a time (a subfolder that is itself too large the same way), and finally deletes the original, re-read for its current eTag, only if OneDrive confirms it empty. The new folder stands for the old one from then on: a new ID, with everything inside it keeping its own. Each step is recorded as it happens, so the store always matches the cloud. The Synced row follows the new folder as soon as it exists, so an interruption leaves what wasn't moved yet in the original folder, which the next round treats as a folder of its own (the move, done in part). Nothing is lost at any point (`a_crash_while_moving_a_large_folder_in_parts_loses_nothing`). An item a batched move reports as changed but that is already in the new folder (the answer was lost and the request resent) is recorded as moved. The original's stored rows are removed without deletion evidence: anything still stored below it was moved elsewhere meanwhile, not deleted, and reads as missing until the next listing places it (`an_item_moved_away_while_a_large_folder_is_moved_in_parts_is_not_deleted`). A change of case alone can't be done in parts (OneDrive compares names ignoring case, so the new folder can't sit next to the original), and is reported as failed. A vault can't list folders this way and reports the move as failed.
* **Delete:** DELETE with `If-Match`, after re-reading the item: Graph deletes a folder *with its contents*, so a folder with any child is refused (`NotEmpty`).
* **Batches** (`$batch`): the executor sends a run of consecutive cloud metadata changes (create folder, move/rename, delete) as one JSON batch of up to 20 (`exec.rs` `batch_of`, `Cloud::batch`). Each keeps its own `If-Match` and its own outcome, and is recorded one by one afterwards in plan order, with the same crash points as alone. The group is cut conservatively before any change that depends on an earlier one in it: the same item twice, an item whose folder the group changes, a destination folder moved or deleted in it, a name freed and then taken (e.g. a swap), or a folder deleted after something in the group came out of it. Requests in a batch run concurrently on OneDrive's side. Deletions re-read their items first (one batch of GETs) for the eTag and emptiness check. Throttled or failed requests inside a batch are sent again after `Retry-After` (which pauses every other request too), a bounded number of times.
* **Restoring a version** is a round's step (`Step::RevertTo`) that downloads it and uploads it as a new version under `If-Match`, checked by hash, because Graph's `restoreVersion` ignores `If-Match` on OneDrive Personal.

Status mapping: 412 and 404 → *changed*, 409 → *name taken*, except that OneDrive's error code wins where there is one: in a batch, a stale eTag comes back as **409 `resourceModified`**, which must read as *changed*. Both make the executor skip and re-plan. **A new folder's eTag changes moments after it's created** (`…,1` then `…,2`): changes are planned from the cloud listing, which has the later one. Pre-authenticated URLs carry a session token, so errors label them ("upload session fragment", "download") instead of printing the URL. A refused request's error keeps at most 2 KiB of its body, so a proxy's page can't overflow problem reports or the control pipe.

**Dead connections.** Every HTTP client starts from `oneup_graph::client::http_builder`: a 20 s connect timeout, 120 s per metadata request, and TCP keepalive (15 s), so a connection that died without closing (sleep and resume, a NAT dropping it) fails. A transfer may take up to 6 hours, so a download is also abandoned after 60 s without receiving a byte; each read restarts that clock, so a slow line that keeps moving is never cut off. There's no client-wide read timeout: reqwest's also bounds the wait for the response headers, which for an upload includes sending the whole fragment. **A failed token refresh** is retried like a failed request (backoff, the token endpoint's `Retry-After`, a bounded number of attempts) when the network failed or the endpoint answered 429/5xx or something that isn't an OAuth error; only a real OAuth refusal (`invalid_grant` and the like) asks the person to sign in again. After a 401, the cached token is dropped only if it's still the one that got the 401, so a burst of 401s causes one refresh.

**Live check.** `oneup cloud-check` (hidden, developers only) refuses any data folder without the test-account marker, and any sign-in whose drive differs from the marker or matches the default folder's drive. It works inside a new `/oneup-cloud-check-<random>` folder and removes it afterwards, checking: create and refuse a taken name; small and fragmented uploads with hash and size verified; download byte for byte and refuse a stale eTag; replace by single PUT and by upload session (same item ID), refusing stale eTags; move/rename, refusing stale eTags and taken names; delete, refusing a non-empty folder and a stale eTag; server-side copy; batched create, rename and delete.

## Parking (`oneup-plan/src/park.rs`)
`Parked` wraps the store's `Trees` and hides items a sync must not transfer:
* **Problem items**, local only: names OneDrive refuses (`names::is_invalid`: forbidden characters, reserved names, leading or trailing spaces, trailing dots) and files over 250 GB. They're collected (`Parked::problems`) so the user can be told and can fix them.
* **Local-by-nature files**, on both sides: `desktop.ini`, Office lock files (`~$…`), `*.tmp` and the OneDrive app's marker file. The official client doesn't sync these either. They're also hidden in the cloud, so a stray cloud copy isn't downloaded onto the local one every round. They're skipped silently.
* **Working files**: a file named `<X>-wal`, `<X>-shm` or `<X>-journal` beside `<X>`, on each side, with its Synced record ([databases.md](databases.md#working-files-never-travel-oneup_planpark)).
* **The user's rules** ([rules.md](rules.md#where-rules-apply)).

A hidden item reads as **Missing** (the `Trees` contract). So a synced file that *becomes* parked, say renamed to `report.tmp`, is held on both sides and never deleted in the cloud. The store's own filtering (links, excluded folders, lossy names, packages) is separate; parking is a pure layer, so the rule list lives with the planner's other OneDrive limits.

## Purity and scale
The reconciler reads the three trees through a small `Trees` trait: lookups by ID and children of one folder. The simulation backs it with an in-memory world, and production backs it with the indexed SQLite store. It never writes, and its output depends only on what it reads, which keeps it deterministic. It plans per **folder context**: one Synced folder, its Synced children, and the current children on both sides. Each item is decided exactly once: Synced items in their *agreed* parent's context (so moves are seen there), new items in their current parent's. In steady state only *dirty* folder contexts are planned (below), so cost follows the number of changes.

## Storage (`crates/oneup-store/src/synced.rs`)
* `synced_item(sid, parent_sid, name, kind, size, qxh, local_id, local_mtime, remote_id, remote_etag)`, indexed by parent, and with **unique** indexes on `local_id` and `remote_id`, so no item can be linked twice. Writes are upserts on `sid` alone: linking an already linked item fails instead of silently replacing the other row. Sids are never reused (the largest ever allocated is kept in `meta`), so a stale plan can't address a newer row.
* **Deletion evidence:** `local_gone(file_id)` and `remote_gone(id)`. They're written by the observer, by the Recycle Bin check ([local-tree.md](local-tree.md#the-recycle-bin-is-evidence)), and by the mirror when delta reports `deleted`: `delete_subtree` records every Synced item in the deleted subtree, because a deleted folder is evidence for its contents. Evidence is kept only for IDs a Synced row links to, the only ones the reconciler asks about, so these tables are never larger than the Synced tree. They're dropped when their row is removed or relinked, and when the item is back in its tree (triggers on `local_item` and `remote_item`: a file restored from either recycle bin, or a child delta reports moved out of a folder after the folder's deletion). Evidence for an item that is still there would turn its later disappearance without evidence into a deletion, so the consistency check refuses it on both sides. A mirror rebuild and a rescan never write evidence, and leave the Synced tree and evidence alone.
* **Forgetting a folder takes its records along.** `Ops::synced_remove` removes a folder's whole subtree of Synced records with their evidence (dropping records never deletes content), so a record whose parent is gone can't be left behind; the store's consistency check refuses such orphans.
* **Hashes:** `local_hash(file_id, size, mtime, qxh)`. A hash counts only while the file still has that exact size and mtime.
* **What the reconciler sees** (`impl Trees for Ops`): local files and folders whose contents were listed and whose names are valid Unicode; cloud files, folders and the root that aren't excluded. Links, excluded/unreadable folders, lossy names and packages are filtered out and read as **Missing** when asked for by ID, so a Synced item that becomes unsyncable is held rather than taken for a deletion. Folder sizes and times are zeroed: OneDrive reports a folder's total size, and a local folder's mtime changes with its children.
* **History:** `synced_history(seq, at_ms, sid, change, parent_sid, name, kind, size, qxh, remote_id)`, indexed by `(sid, seq)`, by `(parent_sid, at_ms)` and by `at_ms`, written by triggers ([§ Rewinding a folder](#rewinding-a-folder-cratesoneup-syncsrcrewindrs)).
* Every lookup is one indexed query, and a folder's children are one query per side, so a round costs what its folders contain. Whether a folder has any children (checked before a deleted folder is removed, or its record forgotten) reads up to the first visible child only (`Trees::any_*_child`, also through parking), not the whole list. Subtree queries use `IN` lookups and a test (`subtree_queries_never_scan`) checks the bundled SQLite's query plans, since without table statistics SQLite can pick a full scan of a multi-million-row table.
* The reconciler sorts every children list itself, so its plans don't depend on the order a backend returns rows in.
* **Write transactions are `IMMEDIATE`**, with a 60 s busy wait (`oneup_store::BUSY_WAIT`): in WAL mode a deferred write transaction fails at once when another connection (the hydration service, the window, a command) committed meanwhile. The executor waits outside SQLite instead, without blocking the round's task (`Store::try_write_now`, [§ Executor](#executor-cratesoneup-exec)).
* **Durability.** The store runs in WAL mode at `synchronous = NORMAL`: a commit survives the process dying, but a power cut or an OS crash can roll back the newest commits (always the newest: the WAL keeps them in order). A rollback of what was recorded *after* an effect leaves the state a crash right after the effect leaves, which recovery already handles. Not so for a transaction *before* an irreversible effect whose rollback would change what the next round does: such a transaction commits at `FULL` (`Store::write_durable`, `Store::try_write_now_durable`; the executor's `Db::write_ahead`), which flushes the WAL, and with it every earlier commit, before the effect starts. SQLite flushes only a commit that changed a page, so each durable commit also counts itself in `meta` (`store.durable_commits`). Such a transaction says so (`Ops::require_durable`, or `Ops::meta_set_ahead` for a record), which refuses (`Error::NotDurable`) at NORMAL, so one written the fast way fails in every test that runs it. They are: the executor's write-ahead records (`exec.pending.*`: recycling, replacing downloads, conflict copies; [§ Executor](#executor-cratesoneup-exec)); its rescue records (`exec.rescue.*`), before a large replacing upload starts (rolled back, an edit the upload went over would be left only in the file's version history); pruning's removal of the Synced rows before the cloud copy goes (rolled back, they would read the cloud's deletion as one to bring to this PC); a move in parts, flushed before the emptied original is removed from OneDrive (rolled back, the Synced row would point at the removed original); a vault move written ahead (`exec.moving.*`, above); the agent's safety window (`safety.window`), saved before each round runs; and a sharing change's intent and activity entry (`sharing_intent`), before the request to OneDrive ([remote-mirror.md § Sharing](remote-mirror.md#sharing)). A durable commit costs about 2 ms (a disk flush) against well under 0.1 ms.

## Activity log (`crates/oneup-store/src/activity.rs`)
The rounds `oneup sync` and `oneupd` share (`sync::Engine::rounds`) append one entry per operation that did something, was skipped or failed: time, outcome, action, path relative to the synced folders, and detail (the line the run prints). Bookkeeping, first-sync pairing and hashing aren't logged. Sync's own events are logged too: safety stops and overflow batches (once each, not every round they stand), trimming and rotation (what was removed for good), rescans, rule changes, problems, and halts. A skip or failure identical to the item's last entry isn't added again, so a file held open for hours doesn't flood the log. The table keeps the latest 50,000 entries (pruned by sequence number on every insert; about 100 B each). Paths compare case-insensitively (`COLLATE NOCASE`, ASCII letters only: a filter, and a collation of our own in the schema would stop other programs from using the file), and a path query covers a folder's contents through an index range. `oneup activity [PATH]` and the settings window read it straight from the database, with or without the agent. It holds names, never contents.

## Dirty folders (`crates/oneup-store/src/dirty.rs`)
Which Synced folders need planning again is recorded **by SQLite triggers** on `local_item`, `remote_item`, `synced_item` and `local_hash`, not by the code that writes those tables. The scanner, observer, mirror and executor all write them. A forgotten "report what you touched" call in any of them would leave a change unplanned, and triggers rule that out by construction, inside the same transaction.
* **Marked:** for every row that appears, disappears or changes, its parent before and after, and the row itself if it is a folder (its contents may now need planning). Removing a Synced row also marks the folder above its parent, since whether an emptied folder can now be deleted is decided when *its* parent is planned. Updates that change no column mark nothing, so echoes of our own writes and repeated delta entries keep a quiet folder quiet. When in doubt a trigger marks: over-marking costs a plan, under-marking would delay a change.
* **Only while syncing:** the local and remote triggers fire only once a Synced tree exists, so a first scan of millions of items pays nothing.
* **Scope:** `dirty_scope()` maps marks (local ID, cloud ID or sid) to Synced folders, with one indexed join per side. A mark that maps to nothing (a new local folder) is dropped. Its parent was marked too, planning the parent creates the folder on the other side, and linking it marks the new Synced row, whose contents the same round plans as it goes (or, for what it leaves, the next round). Each marked folder also brings in the Synced parents of its children that are decided elsewhere: an item moved into a folder not synced yet waits under its *old* folder, with nothing to plan, and what happens next (the new folder created on the other side and linked, or the waiting item renamed or edited) marks only the new folder, whose planning passes over it. Without this, a move into a new folder waited for the next full pass. It costs one indexed lookup per child of a marked folder, which planning that folder reads anyway (`the_scope_never_scans_a_tree`).
* **Clearing:** marks carry an `AUTOINCREMENT` number, and re-marking deletes and re-inserts, so the number is new. A round reads the high-water number *before* planning and clears up to it once it has run (not after a halt, nor when the gate put work off). Marks made during the round, including the executor's own, survive. After a skip (say, a file held open elsewhere, which changes nothing that would mark it again) only the folders of the skipped and failed operations are marked again (`Ops::dirty_clear_except`, `sync::Touched`), so one busy file never makes every round plan the whole tree. Skips that only a change to the item can end don't hold the marks (`sync::settle`): a **refused** item (a hard link, a name Windows can't use), a **taken name** (held by something not synced, such as a symbolic link) and a OneDrive folder that **isn't empty**. Changing the item marks its folder again. `dirty_last()` reads the high-water number, which only grows; the agent uses it to tell new changes from marks waiting for a retry.
* **Checked:** store unit tests, and every end-to-end scenario in `oneup-exec/tests/sync.rs` plans *only* dirty folders and asserts at the end that a full plan finds nothing left.

`oneup sync` plans every folder in its first round, then only dirty ones. `oneupd` does the same only until a round planning every folder has finished with its version (`sync::start_scope`, `meta` `plan.full_pass_version`): a new version may plan differently. Otherwise it starts from the marks, which include what changed while nothing ran (marked as the journal and OneDrive's changes are read at start). Changed rules still plan every folder. A full pass over a 360k-item synced tree takes about 20 s in a release build (`oneup-plan`'s ignored test `plan_speed`); rule matching folds a name's case once per check, not once per pattern (`NameGlob::matches_folded`). The agent logs how long each full plan and the cloud-cleanup walk take (`planned`, `looked for excluded items still in OneDrive`).

## The background agent (`bins/oneup/src/bin/oneupd.rs`)
`oneupd` runs the same rounds as `oneup sync`. The shared code lives in a library target of the `oneup` package (`oneup_app`). It's a separate executable because Windows ignores changes the Cloud Files provider's own executable makes (data-safety invariant 12), so user tools must not be the agent.
* **Waking:** a thread blocks in `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL` with `BytesToWaitFor = 1` (zero CPU) and pings the agent at most every 500 ms. The agent waits 1 s for a burst to finish, runs the observer and checks `dirty_last()`. Only a new mark starts a round, so activity elsewhere on the volume never costs a Graph request.
* **Files that keep changing** (`oneup_app::busy`): the journal watcher reads every record ([§ Journal loss](#journal-loss)) and hands each file written, other than by OneUpDrive itself, to an in-memory `Busy` (at most 4,096 files; those written longest ago and not busy are forgotten first). Records less than a second apart are one change, since one save leaves several. A file changed `busy_changes` times within `busy_window_s` is busy: a round leaves its `Upload` and `Hash` operations out after the gate approved them, keeps its folder's marks like a skipped operation's, and notes it in the activity log (`waiting`, once per stretch). The round still counts as settled; the agent's next wait ends when the earliest held file has gone `busy_quiet_s` without a change, or `busy_max_s` after it became busy, whichever comes first, so a file that never stops is still sent about every `busy_max_s`. It only delays uploads: nothing is deleted or overwritten, and the executor still checks the file's state before sending it. The safety gate sees the held operations in the round that approved them and again when they run. `oneup sync` doesn't hold anything.
* **Push** (`oneup-graph/src/push.rs`): a task asks for `subscriptions/socketIo` and speaks the needed subset of Engine.IO v4 / Socket.IO v5 over `tokio-tungstenite`. TLS uses rustls with Windows' certificate store (`rustls-native-certs`). It joins the namespace, answers the server's pings (every 30 s), and treats a server that stays silent past `pingInterval + pingTimeout` as dead. The `notificationUrl` doesn't match Graph's documented shape on OneDrive Personal, so it's parsed generically (path → namespace, query → passthrough). A notification only pings the agent. After 2 s the agent runs a round, whose delta read finds the change. A dropped channel also pings, because a notification may have been missed. Reconnects back off from 5 s to 10 min. The `notificationUrl` holds a token, so it's never logged; `Endpoint`'s `Debug` and every error message leave it out. While push is live, the timed delta check runs every 10 minutes as a safety net; otherwise it runs every `--poll-seconds` (default 60). `--no-push` turns push off. With a sync interval (`oneup_app::pace`, `[sync] interval_minutes`), the agent's wait no longer ends on a journal change (it still reads the journal, so the Local tree and the dirty marks stay current) or, unless `keep_push`, on a notification; the push channel is closed, and the next pass runs when the interval is up. The user's calls (sync now, answers, resume) and a pass that hit `MAX_ROUNDS` still run at once; retries and held uploads wait for the next pass.
* **Control** ([control-api.md](control-api.md)): a named pipe only the user can open. Calls change in-memory state (`oneup_app::control`) and wake the loop. While both directions are paused, no rounds run.
* **Pausing mid-round:** the gate sees the pause only when a round is planned, and a round can run for tens of minutes (thousands of deletions under Graph's throttling). So the control state also keeps the pause in two atomic flags (`control::LivePause`), set the moment a pause, a resume or the agent's own pause (metered connection, battery saver, full screen, quiet hours; looked at again every 30 s while rounds run) changes it. The executor asks a per-operation check before each operation (`Executor::run_checked`; `LivePause::round_check` is the agent's). It refuses an operation that changes a paused side and, for the rest of the round, every later one changing that side, even if it resumes meanwhile, since they may depend on one that didn't run. Bookkeeping always runs. Refused operations go in `Report::not_run`: not skipped, not failed, so they trigger no retry back-off and aren't counted in the safety window; the round keeps all its dirty marks, as when the gate puts work off, so they're planned again on resume. A batch is cut before the first refused operation. A download under way is asked again at every write of its data (`Stoppable`) and stopped once refused: it was only staged, and the staging file goes with it. Everything else that started finishes, including an upload (its commit is never cut off) and a batch. Hydration (a program opening an online-only file) isn't a sync operation and isn't paused: the user asked for that file.
* **Overflow:** a held version-store batch doesn't stop the agent. It's shown once per fingerprint (and again when its outcome changes), everything else keeps syncing, and it takes `oneup keep/discard CODE`, or `--keep/--discard` at start.
* **Outcomes:** settled (refused items, taken names and non-empty folders count as settled, above) → trim the version store (not while changes to this PC are paused), run the placement pass, wait. Other skips → retry after 30 s, doubling to 15 min (capped at the timed check, whose round would run them anyway). Failures wait item by item (below), so they don't hold the rounds open. A skip because the item changed meanwhile gets a new round at once, but after 3 rounds in a row that did nothing else it's retried like the others, so one that a new round doesn't clear can't keep asking OneDrive for changes. Still busy after 20 rounds → again in 5 s. A **safety stop** changes nothing and waits for `oneup approve CODE`. An executor **halt** (`sync::Halted`: identity check failed) or an observer **NeedsRescan** end the agent, except journal loss (below), saving the reason for the tray ([control-api.md § Problems](control-api.md#problems)). A busy database is retried after 10 s without showing an error. Every other error (network, service) restarts the round from the database after 60 s, doubling to 30 min; the pause starts over at 60 s when the failed attempt had finished a sequence of rounds or ran longer than 30 min.
* **Failed operations back off, item by item** (`oneup_app::backoff`, `oneup_store::retry`, schema v17): a failed operation's folder keeps its marks, so without a record of when to try again every round (any change in the folder, every timed check) ran it again at once. Each failure records, for the item the operation acts on (its local file ID, or its cloud ID for what comes from OneDrive), a hash of the operation as planned (`version`: its `Debug` form, so the local stamp and cloud eTag it carries are in it), the failures in a row, the error, and when it may go again: 1 min after the first, doubling, at most 1 h. A round leaves out an approved operation whose record has the same version and whose time hasn't come, after the gate (like a held busy file), keeps its folder's marks, and sets `Outcome::held_until`, so the agent's wait ends then; the other items in the folder go. A different plan for the item (it changed on either side) isn't held, and its first failure starts over at 1 min. Success removes the record; records not looked at for a day after their time (the item went away) are dropped at the end of each round. Lookups are by key, and none at all while the table is empty; the count and earliest time for `oneup status` (the `retrying` field) and the cleanup use the `until_ms` index. `oneup explain PATH` prints the item's record. Bookkeeping (`Pair`, `Record`, `Forget`, `Hold`) has no item and keeps the old round-level retry. `oneup sync` doesn't back off.
* **OneDrive full:** Graph's 507, or a refusal with the code `quotaLimitReached` or `insufficientStorage`, is `CloudError::Full`, which the executor reports as `Skip::CloudFull`, not a failure. The Graph client doesn't send a 507 again (another try a moment later finds the same, and retried it reached the caller only as "gave up", without its code). Once an upload or a new folder is refused, alone or in a batch, the executor skips the round's remaining uploads and new folders without sending them (a batch is cut before the first of them, as for a pause). The engine (`sync::Full`) then holds `Upload` and `MkdirRemote` operations after the gate in later rounds, keeping their marks; downloads and local work go on, and the rounds settle. It reads `quota.remaining` of the pair's drive (`Graph::remaining`, one small GET) when the next sequence of rounds starts, at most every 60 s, so at the agent's ordinary wake-ups (changes, notifications, the timed check), never on a timer of its own. Uploads go again once the room left grew, or an hour after the last refusal whatever it reads (a drive someone else owns doesn't report it). The status shows the `cloud-full` problem "OneDrive is full" meanwhile (`problem::cloud_full`, `Control::set_cloud_full`, shown while no other problem is), and the activity log notes when uploads stop and resume. In memory only: a restart tries uploads again.
* **Safety window:** the gate's breakers count a round's batch *plus* the mass-sensitive operations the agent carried out in the last 15 minutes (`oneup_gate::Recent`, `Context::recent` of `review_in`), and the content guard its suspicious uploads the same way. Otherwise a mass deletion trickling in over many wake-ups could pass in batches under the limits. The window (`oneup_app::safetywindow`) is kept in the state store (`meta` `safety.window`: counts per minute), read when the agent starts, so a restart of the agent or the PC doesn't reset it. **It never counts less than what ran:** before each round changes anything, the agent records the window with what the round may carry out reserved (`sync::Keep`, `reserved`), and again with what it did; a round whose record can't be written doesn't run, and an attempt that can't save the window fails and is retried. A saved window that can't be read in full (anything but minutes exactly as written, or a count above `UNREADABLE`, which no real count reaches) counts as full for 15 minutes (`UNREADABLE` per count), so every deletion, overwrite or move waits for approval meanwhile; the agent says so in its output and the activity log. None saved is an empty window. It's kept by the minute: a minute's counts go once the last moment of that minute is 15 minutes old, so nothing is forgotten early, nothing lasts more than a minute longer however busy the agent is, and at most 16 minutes are kept. Times are wall-clock; a minute later than now (the clock was set back, at start or while running) is counted as now's on every look. Across retries after errors the agent keeps it in memory too: an operation counts as soon as its round ran it, even if that call of `rounds` then fails, and the next attempt saves it before anything else.
* **Database:** at normal priority (`[agent] background = false`), the agent's own connection maps up to four times its page cache of the file into memory (`Store::map_memory`, so `minimal` 16 MiB, `balanced` 64 MiB, `performance` 256 MiB): a page read is then a memory access instead of a system call, and a walk of a large tree measured no read calls and a fifth less time. At background priority (the default) it doesn't map: Windows keeps a background process's working set small, so mapped pages were trimmed and faulted back in one at a time (a full pass of a 340k-item tree measured 372 s and 220 million page faults, against 47 s reading normally). Other connections (the tray, the settings window, the CLI, the agent's hydration service and program tracker) don't map: Windows can't shrink a file another process has mapped. A disk error in a mapped page ends the agent instead of failing a query. At start, before its other connections open, the agent compacts a database that is mostly free pages (`Space::worth_compacting`: at least 64 MiB and a quarter of the file free), which deleted rows leave behind, if the disk has room for twice the database's files (SQLite's documented need; `[agent] compact_database`, default on; `oneup settings --compact-database`). The activity log says how large the file was before and after. If another connection was reading, the rewrite stays in the WAL and the file shrinks at a later checkpoint; if another program had it mapped, the file keeps its size and SQLite reuses the space. A failure is retried at the next start.
* **Threads:** `oneupd` runs tokio with 2 workers (default: one per core): about 10 idle threads instead of 44 on a 32-core PC, and less private memory, at no cost to a round.
* **One process per data folder:** `sync.lock` in the data folder, opened with no sharing. `oneup sync/versions` take it too. Windows releases it when the process ends, however it ends.
* **Windows' close, sign-out, shutdown and Ctrl+Break** are logged and end the agent cleanly, so a stop can always be told apart from a crash.
* **Starting and stopping** (`bins/oneup/src/launch.rs`): `oneup start` launches `oneupd.exe` from its own folder with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` (so the terminal's Ctrl+C and closing don't reach it), outside the caller's job where allowed, stdin null and stdout/stderr to `oneupd.log` in the data folder (the previous run's kept as `oneupd.log.1`), and returns once the control pipe answers, or shows the log if the agent ended. Before spawning, `oneup` clears the inherit flag on its own standard handles (`oneup_sys::inherit`): Windows gives a child *every* inheritable handle, so the agent would otherwise hold the terminal's output pipe and a caller reading that pipe would wait for the agent to end. `oneup stop` is the `stop` control call: the loop finishes its round and exits, like Ctrl+C.
* **Start at sign-in** is opt-in (`oneup autostart on|off`, or a setup choice): one `REG_SZ` value per data folder, named `OneUpDrive agent (<data folder name>)`, under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. Per user, no admin rights, and visible and switchable in Task Manager's Startup apps. Chosen over a scheduled task because it needs no COM/XML and Windows already lists it for the user. The value runs `oneupd-start.exe`, a Windows-subsystem launcher (no console flashes) that does nothing if the agent answers already, and otherwise calls the same `start_agent`; a launch failure goes to `oneupd.log`. Two launchers racing are harmless: the second agent can't take `sync.lock` and ends.
* **Measured** (test account, debug build): a local edit is uploaded within seconds; a cloud change arrives about 30 s after it was made with push (OneDrive's notification takes most of that), or at the next timed check without. Idle cost is about 0.1 s of CPU per minute (the delta checks plus journal wake-ups from other programs writing to the volume), with a few MiB of private memory.

### Journal loss
When `catch_up` finds the journal wrapped or replaced (expected after the PC or the agent was off for a while: a volume's journal can hold as little as tens of MiB of history), `sync::observe` (used by `oneupd` and `oneup sync`) rescans the folder at once instead of stopping. Only if `Scan::open` reports `Replaced(Finished)`, i.e. the same folder (volume serial + folder ID) with the same rules; anything else halts. The Synced tree and recorded evidence are untouched; the Local tree is rebuilt, so a synced item the rescan doesn't find is **Missing** and held, never deleted. The rescan takes the journal position first and catches up afterwards, and it adds a `rescan` note to the activity log.

A loss also happens while the agent runs. The observer reads the journal only between rounds. During a long round, a burst of disk activity can wrap the journal first: removing a build tree or a dependency folder writes hundreds of thousands of records, and Windows' default journal is 32 MiB. Synced items deleted in that window would then be held, not deleted in OneDrive. The journal watcher (`oneupd`'s `watch_journal`) reads every record as it's written (`oneup_local::observe::JournalTail`), starting from the observer's position so nothing between the observer's last read and the watcher's start goes unread, and without pausing while records wait. It keeps the delete records of items in the Local or the Synced tree (`SeenDeletes`; a file just uploaded is in the Local tree before its Synced row is written). It checks them on its own connection with indexed lookups, keeps at most 2^18 (32 bytes each), and forgets them once the observer has read past them, refusing them afterwards. After a rescan, each one whose item the rescan didn't find becomes evidence (`note_seen_deletes`), and the `rescan` note gives the count. These are the same USN delete records the observer would have applied (invariant 3). Only Synced items get evidence, and an item the rescan finds is left alone. Records from a journal since replaced count too: file IDs belong to the volume. If the journal wraps past the watcher anyway, it goes on from the oldest record kept, and if it was replaced, from the new journal's oldest record; deletions in what was lost are held as before. If reading fails, it tries again after 1 s, doubling to 5 min, from where it was. The program tracker and busy files only get records written after the watcher started.

`a_journal_lost_mid_round_never_invents_or_loses_a_deletion` (`oneup-exec/tests/sync.rs`) loses the journal while a round runs, after a file and a folder tree were deleted, a file moved out of the folder, one moved out and deleted there, a file saved by renaming a new one over it, one renamed, and one deleted and made again. With the watcher's records, exactly the deleted items get evidence and are deleted in OneDrive; the save and the re-made file stay edits of their items, and the moved-out file is held. Without them, nothing is deleted in OneDrive. The simulation loses the journal at random too ([below](#simulation-cratesoneup-synctestssimrs)).

## Simulation (`crates/oneup-sync/tests/sim.rs`)
An in-memory model of a local disk (file IDs, atomic saves, recycle bin, version store) and of OneDrive (item IDs, eTags, version history, recycle bin). A seeded scheduler interleaves random user edits on both sides with sync rounds, including **between** an operation being planned and executed, so preconditions fail realistically. The executor enforces preconditions as the real one must. Checked:
1. **Convergence:** once users stop, a bounded number of rounds makes both sides identical (paths, kinds, contents) with nothing held, and the Synced tree matches both.
2. **No lost edits:** every content version that was new or changed when users stopped is present on **both** sides at the end.
3. **Invariant 1:** whenever local content is replaced or recycled, the cloud already holds that content (current version or history).
4. **The store plans like the model:** every round is also planned from an in-memory SQLite store holding a copy of the world (rows, Synced tree, hashes, evidence written the way production writes them). The two plans must be identical, and the store's invariants must hold.
5. **Invariant 3:** nothing is deleted in the cloud without evidence of its deletion here: the operation's Synced row links that cloud item and a local item noted deleted.
6. **No loop in the Synced tree:** after every round, every Synced row reaches the top.
7. **Rewinding** (`rewinding_a_folder_reproduces_it_and_a_rewind_can_be_rewound`): the world keeps the Synced history as the store's triggers do; after random activity and settling, a folder (the whole drive or one folder there) is rewound to a moment, approved whole and carried out round by round as the agent does, and must be as it was then on both sides (anything the rewind left alone, its name taken by something outside the folder, aside); then the whole drive is rewound to just before the rewind and must be exactly as it was. The plans read only what changed since the moment and the records whose item differs from them on either side, so the check also proves that nothing else needs reading. Every plan is also made from a store holding the world's history, and must be identical.

Two runs add faults:
* **Delta lag** (`a_lagging_listing_converges_without_losing_edits`): the planner reads a mirror of OneDrive that our own operations write as they run (as the executor records the items its requests return), and that each round's listing overwrites with the cloud as it was at the listing before, a round or more ago. So a listing can be older than what an upload, move or deletion of ours just saw. Plans made from it fail their eTags or the move check (`Cloud::is_at`, modelled), and once the listing catches up, checks 1 to 5 hold.
* **Journal loss** (`journal_losses_never_invent_or_lose_a_deletion`): now and then, while idle or while a round runs, the change journal loses users' deletions not read yet. Those the journal watcher kept are evidence after the rescan; the rest read as missing and are held. Held items hold up what depends on them (an item moved into a held folder waits, and so does an edit of it), so the run checks that no edit is lost and that nothing is deleted in the cloud without evidence; then the user answers for what's missing (deleted here, which is evidence), and checks 1 to 5 hold.

Seeds: `SIM_SEEDS=N` (default 200; 50 for the two fault runs, which take longer per seed), `SIM_SEED_FROM=k` to start at seed `k` (to split a long run), `SIM_SEED=n` to replay one, `SIM_DEBUG=1` to print every round's operations and the final state, `SIM_STORE=0` to skip check 4 on long runs (building a database every round makes runs about 200× slower: about 1,000 seeds a second per core in a release build without it, 5 with it). Each seed is 25 rounds of random edits on both sides, using a small set of names with case variants so that collisions are frequent, followed by settling. The same simulation covers one-way backups (`backups_send_this_pc_and_never_change_it`). CI runs the default seeds of each; the nightly run (`.github/workflows/nightly.yml`) runs 4 million of each without check 4 and 20,000 with it, a new window of seeds every night, and opens an issue naming any failing seed.

Scenario tests pin the headline behaviours: first-sync adoption (identical files paired, different ones both kept); an atomic save updates the same cloud item (version history continues); a swap of two names renames rather than re-uploads; an edit beats a deletion; "missing without evidence" is held, never deleted; a record is forgotten only when both sides are deleted; a missing sync folder halts everything; a folder deleted in the cloud survives for a new local file; folders moved into each other don't loop; a folder is never recorded below itself in the Synced tree when the other folder's move is refused; a listing behind the cloud never undoes a rename here.

## End-to-end tests (`crates/oneup-exec/tests/sync.rs`)
A real temp folder goes through the real scanner, observer, planner, gate, effects and executor, with a fake cloud that enforces eTags and name conflicts. Rounds run until both sides are identical and a round changes nothing, and the store's invariants must hold. Besides the first sync, edits, deletions, renames, conflicts, the version store, busy files and parking, the `everyday_` tests take one scenario per thing people do in File Explorer and on the web, and the `held_items_`/`chosen_` tests carry out each answer for a held item, with its refusals (still here, folder gone too, names taken or refused, a stamp changed after the choice) and a batch that trips the breaker. Faults: the fake cloud's listing can lag behind it (`Fake::lag`, `a_listing_behind_the_cloud_loses_nothing`, `a_listing_behind_our_own_rename_never_undoes_a_rename_here`), a hook runs what a user does while a round is under way, and `Sync::lose_journal` runs the rescan that follows a journal loss. Recovery: a rewind (nothing runs before the approval; a file changed after the preview is left alone; edits not synced yet set aside; a large one takes one approval; one whose OneDrive recycle bin was emptied ends with what it could do; a crash at any of its points loses nothing), restoring a kept copy, a OneDrive version and a deleted item, and answering a conflict both ways.

## Limits
* Under delta lag, a change the listing shows from before one of ours plans work that is refused (downloads and cloud changes by their eTags, moves here by the move check) until the next listing settles it. An edit here made while the listing is still behind can be planned as a conflict, which keeps both copies.
* The Files On-Demand effects (replacing or recycling a placeholder, which copies or reverts in a second step) have no crash points: their end-to-end runs need a registered sync root, which CI doesn't have.
* OneDrive's 400-character path limit isn't parked (checking it needs the whole path). An upload that exceeds it fails and is reported.
* Folders another sync app manages are refused (Files On-Demand is OneUpDrive's own: [files-on-demand.md](files-on-demand.md)).
