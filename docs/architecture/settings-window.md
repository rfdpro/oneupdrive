# The settings window and its Files page

The settings window is where every setting can be changed, and its Files page, a tree of each synced folder, is the main way to manage what syncs. User guide: [The settings window](../user-guide/settings-window.md).

## Shape
`oneup-settings` hosts one page (`bins/oneup/src/settings_ui.html`) in WebView2. The page asks, the program answers (`handle` in `oneup-settings.rs`); every change goes through the same functions as the command line (`settingsapi`, `config`, `filetree`, `vaultpair`, `pairs`), with the same checks. A request with `root` (`main`, `pair:<name>`, `vault:<name>`) works on that root's own data folder (`root_dir`), so the same requests (rules, space, placement, explain, Files On-Demand) apply per folder pair without being written twice.

The window is one per data folder. When it's already open, a new `oneup-settings` process passes the page (and item) to it before exiting: `webview::focus_existing` sends a `WM_COPYDATA` (tagged `OUPG`) with `page\0item`, and the window hands the page `{"event":"goto","page":…,"item":…}`. The page name keeps only ASCII lowercase letters and the item is JSON-escaped (with `<`), so whatever sends one can't put more than that into the page.

## The file tree (`oneup_app::filetree`)
* **`list(data_dir, rel, steps)`**: a folder's items from the database, on this PC (Local tree) and in OneDrive (Remote tree under the pair's root, found through the root's Synced link), folders first, at most 2,000. An item with a Synced row goes only with its partner, and stands alone when the partner isn't in this folder (moved elsewhere on one side, or gone), so a move across folders never pairs it with an unrelated item of the same name; the others go with one spelled the same, else one whose name folds alike (`oneup_sync::fold`); names on one side that fold alike each get a row. Each item carries its rows' IDs (`local_id`, `remote_id`), and the page sends them back for each folder on the way down (`steps`), so a folder is opened by its IDs, never by a name that another folder's name folds alike to; by name (exact spelling, else the only one that folds alike) only without them (`oneup dev-tree`). `tree_sizes` answers by the same IDs. Each item's state comes from the rule set the agent uses (config rules and presets, folders synced on their own, folders left to the OneDrive app, and every `.oneupignore` on the way down, as `oneup explain` builds it) plus whether it has a Synced row; Files On-Demand placement comes from the file's attributes (placeholders exposed first). Never reads content. A left-out folder is one opaque row in both trees, so its contents aren't listed (`untracked`).
* **`find(data_dir, needle)`**: names containing the text, on this PC and in OneDrive (`Store::local_find` / `remote_find`, a `LIKE` scan of names: fine for a search someone types, not for anything that runs by itself).
* **Changing what syncs** edits `config.toml`, as `oneup rules` does:
  * `set_sync(…, on=false)` adds the rule naming exactly that item (`/path` or `/path/`, `[` written `[[]`, since rules have no escapes and Windows names can't hold `*` or `?`);
  * `set_sync(…, on=true)` removes that rule, or, when a preset or a broader rule of yours leaves it out, adds the exception `!/path`;
  * a `.oneupignore` rule, a pause, a separate pair or the OneDrive app's folders are reported instead of overridden, and so is an item inside a left-out folder (gitignore semantics: nothing inside an excluded folder can be re-included);
  * each change is checked against the rebuilt rule set and undone if it didn't have the intended effect;
  * `set_paused` edits `[pause] folders`, `set_order` the item's own entry in `[priority] first`/`last`.
* The agent is nudged after each change; it applies rule changes without a rescan ([rules.md](rules.md#changing-rules-without-a-rescan)).
* **Checkboxes** ([rules.md § Choosing in the file tree](rules.md#choosing-in-the-file-tree)): `list` gives each item `partial` (a folder a rule inside leaves partly out). Unticking, the menu's **Exclude…** and the details switch open one dialog fed by `tree_preview` (by the row's IDs); only its **Exclude** writes the rule (and the `cloud_copies` mode, if changed there). Space toggles the focused row's box.
* **Exclude view**: **Suggestions** (`rule_suggestions`, [rules.md § Suggestions](rules.md#suggestions)) with **Exclude** opening the same dialog by path.

## The page
* **The agent's status** heads every page as a light and a word; selecting it opens a menu with the detail and the controls (pause, sync now, start/stop). A problem shows as a card with **Retry now**, **Open log** and **Copy details** ([control-api.md § Problems](control-api.md#problems)). The navigation runs Files, Activity, Apps, then the settings: General, Accounts, Office, Safety, Network, About. `main` keeps its scroll-bar gutter, so a page doesn't shift when it needs one.
* **Tabs** for the roots (from `roots`), and an **Add** menu (a native popover) whose items open dialogs for `pair_add`, `pair_add_known`, `pair_add_shared`, `vault_create` and `vault_add`.
* **Views**: All files (the tree, loaded a folder at a time, keyboard navigable, selection follows focus, sortable by name, status or size; a folder's size is the total of every file inside it, from `tree_sizes`: `Store::local_folder_totals` / `remote_folder_totals`, one recursive query over the folder's subtree, asked for after the listing), Exclude (presets, your rules and exceptions, paused folders with **Pause a folder…**, rule files, the rules as text, and excluded items still in OneDrive), and search results.
* **Right-click menu** on tree items (also the menu key and Shift+F10): open, show in Explorer, exclude / sync again, pause / resume, keep / free, sync this first, links, versions, why. **Share** sits beside the item's name and shows its two links on hover or focus.
* **Details panel**: sections that open and close (`<details>`); Versions, Why and Recent activity load when opened. With nothing selected, the root's own settings: paths, direction, Files On-Demand, free-space policy, start/stop/remove, and for vaults lock/unlock, Windows Hello, recovery key, password.
* **Kept on this PC** lists the version store with **Restore** (`kept`, `kept_restore`, as `oneup versions`/`restore`; the agent is stopped around a restore).
* **Stopping a folder's sync** (`remove_preview`, then `pair_remove`, `vault_remove` or `main_unpair`): a dialog says what stays where and how many files would leave because they're online-only (`Store::local_online_only`, from stored attributes), and offers to download them first (`on_demand` off, which checks the space) before removing. `pairs::unpair` releases the main folder and forgets its pairing (its database), keeping the sign-in, settings and other pairs.
* `--page NAME` opens a page; `--page item --item PATH` selects that file and opens its Versions (Explorer's Version history and Share commands), `itemwhy` and `itemactivity` its Why and Recent activity. Old page names (`folders`, `syncing`, `storage`, `vaults`) open the Files page.

## The Activity page
At the top, while anything needs the user, a card lists it (`problems`, as `oneup problems` builds it: [control-api.md § The problems list](control-api.md#the-problems-list)), read each time the page opens.

Everything the tray and Explorer used to show in a console or Notepad opens here (page id `lists`), one tab each, selected by `launch::start_settings_on(dir, page)` with `--page activity`, `unsynced`, `excluded` or `stops`:
* **Recent**: `activity_log` (`settingsapi::activity`, up to 20,000 entries, more on request);
* **Sync failures**: `unsynced` (`settingsapi::unsynced`: the record, each item's kind, its choices from `resolve::choices` (no restore or upload for an item inside a folder listed for the same reason: that folder's answer covers it), whether it's on this PC, and the answer queued for it); grouped by kind (the reason once, in the group's heading; for items gone from one side, one inside a folder listed for the same reason is indented under it, named from there, without buttons: the folder's answer covers it), with a button per choice, **all N** buttons per kind while the whole kind is shown (`--all --expect N`, refused if the list changed), **Contents** for a folder held as not empty (`unsynced_inside`, from the trees, nothing listed on disk) and **Show**. Each button runs `oneup unsynced resolve PATH --CHOICE --yes` (`unsynced_resolve`; the command does nothing without `--yes`, `--exclude` aside); the page asks first for deletions (naming the items and where they go), for a choice covering many items, and for a new name. Each listed item carries its `subject` (`resolve::subject`: its Synced record, or for a name to change its file ID, size and last-write time); one without (nothing to bind an answer to) is offered only Exclude. Every answer but an exclusion goes through `unsynced_preview` (`resolve::prepare`, as the command works it out), which requires the subject for a single item and refuses if the item at that path is another than was listed, or can't be told. The preview gives how many items the choice concerns, folders' contents included, and a code for exactly those answers and their fingerprints, passed on as `--expect CODE`, so the command refuses if anything changed between the dialog and the click. **Contents** shows the first 200 items by name and how many in all (`count(*)` and `ORDER BY name LIMIT`);
* **Excluded in OneDrive**: `cloud_copies` (`prune::candidates` without the kept ones, then `prune::counted`, as `oneup cloud prune` lists them; read-only, and asked for only when the tab opens, since it calls Graph for unlisted folders);
* **Safety stops**: `stops` (`stoplist::read`, which parses a stop's text file back into action, path, target and note, filtered and capped where it's read: a stop's list can have 100,000 lines). The text files stay: `oneup approve` names them.

## Setting up and moving over from the OneDrive app
First run walks through signing in (hidden sign-in that continues by itself, with Microsoft's account picker), a suggested new folder or an existing one, Files On-Demand, start at sign-in, and a preview before anything changes. Setup shows who's signed in, with **Sign out, to use another account**.

**Move over** is offered when `moveover::app()` finds the OneDrive app's folder (the snapshot's `app_folder`: the folder, whether a sync root still manages it, Windows' own folders inside it). The window runs the read-only steps as separate `oneup` runs so it can say which is under way: `move_scan` (`oneup scan <folder> --exclude <preset>`), `move_list` (`oneup mirror`), `move_check` (`oneup migrate check --json`, which also records the app's choices while it manages the folder, `crate::carryover`). Unlinking is the person's; the page polls `move_state` every 3 s and notes if Windows moved Desktop, Documents or Pictures out of the folder meanwhile. When the app's unlinking stalls (`move_state`'s `stalled`), the page shows **Finish unlinking**, which runs `move_fix` once per step (`oneup migrate finish-unlink --step restart|reset|release --yes --json`; the result is the last JSON line printed), the reset skipped while a work or school account is set up in the app. One confirmation covers the three steps; **Finish it now** runs only `release`. Releasing can take many minutes on a big folder, and `move_fix` waits for it. Preview and Start stay disabled until the app is unlinked; then the pairing is the ordinary `oneup sync <folder> --remote / --pair-only`, whose first scan, content matching (`Op::Hash` for same-size files) and carry-over do the adopting ([files-on-demand.md § Moving over](files-on-demand.md#moving-over-from-the-onedrive-app)).

**Shortcuts** (General, and opened after setup when there are any): `shortcuts`, `shortcuts_fix` (with the links the page listed, re-found first) and `shortcuts_undo`, in-process calls to `oneup_app::shortcuts`, which `oneup shortcuts [--fix|--undo]` uses too. Two kinds of broken shortcut: (1) into the OneDrive app's folder after setting up in a new one: the app's folders are the one recorded when the pair was made (`sync.app_folder`, since the app's own setting disappears when it is unlinked), the app's setting now and `%USERPROFILE%\OneDrive`, never one of ours, and each pair of the account's own drive maps `<app folder>\<remote path>` to its local folder (longest match wins); (2) into one of our folders but saved through the OneDrive app's shell namespace (`{018D5C66-4533-4307-9B53-224DE2ED1FE6}`), gone once the app is unlinked: `IShellLinkW::GetPath` names no target, so the path comes from the file's LinkInfo (`shortcuts::stored_path`, MS-SHLLINK §2.3), and saving it again with the same path rebuilds the item chain. The second kind is what moving over leaves. It walks the Desktop, the Start menu and the taskbar's pinned folder, bounded in depth and entries, reading `.lnk` files with `IShellLinkW` (`oneup_sys::shortcut`; `Resolve` is never called, so targets aren't touched). It skips placeholders, synced folders (every pair's folder, shared folders and vaults included, and any sync root, because a change there is a change to user content that would sync; a pair or vault that can't be read, by strict listings, stops the search) and shortcuts whose new target doesn't exist. An ANSI-only LinkInfo path outside ASCII is refused, since its code page isn't in the file. Only dead links into pairs of the account's own drive are rebuilt (a shared folder or a vault never was in the app's folder). One change at a time (`shortcuts\lock`, opened exclusively); the folders we sync are read again under it, before fixing or undoing. Whether a shortcut changed is told by its contents (SHA-256), not its size and time. Fixing re-checks each shortcut's contents and target, writes its copy to a new `<data folder>\shortcuts\<ms>\` and its entry to `fixed.json`, builds the new shortcut in a temporary file beside it (`retarget_to`), notes the new one's fingerprint, and, if the shortcut's contents are still as found, swaps it in with `ReplaceFileW`, which keeps its permissions and other streams. Our own files are written through a temporary file and `MoveFileExW` with write-through. If `ReplaceFileW` fails partway with the shortcut gone, the new one takes its name unless something else has (or stays under its temporary name): it is never deleted then. A shortcut deleted while it's being fixed stays deleted. The new target is checked again just before the swap. Undo puts a copy back the same way, only over exactly the shortcut the fix made (by fingerprint; an earlier version's entries by size and time). An entry is settled only when someone changed or removed the shortcut since, or it was never changed; any other failure leaves it for the next undo. Only a batch without a list is passed over; a list that can't be read stops undo rather than undo an older batch. Quick Access and programs' recent-file lists would be further places.

## The Search page
`search` and `search_onedrive`, in-process calls to `oneup_app::search` ([search.md](search.md)): names from the index as the person types (150 ms after the last key), OneDrive's search inside files only on **Search** or Enter, and only when `[search] onedrive` is on (the handler checks the setting itself, so nothing reaches Microsoft without it). While the index is still being built, `search` posts `search_build` events with the count so far. Results reuse the Files page's flat rows; **Open** and **Show** are `open_path` and `reveal` on the item's path on this PC, **Sync this first** is `sync_first`. The settings save as section `search`, which also tells the tray (a named event) to take up a new hotkey. `--page find` opens the page (the tray's **Search** entry and the hotkey).

## Parity with the command line
**Hooks** (General): `hooks` (`oneup_app::hooks::json`: each `[[hook]]` checked as the agent checks it, with the reason it's refused if it is), `hook_enable` (name, on) and `hooks_pause` (on), which write `config.toml` (`config::set_hook_enabled`, `set_hooks_paused`) and nudge the agent with `sync_now`, after which it reads the hooks again ([hooks.md](hooks.md)).

Every window action has a CLI equivalent (ticking and unticking = `oneup rules --include-path/--exclude-path`, Suggestions = `oneup rules --suggest`, Recent activity = `oneup activity`, Hooks = `oneup hooks`, Kept on this PC = `oneup versions`/`restore`, Sync this first = `oneup sync-now PATH`, Sign out/Sign in = `oneup logout`/`login`, shared folders = `oneup login --shared-folders`, updates = `oneup updates`, accounts = `oneup accounts`, Shortcuts = `oneup shortcuts`, Sync failures = `oneup unsynced resolve`, Search = `oneup find`, its settings = `oneup search`). CLI-only by design: safety-stop answers (`oneup approve`; the tray's dialogs in the GUI), `verify`, `diagnose`, `plan`, `observe` and the developer commands.

## Language
The page's text is looked up in the user's language's catalogue (`tr()`, and its own markup when it loads), and its numbers and dates use the regional format the program passes in: [localisation.md](localisation.md).

## Accessibility
Target: WCAG 2.2 AA, by keyboard and with a screen reader (Narrator, NVDA), in light, dark and Windows' contrast themes. `bins/oneup/tests/settings_a11y.rs` checks the page headless, as text, in `cargo test`: every control in the markup and every one the script makes (`el("input", …)` and the like) has a name, dialogs are named by their headings, icons are hidden from screen readers or described, ids are unique and the ids ARIA attributes name exist, the tab lists, tree and live regions have their roles, the details panel isn't a live region, and the palette's pairs meet 4.5:1 (text) and 3:1 (field borders, focus ring, status dots) in light and dark; the CSS must answer `prefers-color-scheme`, `forced-colors` and `prefers-reduced-motion`, and no focus style may drop the outline. axe-core (MPL-2.0) isn't on the licence list, hence a check of our own. `bins/oneup/tests/settings_keyboard.rs` runs the page in headless Edge with a made-up host and presses keys: focus stays on a tree row when the tree redraws, the arrows, Home, End and letters move it, selection and `aria-checked` follow, Space opens the exclude preview, menus and dialogs give focus back (to the item's new row if the tree redrew meanwhile), the folder tabs and views keep one tab stop and choose with the arrows, and a program in the Apps table opens from the keyboard and keeps focus across reloads. Dialogs give focus back as soon as the script closes them, not only on their `close` event, which Chrome fires with the next frame.

**Checked and fixed:**
* *Keyboard.* The tree lost focus whenever it redrew (a row's focus selects it, which redraws): arrow keys did nothing after the first row was focused or a folder opened. It now gives focus back to the same item. Typing a letter goes to the next item starting with it. The folder tabs and the views are tab lists with one tab stop and Left, Right, Home and End. Every menu (status, Add, right-click) takes Up, Down, Home and End; Esc closes menus and dialogs, and both give focus back where it was, to the item's new row if the tree redrew meanwhile. **Share**'s links open with Enter and are plain buttons, not a menu that couldn't be arrowed through. A program in the Apps table opens its files from the keyboard (its name is a button with `aria-expanded`; the table keeps focus across its 15-second reload). Focus in menus was a 4.5 % tint; it's an outline now.
* *Screen readers.* Each tree item says its name, status and size, and its box as `aria-checked` (true, false, mixed); the "Looking…" and "N more" lines are disabled items. The tree region is a tree only while it lists items (search results and the Exclude view are a region). Sort buttons say the order in words (the arrow is hidden); `aria-sort` was on a button, where it means nothing. On/off switches are `role=switch`. Every field has a name (the settings pages' number and text fields had none; placeholders no longer stand in for labels). Dialogs are named by their headings (`<dialog>` with `showModal` gives `aria-modal`, the focus trap and Esc). Icons are `aria-hidden`. The details panel was a live region, so every arrow key in the tree read the whole panel out; it's a named region now. What changes by itself is announced politely: the agent's status word, list and search summaries, the setup and dialogs' progress lines, shortcut search, update checks, and the toast.
* *Contrast.* Light mode's green, amber and red text were 3.9–4.4:1 on the panels and tags: darkened to 4.5:1 or more. Fields' borders were 1.5:1: a `--field` colour at 3:1. White on the red count badge was 2.2:1 in dark mode: `--bad-ink`. In a contrast theme (`forced-colors`), the selected tree row, the current page, the chosen tab and pressed buttons use `Highlight`, switches draw their track and knob in system colours, status dots get an outline, and the Apps chart keeps its colours. Reduced motion turns off transitions and the problem card's flash.
* *Zoom.* Below 860 px wide (a narrow window, or 200 % zoom), the details panel goes under the tree.

**The tray** uses Windows' own menu, notifications, message boxes and task dialogs, which Narrator reads and the keyboard reaches (Win+B, the arrow keys to the icon, then Enter, Space or the menu key for the menu; Esc closes it and cancels a task dialog). Its labels are text, not pictures; the status dot sits beside a word.

**Left:** the Apps chart's per-day numbers show only on hover (the table has the totals); an empty table header (the Activity list's outcome column); the tree's 14 px boxes are below the 24 px target size (each row is the target too: a click selects it, Space ticks); vault passwords are asked with `prompt()`, which doesn't hide what's typed; the navigation keeps its width at 320 px. What only a person can check: a pass with Narrator and NVDA through each page, and each contrast theme by eye.

## The window in the taskbar
The settings window sets its own AppUserModelID (`OneUpDrive.Settings`, through the window's property store) and its big and small icons (`WM_SETICON`). With only the package identity, the taskbar would show the package's logo on a grey plate and treat a click on the button as launching the package's app rather than bringing the window forward. The program is a Windows-subsystem program in every build.

## The mark
The icon is drawn in code (`tray::mark`, `tray::render`): a cloud cut along a chevron, its top lifted a step ("one up"), sky to azure above and azure to indigo below, transparent gap between. `packaging/oneupdrive.ico` (every program's icon, and the settings window's title bar and taskbar button through `LoadIconW`) is generated from it (`ONEUP_WRITE_ICON=1 cargo test -p oneup --lib the_icon_file`); the tray's status icons put their badges on the same mark. The page draws the same geometry as an inline SVG; the identity package's logos are rendered from it at their sizes.
