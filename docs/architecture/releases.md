# Installing, signing and updating

Releases are signed, published on GitHub, and update themselves.

## Choice: Velopack, per-user
| Option | For | Against |
|---|---|---|
| **Velopack** (MIT) ✅ | Per-user install (no admin), updates from GitHub Releases with deltas, install/update/uninstall hooks in our own code, signs every program at pack time (Azure Artifact Signing or signtool), Rust crate | A dependency for updating; its install folder is `%LOCALAPPDATA%\<package id>` |
| MSIX | Package identity built in, Store-ready | No code at uninstall (can't stop agents or release sync roots first), file-system and registry virtualisation fight a sync agent (data folder, `Run` key), App Installer feeds need a web host |
| MSI (WiX) or Inno Setup | Familiar | Updating is ours to write; WiX's newer releases carry a maintenance-fee licence term; Inno needs its own toolchain |

Explorer integration needs **package identity**; it comes from a separate signed *sparse* package registered by the install hook, the way the OneDrive app does it ([explorer.md](explorer.md)).

## What gets installed
`oneup.exe`, `oneupd.exe`, `oneupd-start.exe`, `oneup-tray.exe` (Velopack's main program: the Start menu shortcut), `oneup-settings.exe`, `oneup-open.exe`, `oneup_shell.dll`, the identity package, `LICENSE` and `THIRD-PARTY-NOTICES.txt` (generated by `cargo about` from `packaging/about.toml`), into `%LOCALAPPDATA%\OneUpDrive.App\current`. **The package id is `OneUpDrive.App`, never `OneUpDrive`:** the install folder is named after it, and `%LOCALAPPDATA%\OneUpDrive` is the default *data* folder (database, sign-in, vault keys), which uninstalling would remove along with the programs. The uninstall hook also never touches a data folder inside the install folder. The installer is `OneUpDrive.App-<channel>-Setup.exe`.

Every program carries the icon (`packaging/oneupdrive.ico`, drawn by `tray::ico` and kept in step by a test), version information and an application manifest (per-monitor DPI, long paths, common controls 6, `asInvoker`), from `bins/oneup/build.rs`.

## Hooks (`oneup_app::install`, called first thing by `oneup-tray`)
* **Install and update:** register the identity package ([explorer.md § Registering and updating the package](explorer.md#registering-and-updating-the-package)).
* **Uninstall:** stops the agents of every account's data folder (`accounts::list`) and its vault and extra pairs, releases their Files On-Demand folders (Windows then removes only the online-only files, which are in OneDrive, and turns every other placeholder into an ordinary file with its content), and removes "start at sign-in" and the Office and Explorer registrations. The data folders stay.
* **Start menu / sign-in / after an update:** `oneup-tray` with no arguments or with `--start` starts the agent and the vaults whose keys are remembered.

## Updates (`oneup_app::updates`, driven by the tray)
* Feed: GitHub Releases of the repository the release was built for (`ONEUP_UPDATE_REPO`, set by the workflow), or `[updates] repo`; `channel = "stable"` (releases) or `"preview"` (pre-releases too); `auto = true` by default.
* The tray looks 2½ minutes after starting, then daily (only while `auto` is on), and at once when the settings window's **Check now** raises its named event (`oneup_sys::signal`, `updates::check_signal`; also with `auto` off). It downloads in the background, then **checks the package**: its `oneupd.exe` must carry a valid Authenticode signature from **the same publisher (full subject) as the running program** (`oneup_sys::authenticode`, `WinVerifyTrust` without network revocation checks). Otherwise the package is deleted and nothing is installed. An unsigned installation never updates itself.
* With `auto` on, it installs by itself when the agent is idle (no transfers, nothing waiting for the user) and no vault is unlocked by password only (restarting would lock it); the menu offers **Install update …** meanwhile. With `auto` off, a found update waits for **Install update…**. Installing stops every agent of every account (control API `stop`, waiting up to 2 minutes; the updater ends all programs running from the install folder), applies, and restarts the tray with `--start --after-update`, which also starts the other accounts' trays that start at sign-in. `oneup updates` does the same from the command line.

## Building and publishing
* **The sign-in's client ID** is built in (`-ClientId`, the workflow's `vars.ONEUP_CLIENT_ID`, read with `option_env!` as `setup::BUILT_CLIENT_ID`): without it a release can't sign anyone in. It's a public client ID, not a secret, but stays out of the repository like the rest of the account's identifiers.
* `packaging/build-release.ps1`: cargo release build with the version, update repository and publisher; stage; the identity package `OneUpDrive.Sync.msix` with `makeappx`; `vpk download` of the previous release for deltas, `vpk pack` with signing, `vpk upload github`. Without signing it makes a local, unsigned installer for trying on a test PC.
* `.github/workflows/release.yml` runs it on a `v*` tag in two phases (stage; then pack and publish), signing the programs and the identity package in between with `Azure/artifact-signing-action`, and the installer pieces vpk makes with vpk's own signing, all with **Azure Artifact Signing** through GitHub's OpenID Connect token (no stored password), in a `release` environment that can require approval.
* **One TLS backend per process.** The updater's HTTP client (ureq) turns on rustls' `ring` backend next to reqwest's `aws-lc-rs`; with two, rustls refuses to choose and every HTTPS connection panics. Every program installs `aws-lc-rs` as the process default first (`setup::tls`), and a test builds a client.
