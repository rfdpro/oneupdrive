# Files On-Demand

Files in a synced folder can be *online-only*. Explorer lists them with their real names and sizes, and they take no disk space until opened. Opening one downloads it, which the user sees as a short delay. "Always keep on this device" and "Free up space" work as in the OneDrive app. Nothing about it may lose data: this API has a real data-loss path when used naively, so the binding rules are data-safety invariants 11–16 ([data-safety.md](data-safety.md#files-on-demand)). User guide: [Files On-Demand](../user-guide/files-on-demand.md).

## Shape
* **Opt-in per folder pair** (`oneup sync … --on-demand` makes a new pair on-demand before its first round; `oneup on-demand on|off` for an existing one; the settings window's setup page, which suggests it, and Files page). Off by default on the command line.
* OneUpDrive is a **Cloud Files provider** (`CfRegisterSyncRoot` or the shell's `StorageProviderSyncRootManager`, then `CfConnectSyncRoot`) for the synced folder ([explorer.md § Sync roots](explorer.md#sync-roots-registered-with-the-shell)). Only `oneupd` connects. Without it running, opening an online-only file fails at once with Windows' "cloud provider not running" error: it never hangs, and never yields zeros.
* **Never inside another provider's sync root** (the coexistence check, [local-tree.md](local-tree.md#another-sync-app-on-the-same-folder)), and never over the OneDrive app's folder while the app manages it ([Moving over](#moving-over-from-the-onedrive-app)).

## Placeholders and identity
Every cloud file and folder in the pair has a **placeholder** here. A placeholder is either *dehydrated* (no content on disk) or *hydrated* (the full file). Its **file identity** (an opaque blob Windows stores with it and hands back in every callback) is ours:

```
version 1 | cloud item ID | eTag | size | QuickXorHash (20 bytes)
```

Invariant 13: before a single byte is transferred, the identity must match the placeholder's own size, the Remote tree's current version of that item, and finally the downloaded content's size and hash.

## What changes in the engine
The reconciler stays as it is. It plans *what* should happen, and on-demand mode changes *how* the executor does it. Each local item the Local tree reports is one of: an ordinary file, a hydrated placeholder, or a dehydrated placeholder. Placeholders of **our** sync root are exempt from the "another provider's placeholder" parking (they're ours, and their content is known by identity).

| Planned | Full-file mode | On-demand mode |
|---|---|---|
| Download a new cloud file | download to staging, verify, place | **create a dehydrated placeholder** (no download); a file without OneDrive's hash is refused, since nothing could vouch for it |
| New cloud folder | create the folder | create a folder placeholder |
| Download replacing a local file (cloud edit) | download, verify, replace (old copy kept or dropped) | dehydrated: **update the placeholder** (new identity and size, still no content). Hydrated: proved to be the last synced version under a share-none handle (or a copy is kept as an ordinary file in the version store), then marked in sync and dehydrated with the new identity (`VERIFY_IN_SYNC`, invariant 11). Pinned: hydrated again afterwards |
| Upload (local edit or new local file) | read, upload, verify | the same: only an ordinary file or a **hydrated** placeholder is read (never a dehydrated one, which would ask ourselves for it), then **marked in sync** with the new identity under an exclusive handle, after checking it's unchanged (invariant 5), or converted if it was an ordinary file |
| An item already here and the same as OneDrive's (`Op::Pair`, a first sync over an existing folder) | recorded | recorded and **converted** to a placeholder that keeps its content |
| Recycle a local item (cloud deletion) | move into `.oneup\versions` | hydrated: moved into the version store and reverted there to an ordinary file, so a kept copy never depends on the cloud. Dehydrated: removing it destroys no local bytes (its content is the cloud version now in OneDrive's recycle bin), so it is deleted without a copy, and recorded as such |
| Conflict copy, moves, renames | as usual | as usual (metadata only); after our own moves the placeholder is marked in sync again (below) |

**Hashes without reading.** For a placeholder whose identity vouches for the content (dehydrated, or in sync and fully on disk), its identity's QuickXorHash is its content's hash. The executor records a placeholder's identity hash in `local_hash` when it creates or updates one, so the scanner never opens millions of placeholders and the planner never needs to read one. A placeholder is never opened for data unless all of it is on disk.

**The in-sync bit.** Because the agent writes user content only through transfers (invariant 12), the bit is cleared by real user edits and is a *hint*. The Local tree's size and mtime stay the truth. A hydrated placeholder whose stamp moved since its Synced row is an edit, whatever the bit says. **Renames clear the bit**, so after our own moves a placeholder that was in sync before the move is marked in sync again, through a second attribute-only handle while the moving handle is still held (one a program edited stays not in sync: its edit isn't sent yet, and the bit is what keeps Windows from freeing it); otherwise a later cloud edit of a hydrated, moved file would be refused by `VERIFY_IN_SYNC` every round.

**Opening a dehydrated placeholder with data access downloads it**, without any read, and even with `FILE_FLAG_OPEN_NO_RECALL`. Files read for an upload or a hash are judged from their folder's listing just before they're opened for reading; one dehydrated in between would be downloaded by that open (from OneUpDrive itself, so an unneeded download, never wrong content), and is then refused on the handle before any byte is read ([sync-engine.md § Executor](sync-engine.md#executor-cratesoneup-exec)). So OneUpDrive opens its dehydrated placeholders with attribute and delete access only (`win::open_path_for_dehydrated`), judged by attributes read through an attribute-only handle. Windows doesn't enforce share modes on such handles, so removing or re-versioning one happens under a **hold** (`provider::hold`): every fetch of that identity fails meanwhile, and as the provider we're the only way its content could arrive. A hold is **refused while a fetch of that identity is under way**: hydration downloads the whole file before transferring its first byte, so the placeholder shows nothing on disk while its old version is on the way, and changing its identity then would let those old bytes into a placeholder that stands for the new version (invariant 13). `oneup-cfapi` counts a fetch as under way from its callback until its `Fetch` is gone (completed, failed or dropped), under the same lock as the holds, so a hold and a fetch of one identity exclude each other; a transfer for a held identity is refused as well. The round skips that placeholder (changed meanwhile) and updates it once the fetch is over.

**A placeholder partly here** (a download cut short: a program closed the file, or the request was cancelled) holds only bytes OneUpDrive transferred of its identity's version, which were verified before the transfer. With whole-file hydration, a program can't write to it until all of it is here: measured, a write fails and leaves nothing modified. Reading the rest would ask for that version, which after a cloud edit or deletion the hydrator refuses, so the operation would fail every round. So a cloud edit dehydrates it with the new identity, and a cloud deletion removes it, neither reading it nor keeping a copy (OneDrive's version history or recycle bin has that version). Both happen under a hold, through a share-none handle, after checking under that handle that it is the planned item and stamp, in sync, with nothing written here (`ModifiedDataSize` 0) and still partly here (`LocalFs::open_partial`); the edit's dehydration also passes `VERIFY_IN_SYNC` (invariant 11). Its attributes say "recall on data access", as a dehydrated one's do, so it is found through an attribute-only handle first.

**`LocalFs` knows it's on demand** when its folder is registered as OneUpDrive's sync root with this pair's token. The effects for it are in `oneup-effects/src/ondemand.rs`; the full-file download and mkdir paths refuse in that mode, so no content is ever written into the sync root (invariant 12).

## Hydration (`FETCH_DATA`, `oneup_exec::hydrate`)
`Hydrator<C: Cloud>` (`Serve` is its `Provider`), connected by `oneupd` while the pair is on demand.
1. The callback hands over the identity, the requested range, and the requesting process. It answers on a tokio task: the Cloud Files callback thread is never blocked on the network.
2. Check: the identity decodes; its size equals the placeholder's; the Remote tree's current version of the item (eTag, size, hash, read through the hydrator's own database connection) equals the identity's. Otherwise **fail** the request (`STATUS_CLOUD_FILE_NOT_IN_SYNC`) and wake the agent, so the next round updates the placeholder.
3. Download the whole file into `<data folder>\hydration` (never into the sync folder), hashing as it goes. Size and QuickXorHash must equal the identity's, or fail the request.
4. Transfer from the staging file with `CfExecute(TRANSFER_DATA)` in 1 MiB chunks (with progress), then delete the staging file.

Whole-file hydration (the `FULL` policy) keeps every hydrated file complete and verified. Streaming ranges straight from Graph would start sooner on huge files, but would put unverified bytes into the file.

* **Who's asking** comes with every callback (`REQUIRE_PROCESS_INFO`), and is logged in the activity log ("opened by explorer.exe") and counted per program ([usage.md](usage.md)).
* **Cancellation:** `CANCEL_FETCH_DATA` aborts the task and removes its staging file; the request fails.
* **Not paused:** a pause stops sync operations, not hydration. A program opening a file is the user asking for it.
* **A failed `TRANSFER_DATA` must name the requested range** with no buffer. With a zero length the reading program waits more than 60 s; with the range, it fails in milliseconds.

## Folders are fully populated
Folders are created fully populated (`ALWAYS_FULL`); lazy population (`FETCH_PLACEHOLDERS`) isn't used. Creating placeholders one at a time runs at about 7,800 a second (`oneup-cfapi` test `placeholder_rate`, ignored by default), so a folder of 300,000 files costs under a minute of Cloud Files work, and the executor's own bookkeeping dominates. Lazy folders would also leave folders whose contents this PC has never seen, which complicates deletion evidence. Folder placeholders need a non-empty identity (`CfCreatePlaceholders` refuses the whole batch otherwise).

## Pinning and freeing space
* **Always keep on this device** (`PINNED`): the provider must hydrate these itself. Pinning a folder leaves its children's explicit states, but a placeholder created in it inherits the pin, still dehydrated.
* **Free up space** (`UNPINNED`): setting it frees nothing by itself; Windows dehydrates in-sync files, and because the in-sync bit is only cleared by real edits, it can't dehydrate an unsynced edit. OneUpDrive's own dehydration (a cloud edit of a hydrated file, the space policies) always uses the safe sequence.
* **Bytes a program wrote stay "modified" after being marked in sync, and dehydration frees only validated data.** Reverting and converting again through one exclusive handle (`Exclusive::revalidate`) validates them; `mark_uploaded` does that after an edit was sent, so freed files are freed completely.
* **Finding the work:** partial indexes on `local_item` for "pinned, not here" and "free up space, still here" (`local_to_fetch` / `local_to_free`), so finding it costs only those rows (a test checks the query plan). Empty files are left out: an empty file looks freed already, and the effects layer refuses it.
* **The placement pass** (`oneup_exec::placement`) runs after each settled round (`Engine::placement`, nothing while "changes to this PC" are paused). `pinrules::fetch_pass` hydrates pinned files through our own hydration (`placement::fetch_one`), off the async runtime, at the bandwidth caps and priority the user set. `free_ops` makes **`Op::Dehydrate`** operations; they go through the gate (side: this PC) and the executor, which requires the Synced hash and the cloud's current hash to equal the op's hash, then `LocalFs::free_up` re-hashes the content under a share-none handle and dehydrates with `VERIFY_IN_SYNC`. The automatic space policies feed the same operations ([usage.md § Space policies](usage.md#space-policies-oneup_appspace)).
* `oneup pin PATH` sets the pin state (recursively for a folder), as Explorer does, and nudges the agent; what it names becomes the user's, a folder's contents too (`pinrules::claim_for_user`, a page at a time): no rule's note, retry or release stays on them, so removing a rule never undoes that pin. `oneup free PATH` follows the maintainer's order of what wins (`pinrules::free_plan`, from the database a page at a time): a file named itself is unpinned and freed even if it was kept on this device, and if a pin rule kept it, it's released from the rules (`pin_released`); a folder is set to free up space with what's in it, except what's kept, which is skipped and counted: a pinned file, a pinned folder and everything in it, and what a pin rule keeps. Both commands record the person's choice first, in a durable transaction (the claim, a page per transaction; the release of a file freed by name), and change the pin only then: a crash or an agent pass in between finds the record and neither undoes the pin nor pins the freed file again; running the command again finishes it.
* **Nothing pinned is freed.** `LocalFs::free_up` reads the pin on its share-none handle just before dehydrating and refuses a pinned placeholder, whoever planned the operation and however late the pin was set (`on_demand_a_pinned_file_is_never_freed`).

## Pin rules
`[rules] pin` ([rules.md § Pin rules](rules.md#pin-rules)) sets "Always keep on this device" on what it matches; the placement pass then downloads them like any pinned file. `oneup_app::pinrules`, from `Engine::placement` after each settled round, before fetching and freeing:
* **Only a rule's own pins are undone.** Each item a rule pinned is noted in `pin_owned` (schema v22, `oneup_store::pins`), with the activity log's last entry at the time. A placeholder found already pinned by a walk (the rules looking at it for the first time, or a folder's contents after a rule pinned the folder) is the user's and noted so (`pin_user`). A placeholder the activity log names after its folder took a rule's pin, that no walk found pinned before, took the pin from the folder (Windows gives new placeholders their folder's pin) and is noted as the rule's, so removing the rule undoes it with the folder; a folder a rule pins from a change rather than a walk gets a walk of its own first (`pin_subtree`), so the user's pins in it are told apart before anything is taken as inherited.
* **A rule unpins only what it can prove it pinned.** Every pin change goes through a handle on which the item's file ID and creation time are read first (`provider::identity`, `pinrules::Pinner`). Pinning writes the rule's note with that creation time before the pin is set (an intent: a crash in between leaves the item the rule's, so its download still counts against the approved budget, and removing the rule still undoes it), then sets the pin through a handle checked again. Unpinning checks the file ID and the recorded creation time on the handle that unpins: another item at that path, a new file or one reusing the ID, is the user's, and the rule's note is dropped instead. Anything uncertain is the user's. What the user claimed (`pin_user`, by `oneup pin` before the pin is set on disk, or found pinned) is never pinned or unpinned by a rule: the walk, the incremental pass and the retries check it, and an unpin reads it again right before acting.
* **Bound to the Local row.** A file ID can be reused once its file is gone, so the notes go with their Local row in the same transaction: triggers on `local_item` drop them when the row is deleted or its kind changes, and a note is only made for an item in the Local tree. A later item with the old ID starts with none. A rescan of the same folder (after the change journal was lost, say) deletes every Local row: `local_begin` first sets the rules' notes, retries and releases and the user's notes (with whether a user's folder was waiting for its pin back) aside and forgets that the rules were applied, and the agent's next pass puts back those whose file IDs the new scan found (`pins_rebind`, once per rescan). The scan inserts rows, which no trigger watches, so that pass also notes the folders it found pinned that aren't the rules' as the user's, and queues again a user's folder that was waiting. An ID alone proves nothing, so a note put back is only ever used through the creation-time check above (a replacement reusing the ID keeps the user's pin), and a release put back only keeps a rule from pinning: a file freed by name stays freed after a rescan.
* **When the pin rules change** (their fingerprint differs from `meta pins.applied`): first the noted items, a page at a time: one the new rules don't match and still pinned goes back to unspecified (and is no longer noted; one the user unpinned meanwhile is just dropped). Then a walk of the Local tree in the database that pins what the new rules match and isn't pinned (folders too, so placeholders created in them inherit it), skipping excluded folders and the engine's folder. The walk reads each folder 256 children at a time in the parent index's order (`local_children_page`) and goes depth first, so it holds only the folders on the way down, each with a cursor; that state is saved in `meta pins.walk` after each 20 s slice, so a slice never holds a whole folder, and a walk cut short (the agent stopped) carries on where it was. The new fingerprint is stored when the walk is done. With no rules and nothing noted, there's nothing to walk.
* **Otherwise**, only what changed: the done activity-log entries after `meta pins.seq` (2,000 a pass, by the log's key), each item and a move's destination looked up by name. If more entries were dropped from the log than it keeps, the next pass walks again. Each named item is brought in line with the rules (`pinrules::reconcile`): pinned if they match it, set back to the default if it's theirs and they don't (a file moved out of a pinned folder). A folder that moved is queued in `pin_subtree`, and its contents at the new place get a walk of their own, saved between passes like the main walk (`meta pins.subwalk`).
* **Nothing is forgotten.** A pin or an unpin that can't be set yet (not a placeholder yet, say) waits in `pin_retry` with its operation (at most 10,000) and is tried again after a minute, doubling to at most six hours, until it's done, the item is gone, or it's no longer wanted; an unpin keeps the rule's note until it's done. One that found the table full marks `meta pins.rewalk`: as soon as the table has room again, another walk starts, and the mark is cleared only once that walk is saved as under way (a walk already under way finishes first; a mark set during it brings the next).
* **"Free up space" on the file wins; through a folder, the pin does.** An item a rule pinned that loses its pin produces no sync activity, only an attribute change in the change journal, which the observer writes to the Local tree; a trigger then queues it in `pin_changed` (rows of `pin_owned` and the user's folders only). The next pass tells a file-level request from a folder-level one by the folder above: File Explorer marks everything it frees, the chosen folder too, so a file whose folder isn't set to free up space was freed by name (`pinrules::freed_by_name`); only files are released this way: a folder a rule keeps is pinned again, whoever frees it. Freed by name, the file is released (`pin_released`, schema v22): no longer the rule's, freed, and left so by every walk, pass and space policy until it's pinned again (a trigger ends the release when the pin attribute comes back; `oneup pin` ends it at once). Through a folder, it's pinned again and logged. Windows doesn't say which was chosen, so a folder freed first and a file in it afterwards counts as the folder's request. A queued item leaves the queue only once released, pinned again, or handed to `pin_retry` (with that full it stays queued), so a crash loses nothing. `oneup explain` says which applies. The synced folder counts like any folder above: freed itself, it's a folder-level request. A folder the user pins is noted by a trigger (`pin_user`, a folder that gets the pin without a rule's note), so it beats a "Free up space" on a folder above too: it's pinned again (queued like the rules' items), and what's in it isn't freed (`pinrules::kept_by_folder_above`, a walk up the parents of each candidate, for the space policies and "Free up space" through a folder); "Free up space" on that folder itself is the user's choice and ends the note. The observer applies only the records there when it started, so a folder above may be marked in a later batch: a user's folder whose folders above aren't marked stays queued one more pass, and its note ends only if they're still unmarked then. A folder found pinned by a scan is noted the same way after it (above). Its pin is put back only on that folder: the trigger also queues it, and the pass reads its creation time on a handle while it's pinned (`pin_user.created`; queued until it can be read, and kept when the pin comes back after a restore); a restore sets the pin through a handle that must show that time. A rescan keeps only notes that have it, so a folder ID reused after a rescan isn't pinned (nor its files downloaded). A pin that can't be restored now (the folder in use, say) stays queued for the next pass.
* Pins are set through an attribute-only handle (`provider::open`), never reading content.
* **Downloading what they keep** is the placement pass's `pinrules::fetch_pass`. It reads the files to fetch a page at a time by file ID (`local_to_fetch_after`) from where the last pass stopped (`meta pins.fetch_after`, wrapping around at the end), until it has a batch it will download, has read 1,024 files, or has gone once around. It passes over a file this pass won't download (one of the rules' past the budget, or one whose identity can't be read now), so those never hold up the rest, and a pass costs at most those 1,024 reads (and opens), however many files are ahead. The scan's place only moves forward (back only to the file a pause or the share stopped at, which can go). The first of the rules' files past the budget is remembered on its own (`meta pins.fetch_waiting`): it's the one the go-ahead is for, and each pass tries it first. Once it fits, it's downloaded (too big for the free space or the pass's share now, it's tried again next pass and the rest of the batch goes on; only a pause stops the pass there); while it's still past the budget, or can't be read this pass, its bytes are held from the rules' other files; gone, here already, no longer kept on this device, released or no longer the rules', it's forgotten. So files waiting for a go-ahead never stop the scan from reaching the user's own pins, wherever they sort. It asks before each file (`pinrules::FetchLimit`, pure) and says why it stopped (`placement::Stop`): a pause that came meanwhile (the agent's controls, read live); the disk would keep less free than a gibibyte or the space policy's low-disk share; free space that can't be read (nothing is downloaded blind); the pass's share used (2 GiB or 60 s, its first file may be larger); or a download that needs the person's go-ahead (below). The bandwidth caps apply as for any hydration. When the share stopped it, or its batch of 32 was full, `Engine::pins_pending` brings the next pass 5 s later (never after a pass that only passed files over: the agent's regular check carries on from the saved place); a pause, the disk or a question wait for an event instead (resuming, a change of settings, the agent's own wake-ups), never a short timer. Within a file a pause waits for the file to finish.
* **Downloads are asked for.** `pinrules::preview` counts the online-only files a set of pin rules would pin that aren't pinned yet (the same paged walk, at most 10 s, "at least" past that). Every change of pin rules from the window or `oneup rules --pin/--unpin` (removing a `!` rule too) that would download anything, or whose count couldn't finish, is shown and needs a yes (the window's question, `--yes`). The yes is recorded for exactly those rules (`meta pins.approve`, fingerprint and bytes) and joins `meta pins.budget` once they're the rules. The agent takes what it downloads for the rules' own items off that budget; when a file would take it more than 1 GiB below zero (rules changed by hand, files that keep arriving, a count cut short), that file and the rules' files after it wait (other files are still downloaded), and the agent notes the file's size in `meta pins.waiting`, logs that it waits, and the window (**Download**) or `oneup rules --allow-downloads` gives the go-ahead. Repeated small changes can't reset that count: it carries across changes of rules. Budget is reserved before any download: the rules' own files among a pass's batch that fit are taken off the budget and listed in `meta pins.reserved` in one transaction, then fetched; afterwards what wasn't downloaded comes back. A reservation a crash left is settled before the next pass: a file on this PC by then (by its attributes alone) stays spent, the rest comes back, so an approval can't be used twice. A file counts as the rules' for the budget only while their note still names it (its file ID and creation time read on a handle, `pinrules::owned_verified`; a stale note is dropped), and a download that was tried counts whether it finished or not, so failures can't go past the approval again and again. While changes to this PC are paused, nothing more is scheduled soon. The reservation and each rule's note are durable commits, and each of the rules' files is marked started, durably, right before its download: a reservation a crash leaves is never refunded for a started file. A file whose identity can't be read this pass is neither charged nor fetched.
* **A pin rule wins over automatic freeing**: `space::select` skips what it matches even before its pin is set, unless the file was released; a "Free up space" (`local_to_free`) on such a file is dropped from the pass and pinned again when it came through a folder, and freed (the file released) when it was the file's own. The effects layer's refusal above backs both.

## Turning it on and off (`oneup_app::ondemand`)
* **On:** register the sync root on the paired folder (identity: the pair's token), then **convert** every Synced folder and every unchanged Synced file to a placeholder that keeps its content (`CfConvertToPlaceholder(MARK_IN_SYNC)` under an exclusive handle). Unchanged means the hash on record for its current size and time is the synced hash, so nothing is re-read; the stamp is re-checked under the share-none handle. Files not in sync are converted after their upload. Nothing is dehydrated by turning it on. The walk pages through the Synced rows whose local item isn't recorded as a placeholder (`Ops::synced_not_placeholders`), so running it again costs a pass of the table, not an open of every item; up to three passes, as a folder's sid can come after its children's.
* **Finishing in the background.** The agent does the same after each settled round (`Engine::convert_leftovers`): slices of at most 20 s, 5 s apart while there's more, once per start, not while changes to this PC are paused, never for a vault pair; one activity note at the end. So an interrupted turn-on, or a repaired registration, ends with every file a placeholder.
* **Off:** refused unless free space covers the online-only bytes plus 1 GiB (the command says how much is needed). It then serves downloads in-process with the same hydrator, hydrates and reverts every file placeholder (`CfRevertPlaceholder`), reverts the folders deepest first, and unregisters. Never unregister with dehydrated placeholders left: Windows deletes them when the sync root is unregistered, so those files would vanish from the PC (they stay in OneDrive).
* **Uninstalling** releases each Files On-Demand folder: Windows removes only the online-only files and turns every other placeholder into an ordinary file with its content ([releases.md](releases.md)).

## Keeping the registration
* **Our sync root isn't "another provider".** `oneup_cfapi::other_sync_root` skips a sync root registered as OneUpDrive. It reads the registered provider (`CF_SYNC_ROOT_INFO_STANDARD`), not the connected one: with no provider connected, `CF_SYNC_ROOT_INFO_PROVIDER` leaves the name unset. Our folder is also recognised by the shell's record (`SyncRootManager\OneUpDrive!<user>!<token prefix>`; `shell::is_ours`, and `shell::is_pairs_root` for one pair) when the registration has no provider name, because Windows can leave the Cloud Files registration without its provider name and identity while the shell's record is intact; taken at face value, the folder would then look like an ordinary one with every online-only file a file to fetch. A registration under another name is another provider's even inside a folder that record covers: the record can outlive our Cloud Files registration, and another program may have registered the folder since.
* **Never re-register while connected.** Registering the folder through the shell while the agent is connected as its provider leaves a registration Windows drops when the agent disconnects. So the agent runs `oneup refresh-explorer-entry --repair` (repair if needed, then refresh the icon and version) **before** it connects, and waits for it (`oneupd::prepare_registration`).
* **Repaired at the agent's start.** The registration can also go entirely (for example when the identity package's files vanish). When the folder's own record (`.oneup\on-demand`) says it was our Files On-Demand folder and Windows no longer does, `syncroot::repair` registers it again only if no other provider has the folder and up to 200 files that were online-only at the last look (`local_online_only_sample`) are all still there, looked up by attributes: losing the registration can make Windows delete every online-only placeholder, and their absence must never be read as deletions to send. Otherwise the agent stays stopped with the identity-check error, which says to turn Files On-Demand on again (invariant 15).

## Moving over from the OneDrive app
`oneup migrate check` (`bins/oneup/src/migrate.rs`, `oneup_app::moveover`) and the settings window's **Move over** path ([settings-window.md](settings-window.md#setting-up-and-moving-over-from-the-onedrive-app)). It finds the app's personal folder (registry `HKCU\Software\Microsoft\OneDrive\Accounts\Personal\UserFolder`, then the environment), reports whether a sync root other than ours is registered there, and summarises this data folder's scan of it. It is read-only.

* **The app's online-only files.** When a provider's sync root is unregistered (what unlinking does), Windows deletes its dehydrated placeholders and its folders never listed, and turns every placeholder with content here into an ordinary file with its bytes, including an edit not yet sent and a pinned file (the pin attribute stays). A placeholder held open at that moment goes when it's closed. So no placeholders are left to replace, and a hydrated file becomes an ordinary file that the first sync pairs by hash. `oneup-cfapi` test `unregistering_another_provider_removes_only_what_is_in_the_cloud` pins this (a stand-in provider with its own name, ID, identity format and partial population, like the OneDrive app's). **Before unlinking**, the check verifies from the scan and the cloud listing (the observe planner) that every online-only file and unopened folder is in OneDrive at the same path, counts those with a newer version there, and lists any that aren't, telling the user not to unlink until they're explained.
* **The app's choices** are recorded while it still manages the folder (`crate::carryover`, `carry-over.json`): its account, and its folders not on this PC, carried over as **paused** folders (not brought here, never offered for removal).
* **Adopting** is the ordinary first sync of the same folder with the whole drive (`oneup sync <folder> --remote / --pair-only`): files present on both sides are paired by QuickXorHash, both copies are kept where contents differ, and OneDrive's online-only items become our placeholders. The app's stand-ins for packages (`Personal Vault.lnk`, a notebook's `<name>.url`) are kept back by the store's children query (`STAND_IN` in `oneup-store/src/synced.rs`); its marker file, `desktop.ini`, `~$` and `.tmp` files by parking.
* **The app's registry leftovers** (`oneup_app::appleftovers`). Unlinking the personal account leaves the app's `Accounts\Personal` key with only its own counters, and its "OneDrive - Personal" navigation-pane entry (its per-user class `{018D5C66-4533-4307-9B53-224DE2ED1FE6}` under `Software\Classes\CLSID`, and the Desktop `NameSpace` entry that shows it), which targets the OneDrive known folder: now our folder, shown a second time under the app's name, and opening it asks the app. The first pairing of the app's folder (as the app's settings or the environment name it) clears them; `oneup migrate leftovers [--clear | --undo]` shows, clears or puts them back. Each is cleared only when provably stale (`review`, pure, tested on a fake registry): no other sync root holds the folder, the personal key has none of an account's values (`UserFolder`, `cid`, `UserEmail`…), and the class targets the OneDrive known folder or the folder itself; the `NameSpace` entry goes only with that class and only if it holds nothing but a name. Work or school accounts (other keys, other class IDs) and our own pane entry (another class ID) are never touched. Nothing is cleared while the app runs (`OneDrive.exe` among this user's processes: the only writer of these keys, and it could link the account again), and one clear or undo runs at a time for the Windows user, whichever data folder it is for (a named mutex in the global namespace keyed by the user's SID, as every data folder shares the user's registry; Windows lets go of it when its process ends). Just before each key goes, the folder must still be free of other sync programs, the key exactly as backed up and, checked last, the app still not running. The registry has no compare-and-delete, so one call's window remains; the backup and an undo that only adds what's missing cover it. The keys are copied whole (types and raw bytes, `oneup_sys::user_registry::tree`) to a new `<data folder>\backups\onedrive-app-leftovers-<n>.json` first (written under a temporary name and linked to its own, never over another, numbered after every earlier backup), and the activity log notes what went, also when an error stops it partway. Undo creates only missing keys and values (`restore_missing`), so whatever the app wrote since stays (a running app may create an empty `Personal` key again, which is harmless). Left alone: the app's `HideDesktopIcons` value for the class (Windows may register the class machine-wide, and removing the value could show a OneDrive desktop icon) and Windows' OneDrive known folder.
* **A stalled unlinking.** The app can remove its account but never unregister its sync root, spinning for days with every online-only file still there. `moveover::App::stalled()` detects it; `oneup migrate finish-unlink` (and the window's **Finish unlinking**) restarts the app, runs its own `/reset`, then releases the folder itself through the gate's `release::review_release` and `oneup_effects::release::release_root` (invariant 16). Another program can unregister a stalled root with the same result as an ordinary unlinking (`a_stalled_unlink_can_be_finished_by_another_program`). Windows skips a subtree some program has open during the unregistering yet reports success (`a_folder_held_open_is_left_orphaned_until_released_again`), so `finish-unlink` rescans and clears placeholders left behind item by item through the same gate decision (`oneup_effects::release::clear_left_behind`: revert what has content, remove what's online-only, judged by reparse tag and attributes, since Windows won't describe an orphaned placeholder); the first pairing refuses a folder with orphaned cloud placeholders. Unregistering a big folder can take many minutes inside `CfUnregisterSyncRoot`, silently, so the command prints a line a minute.

## Excluded items and "Sync pending"
Explorer shows any non-placeholder item in a sync root as "Sync pending", and so the folders above it: excluded items (`node_modules`, `.git`…) look pending forever. Marking excluded folders as *excluded* placeholders was tried and set aside: it didn't clear the indicator on a real folder, and unmarking one with a revert removed an online-only leftover inside it. What remains is the clean-up of such marks: `Engine::clear_excluded_marks` resets the pin of any mark after settled rounds (never a revert; `LocalFs::unmark_excluded_folder`), `convert_folder` does the same before a marked folder syncs, and turning Files On-Demand off leaves marked folders to the unregistration.
