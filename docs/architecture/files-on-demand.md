# Files On-Demand

Files in a synced folder can be *online-only*. Explorer lists them with their real names and sizes, and they take no disk space until opened. Opening one downloads it, which the user sees as a short delay. "Always keep on this device" and "Free up space" work as in the OneDrive app. Nothing about it may lose data: this API has a real data-loss path when used naively, so the binding rules are data-safety invariants 11–16 ([data-safety.md](data-safety.md#files-on-demand)). User guide: [Files On-Demand](../user-guide/files-on-demand.md).

## Shape
* **Opt-in per folder pair** (`oneup sync … --on-demand` makes a new pair on-demand before its first round; `oneup on-demand on|off` for an existing one; the settings window's setup page, which suggests it, and Files page). Off by default on the command line.
* OneUpDrive is a **Cloud Files provider** (`CfRegisterSyncRoot` or the shell's `StorageProviderSyncRootManager`, then `CfConnectSyncRoot`) for the synced folder ([explorer.md § Sync roots](explorer.md#sync-roots-registered-with-the-shell)). Only `oneupd` connects. Without it running, opening an online-only file fails at once with Windows' "cloud provider not running" error: it never hangs, and never yields zeros.
* **Never inside another provider's sync root** (the coexistence check, [local-tree.md](local-tree.md#another-sync-app-on-the-same-folder)), and never over the OneDrive app's folder while the app manages it ([Moving over](#moving-over-from-the-onedrive-app)).

## Placeholders and identity
Every cloud file and folder in the pair has a **placeholder** here. A placeholder is either *dehydrated* (no content on disk) or *hydrated* (the full file). Its **file identity** (an opaque blob Windows stores with it and hands back in every callback) is ours:

```
version 1 | cloud item ID | eTag | size | QuickXorHash (20 bytes)
```

Invariant 13: before a single byte is transferred, the identity must match the placeholder's own size, the Remote tree's current version of that item, and finally the downloaded content's size and hash.

## What changes in the engine
The reconciler stays as it is. It plans *what* should happen, and on-demand mode changes *how* the executor does it. Each local item the Local tree reports is one of: an ordinary file, a hydrated placeholder, or a dehydrated placeholder. Placeholders of **our** sync root are exempt from the "another provider's placeholder" parking (they're ours, and their content is known by identity).

| Planned | Full-file mode | On-demand mode |
|---|---|---|
| Download a new cloud file | download to staging, verify, place | **create a dehydrated placeholder** (no download); a file without OneDrive's hash is refused, since nothing could vouch for it |
| New cloud folder | create the folder | create a folder placeholder |
| Download replacing a local file (cloud edit) | download, verify, replace (old copy kept or dropped) | dehydrated: **update the placeholder** (new identity and size, still no content). Hydrated: proved to be the last synced version under a share-none handle (or a copy is kept as an ordinary file in the version store), then marked in sync and dehydrated with the new identity (`VERIFY_IN_SYNC`, invariant 11). Pinned: hydrated again afterwards |
| Upload (local edit or new local file) | read, upload, verify | the same: only an ordinary file or a **hydrated** placeholder is read (never a dehydrated one, which would ask ourselves for it), then **marked in sync** with the new identity under an exclusive handle, after checking it's unchanged (invariant 5), or converted if it was an ordinary file |
| An item already here and the same as OneDrive's (`Op::Pair`, a first sync over an existing folder) | recorded | recorded and **converted** to a placeholder that keeps its content |
| Recycle a local item (cloud deletion) | move into `.oneup\versions` | hydrated: moved into the version store and reverted there to an ordinary file, so a kept copy never depends on the cloud. Dehydrated: removing it destroys no local bytes (its content is the cloud version now in OneDrive's recycle bin), so it is deleted without a copy, and recorded as such |
| Conflict copy, moves, renames | as usual | as usual (metadata only); after our own moves the placeholder is marked in sync again (below) |

**Hashes without reading.** For a placeholder whose identity vouches for the content (dehydrated, or in sync and fully on disk), its identity's QuickXorHash is its content's hash. The executor records a placeholder's identity hash in `local_hash` when it creates or updates one, so the scanner never opens millions of placeholders and the planner never needs to read one. A placeholder is never opened for data unless all of it is on disk.

**The in-sync bit.** Because the agent writes user content only through transfers (invariant 12), the bit is cleared by real user edits and is a *hint*. The Local tree's size, mtime and USN stay the truth. A hydrated placeholder whose stamp moved since its Synced row is an edit, whatever the bit says. **Renames clear the bit**, so after our own moves a placeholder that was in sync before the move is marked in sync again, through a second attribute-only handle while the moving handle is still held (one a program edited stays not in sync: its edit isn't sent yet, and the bit is what keeps Windows from freeing it); otherwise a later cloud edit of a hydrated, moved file would be refused by `VERIFY_IN_SYNC` every round.

**Opening a dehydrated placeholder with data access downloads it**, without any read, and even with `FILE_FLAG_OPEN_NO_RECALL`. So OneUpDrive opens its dehydrated placeholders with attribute and delete access only (`win::open_path_for_dehydrated`), judged by attributes read through an attribute-only handle. Windows doesn't enforce share modes on such handles, so removing or re-versioning one happens under a **hold** (`provider::hold`): every fetch of that identity fails meanwhile, and as the provider we're the only way its content could arrive. A hold is **refused while a fetch of that identity is under way**: hydration downloads the whole file before transferring its first byte, so the placeholder shows nothing on disk while its old version is on the way, and changing its identity then would let those old bytes into a placeholder that stands for the new version (invariant 13). `oneup-cfapi` counts a fetch as under way from its callback until its `Fetch` is gone (completed, failed or dropped), under the same lock as the holds, so a hold and a fetch of one identity exclude each other; a transfer for a held identity is refused as well. The round skips that placeholder (changed meanwhile) and updates it once the fetch is over.

**`LocalFs` knows it's on demand** when its folder is registered as OneUpDrive's sync root with this pair's token. The effects for it are in `oneup-effects/src/ondemand.rs`; the full-file download and mkdir paths refuse in that mode, so no content is ever written into the sync root (invariant 12).

## Hydration (`FETCH_DATA`, `oneup_exec::hydrate`)
`Hydrator<C: Cloud>` (`Serve` is its `Provider`), connected by `oneupd` while the pair is on demand.
1. The callback hands over the identity, the requested range, and the requesting process. It answers on a tokio task: the Cloud Files callback thread is never blocked on the network.
2. Check: the identity decodes; its size equals the placeholder's; the Remote tree's current version of the item (eTag, size, hash, read through the hydrator's own database connection) equals the identity's. Otherwise **fail** the request (`STATUS_CLOUD_FILE_NOT_IN_SYNC`) and wake the agent, so the next round updates the placeholder.
3. Download the whole file into `<data folder>\hydration` (never into the sync folder), hashing as it goes. Size and QuickXorHash must equal the identity's, or fail the request.
4. Transfer from the staging file with `CfExecute(TRANSFER_DATA)` in 1 MiB chunks (with progress), then delete the staging file.

Whole-file hydration (the `FULL` policy) keeps every hydrated file complete and verified. Streaming ranges straight from Graph would start sooner on huge files, but would put unverified bytes into the file.

* **Who's asking** comes with every callback (`REQUIRE_PROCESS_INFO`), and is logged in the activity log ("opened by explorer.exe") and counted per program ([usage.md](usage.md)).
* **Cancellation:** `CANCEL_FETCH_DATA` aborts the task and removes its staging file; the request fails.
* **Not paused:** a pause stops sync operations, not hydration. A program opening a file is the user asking for it.
* **A failed `TRANSFER_DATA` must name the requested range** with no buffer. With a zero length the reading program waits more than 60 s; with the range, it fails in milliseconds.

## Folders are fully populated
Folders are created fully populated (`ALWAYS_FULL`); lazy population (`FETCH_PLACEHOLDERS`) isn't used. Creating placeholders one at a time runs at about 7,800 a second (`oneup-cfapi` test `placeholder_rate`, ignored by default), so a folder of 300,000 files costs under a minute of Cloud Files work, and the executor's own bookkeeping dominates. Lazy folders would also leave folders whose contents this PC has never seen, which complicates deletion evidence. Folder placeholders need a non-empty identity (`CfCreatePlaceholders` refuses the whole batch otherwise).

## Pinning and freeing space
* **Always keep on this device** (`PINNED`): the provider must hydrate these itself. Pinning a folder leaves its children's explicit states, but a placeholder created in it inherits the pin, still dehydrated.
* **Free up space** (`UNPINNED`): setting it frees nothing by itself; Windows dehydrates in-sync files, and because the in-sync bit is only cleared by real edits, it can't dehydrate an unsynced edit. OneUpDrive's own dehydration (a cloud edit of a hydrated file, the space policies) always uses the safe sequence.
* **Bytes a program wrote stay "modified" after being marked in sync, and dehydration frees only validated data.** Reverting and converting again through one exclusive handle (`Exclusive::revalidate`) validates them; `mark_uploaded` does that after an edit was sent, so freed files are freed completely.
* **Finding the work:** partial indexes on `local_item` for "pinned, not here" and "free up space, still here" (`local_to_fetch` / `local_to_free`), so finding it costs only those rows (a test checks the query plan). Empty files are left out: an empty file looks freed already, and the effects layer refuses it.
* **The placement pass** (`oneup_exec::placement`) runs after each settled round (`Engine::placement`, nothing while "changes to this PC" are paused). `fetch_pinned` hydrates pinned files through our own hydration, off the async runtime, at the bandwidth caps and priority the user set. `free_ops` makes **`Op::Dehydrate`** operations; they go through the gate (side: this PC) and the executor, which requires the Synced hash and the cloud's current hash to equal the op's hash, then `LocalFs::free_up` re-hashes the content under a share-none handle and dehydrates with `VERIFY_IN_SYNC`. The automatic space policies feed the same operations ([usage.md § Space policies](usage.md#space-policies-oneup_appspace)).
* `oneup pin PATH` / `oneup free PATH` set the pin state (recursively for folders), as Explorer does, and nudge the agent.

## Turning it on and off (`oneup_app::ondemand`)
* **On:** register the sync root on the paired folder (identity: the pair's token), then **convert** every Synced folder and every unchanged Synced file to a placeholder that keeps its content (`CfConvertToPlaceholder(MARK_IN_SYNC)` under an exclusive handle). Unchanged means the hash on record for its current size and time is the synced hash, so nothing is re-read; the stamp is re-checked under the share-none handle. Files not in sync are converted after their upload. Nothing is dehydrated by turning it on. The walk pages through the Synced rows whose local item isn't recorded as a placeholder (`Ops::synced_not_placeholders`), so running it again costs a pass of the table, not an open of every item; up to three passes, as a folder's sid can come after its children's.
* **Finishing in the background.** The agent does the same after each settled round (`Engine::convert_leftovers`): slices of at most 20 s, 5 s apart while there's more, once per start, not while changes to this PC are paused, never for a vault pair; one activity note at the end. So an interrupted turn-on, or a repaired registration, ends with every file a placeholder.
* **Off:** refused unless free space covers the online-only bytes plus 1 GiB (the command says how much is needed). It then serves downloads in-process with the same hydrator, hydrates and reverts every file placeholder (`CfRevertPlaceholder`), reverts the folders deepest first, and unregisters. Never unregister with dehydrated placeholders left: Windows deletes them when the sync root is unregistered, so those files would vanish from the PC (they stay in OneDrive).
* **Uninstalling** releases each Files On-Demand folder: Windows removes only the online-only files and turns every other placeholder into an ordinary file with its content ([releases.md](releases.md)).

## Keeping the registration
* **Our sync root isn't "another provider".** `oneup_cfapi::other_sync_root` skips a sync root registered as OneUpDrive. It reads the registered provider (`CF_SYNC_ROOT_INFO_STANDARD`), not the connected one: with no provider connected, `CF_SYNC_ROOT_INFO_PROVIDER` leaves the name unset. Our folder is also recognised by the shell's record (`SyncRootManager\OneUpDrive!<user>!<token prefix>`; `shell::is_ours`, and `shell::is_pairs_root` for one pair), because Windows can leave the Cloud Files registration without its provider name and identity while the shell's record is intact; taken at face value, the folder would then look like an ordinary one with every online-only file a file to fetch.
* **Never re-register while connected.** Registering the folder through the shell while the agent is connected as its provider leaves a registration Windows drops when the agent disconnects. So the agent runs `oneup refresh-explorer-entry --repair` (repair if needed, then refresh the icon and version) **before** it connects, and waits for it (`oneupd::prepare_registration`).
* **Repaired at the agent's start.** The registration can also go entirely (for example when the identity package's files vanish). When the folder's own record (`.oneup\on-demand`) says it was our Files On-Demand folder and Windows no longer does, `syncroot::repair` registers it again only if no other provider has the folder and up to 200 files that were online-only at the last look (`local_online_only_sample`) are all still there, looked up by attributes: losing the registration can make Windows delete every online-only placeholder, and their absence must never be read as deletions to send. Otherwise the agent stays stopped with the identity-check error, which says to turn Files On-Demand on again (invariant 15).

## Moving over from the OneDrive app
`oneup migrate check` (`bins/oneup/src/migrate.rs`, `oneup_app::moveover`) and the settings window's **Move over** path ([settings-window.md](settings-window.md#setting-up-and-moving-over-from-the-onedrive-app)). It finds the app's personal folder (registry `HKCU\Software\Microsoft\OneDrive\Accounts\Personal\UserFolder`, then the environment), reports whether a sync root other than ours is registered there, and summarises this data folder's scan of it. It is read-only.

* **The app's online-only files.** When a provider's sync root is unregistered (what unlinking does), Windows deletes its dehydrated placeholders and its folders never listed, and turns every placeholder with content here into an ordinary file with its bytes, including an edit not yet sent and a pinned file (the pin attribute stays). A placeholder held open at that moment goes when it's closed. So no placeholders are left to replace, and a hydrated file becomes an ordinary file that the first sync pairs by hash. `oneup-cfapi` test `unregistering_another_provider_removes_only_what_is_in_the_cloud` pins this (a stand-in provider with its own name, ID, identity format and partial population, like the OneDrive app's). **Before unlinking**, the check verifies from the scan and the cloud listing (the observe planner) that every online-only file and unopened folder is in OneDrive at the same path, counts those with a newer version there, and lists any that aren't, telling the user not to unlink until they're explained.
* **The app's choices** are recorded while it still manages the folder (`crate::carryover`, `carry-over.json`): its account, and its folders not on this PC, carried over as **paused** folders (not brought here, never offered for removal).
* **Adopting** is the ordinary first sync of the same folder with the whole drive (`oneup sync <folder> --remote / --pair-only`): files present on both sides are paired by QuickXorHash, both copies are kept where contents differ, and OneDrive's online-only items become our placeholders. The app's stand-ins for packages (`Personal Vault.lnk`, a notebook's `<name>.url`) are kept back by the store's children query (`STAND_IN` in `oneup-store/src/synced.rs`); its marker file, `desktop.ini`, `~$` and `.tmp` files by parking.
* **A stalled unlinking.** The app can remove its account but never unregister its sync root, spinning for days with every online-only file still there. `moveover::App::stalled()` detects it; `oneup migrate finish-unlink` (and the window's **Finish unlinking**) restarts the app, runs its own `/reset`, then releases the folder itself through the gate's `release::review_release` and `oneup_effects::release::release_root` (invariant 16). Another program can unregister a stalled root with the same result as an ordinary unlinking (`a_stalled_unlink_can_be_finished_by_another_program`). Windows skips a subtree some program has open during the unregistering yet reports success (`a_folder_held_open_is_left_orphaned_until_released_again`), so `finish-unlink` rescans and clears placeholders left behind item by item through the same gate decision (`oneup_effects::release::clear_left_behind`: revert what has content, remove what's online-only, judged by reparse tag and attributes, since Windows won't describe an orphaned placeholder); the first pairing refuses a folder with orphaned cloud placeholders. Unregistering a big folder can take many minutes inside `CfUnregisterSyncRoot`, silently, so the command prints a line a minute.

## Excluded items and "Sync pending"
Explorer shows any non-placeholder item in a sync root as "Sync pending", and so the folders above it: excluded items (`node_modules`, `.git`…) look pending forever. Marking excluded folders as *excluded* placeholders was tried and set aside: it didn't clear the indicator on a real folder, and unmarking one with a revert removed an online-only leftover inside it. What remains is the clean-up of such marks: `Engine::clear_excluded_marks` resets the pin of any mark after settled rounds (never a revert; `LocalFs::unmark_excluded_folder`), `convert_folder` does the same before a marked folder syncs, and turning Files On-Demand off leaves marked folders to the unregistration.

## Tests
* `crates/oneup-cfapi/tests/provider.rs`, on temporary sync roots with `cmd.exe` as the user's program: reads hydrate with verified content; a hydrated file is read locally; safe dehydration works and an exclusive handle locks others out; after an edit by another program, in-sync is cleared and `VERIFY_IN_SYNC` refuses dehydration; a wrong-version placeholder is refused and nothing is written into it; a dehydrated placeholder updates to the new version and serves it; convert and revert keep the content; without the provider connected, a read fails at once; pin states; edited content frees fully only after reconversion; holds refuse fetches.
* `crates/oneup-exec/tests/sync.rs`, a real temporary sync root served by the real `Hydrator` from the fake cloud: cloud files arrive dehydrated and download when opened; cloud edits update dehydrated and hydrated placeholders; a program's edit and a new file are sent and then marked in sync or converted; a cloud rename moves a dehydrated placeholder without downloading it; cloud deletions remove a dehydrated placeholder without a copy and keep a hydrated one's content; moved hydrated files still take cloud edits; pinned files download and freed files free up; files already here become placeholders; a placeholder whose cloud copy changed but isn't updated here yet is refused, never filled with the new bytes.
