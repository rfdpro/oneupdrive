# Database files

Sync clients corrupt databases by copying them mid-write. A program keeps a database open and changes it in place, often in several writes per change, and SQLite keeps recent changes in a `-wal` file beside it. A copy taken at the wrong moment is a broken database: a password vault or a mailbox that no longer opens. A newer version placed underneath a program that has the file open is as bad. So OneUpDrive sends a database only in a consistent state and replaces it only while it's closed. User guide: [Databases](../user-guide/databases.md).

## Recognising a database (`oneup_rules::database`, pure)
In this order:

0. **The user's opt-out**: a `!` pattern in `[databases] patterns` says a file isn't a database, whatever it holds; then nothing here applies to it or to files beside it.
1. **Content**: the file's first 64 bytes, read through the upload's own watched handle. `SQLite format 3\0`; KeePass (`03 D9 A2 9A` followed by the 1.x, 2.x pre-release or 2.x signature); Access (`Standard Jet DB` / `Standard ACE DB` at offset 4); Outlook (`!BDN`); virtual disks (`vhdxfile`, VMDK `KDMV`, dynamic VHD `conectix`, QCOW2 `QFI\xFB`); Thunderbird's summary files (Mork, `// <!-- <mdb:mork`).
2. **The user's patterns** (`[databases] patterns`, gitignore syntax, last match wins), after the opt-in **database presets** for formats with no signature: `finance` (QuickBooks, Quicken, GnuCash, Moneydance), `firebird`, `filemaker`, `dbase`, `lotus-notes`. Presets are suggestions, never on by default.
3. **Name**: `.sqlite`, `.sqlite3`, `.db`, `.db3`, `.kdbx`, `.kdb`, `.accdb`, `.accde`, `.mdb`, `.mde`, `.msf`, `.pst`, `.ost`, `.vhdx`, `.avhdx`, `.vhd`, `.vmdk`, `.vdi`, `.qcow2`.
4. **Neighbours** (`oneup_effects`): a file with a `.msf` beside it is a Thunderbird mail folder; an empty file with a `-wal` or `-journal` beside it is SQLite's (with nothing in it to go by).

**Why `[databases] patterns` and not a `database` action in the rule language.** Rules are one kind of line today, an exclusion, with git's semantics (last match wins, nothing inside an excluded folder comes back) that pruning and the fingerprints rely on, and `.oneupignore` files carry them from OneDrive, untrusted. An action per line would make every rule source mix two questions (does it sync, is it a database) under one last-match order, and change the language, its fuzz target and every fingerprint. So the patterns are a list of their own with the same syntax and the same matcher (`oneup_rules::Rule`), in `config.toml` only: a scope decision, revisited if rule actions come (a `pin` action is the other candidate, [rules.md](rules.md#user-controls)).

Only ordinary files are read, through the same paths as every other read (`oneup_ntfs::win::WatchedFile`); another provider's placeholders and online-only files never are. A companion that isn't an ordinary file counts as holding changes.

## When a copy is consistent
* **SQLite** (`Consistent::Sqlite`): every change is in the file itself. Its `-wal` is absent or empty (checkpointed with `TRUNCATE`, or closed: SQLite removes it) and its `-journal` is absent, empty, or has a zeroed header (`journal_mode = PERSIST`). The program may keep it open meanwhile. A database whose `-wal` is never truncated while open waits until the program closes it.
* **Everything else** (`Consistent::WhileClosed`): no other program has it open, as Windows' Restart Manager says (search and antivirus readers aside); for Access, also no `.laccdb`/`.ldb` lock file beside it. Restart Manager is asked only about a file whose data is all here (asking about an online-only file downloads it; none can be changing then), and when it can't answer, the file counts as busy and is tried again later (`Skip::Busy`), never as closed. KeePass saves by writing a new file and renaming it over the old one, so its database is closed between saves and goes up as soon as it's saved.

SQLite's consistency is required always. `[databases] wait` only decides whether other databases wait for their programs to close them (on by default).

## Sending (`Executor`, `LocalFs::check_database_upload`)
The upload opens its file as always (a Read-Handle oplock, `win::WatchedFile`), reads the first bytes, and decides:
* **Not a database**: sent as any file.
* **A database that may be SQLite, consistent** (its content, name or a pattern says so: a pattern-named one is watched too, `a_database_named_by_a_pattern_is_read_with_its_wal_watched`, and again after the file is opened anew once Restart Manager was asked): its `-wal` and `-journal` are opened as watched files too and joined to the upload's source (`UploadSource::watch_also`), and every read checks again that nothing waits outside the database (`UploadSource::watch_sqlite`), which catches a `-wal` or `-journal` created during the read. A write to any of them, a checkpoint into the file, or a program needing one closed breaks a watch, and every later read fails with `ChangedMeanwhile`, so the upload is cancelled before it commits (a one-request upload is read whole before it's sent; a session's last fragment is read before it's sent). The `-shm` isn't watched: SQLite keeps it mapped for writing while the database is open, and it only indexes the `-wal`.
* **SQLite, not consistent**: skipped as `Skip::Database`, with an `oneup_effects::DbState` (why, and the programs that have it open) in `Report::databases`.
* **Any other database**: the file is closed first, then Restart Manager is asked which programs have it open (`LocalFs::database_open_by`; asking breaks the file's own oplock, which would fail every read after it), then, if none, it's opened again at its planned stamp and sent. Open elsewhere: skipped as `Skip::Database`. With `wait` off, it's sent without asking.

Each upload of a file recognised as a database records its format (`Report::recognised`), and so does each download, from the first bytes of its verified copy in OneUpDrive's staging folder (`oneup_effects::staged_format`), so an Outlook data file or a virtual disk under an ordinary name is warned about too (`a_renamed_outlook_file_is_known_by_its_content`, `a_downloaded_outlook_file_is_known_by_its_content`).

A skipped database is retried like a busy file: after 30 s, doubling to 15 minutes; a change to its folder (SQLite removing the `-wal` on close) plans it again at once. Waiting only delays an upload: nothing is deleted or overwritten. Files that keep changing are held first by the busy-file hold ([sync-engine.md](sync-engine.md#the-background-agent-binsoneupsrcbinoneupdrs)); the database check comes after it.

## Replacing (`LocalFs::check_database_replace`, `place_download`, `replace_placeholder`)
A download that replaces a file here first checks, before anything is downloaded (so a database open all day isn't fetched every round), whether that file is a database another program has open, or has changes beside it not in it (`-wal` not empty, `-journal` in a transaction). Either way it's skipped as `Skip::Database`, naming the program. The check of the `-wal` and `-journal` is made again inside the replacement, under the exclusive handle the replacement goes through, whatever `[databases] wait` says (`Error::DatabaseWaits`): that handle keeps SQLite from opening the database, and so from writing beside it, until the replacement is done. Replacing a database while a `-wal` holds changes would have SQLite apply them to the new file the next time it opens it: a broken database, and the changes, which never reached OneDrive, lost.

With `[databases] wait` off, the check before the download still holds back a SQLite database with changes beside it (only the program check is off), so the round says why instead of the replacement's own check refusing it unexplained; when that check does refuse (changes arrived meanwhile), the reason is worked out the same way for the report.

**Moving or recycling a database here** (a rename or deletion in OneDrive, a conflict copy) waits while changes wait beside it in a `-wal` or `-journal`, and a move waits too if changes wait beside the name it would take: moved away, those changes would stay behind to be applied to whatever takes the old name; moved there, another database's would be applied to it. Judged by the move itself on the actual names, right before it, under the exclusive handle it goes through (`LocalFs::check_move`), with the configured recognition, each name on its own (a file opted out where it is is still a database under a database's name, `an_opted_out_file_isnt_renamed_into_a_databases_name_beside_changes`): a `!` pattern opts that name out; otherwise the file's content (read only if all of it is here) or its name or a pattern, at either name, saying SQLite or another database the user named, or content that can't be read, all count, since an encrypted SQLite database (SQLCipher) has no signature (`an_encrypted_database_known_by_its_name_keeps_its_wal`, `a_move_never_lands_a_database_beside_changes_or_a_file_in_a_working_files_name`). The same judgement is the replacement's own last check.

**A new database from OneDrive** (a download into a free name, or an online-only placeholder for one) isn't placed beside a `-wal` or `-journal` with changes, wherever they came from: SQLite would apply them to it (`LocalFs::check_new_beside`, `a_new_database_isnt_placed_beside_an_older_wal`). A downloaded file is judged by its first bytes and its name (a SQLite database, a database a pattern names, or an empty file is held back); a placeholder has no content here to judge by, so it waits whenever such files are beside its name.

A database that changed here while OneDrive's version waited becomes an ordinary conflict once it's closed: both copies are kept.

## Working files never travel (`oneup_plan::park`)
A file named `<X>-wal`, `<X>-shm` or `<X>-journal` whose sibling `<X>` exists, on its side or in the Synced tree, is parked on each side, and so is its Synced record: the reconciler plans nothing for it, whatever `<X>` is (content, name and patterns don't enter into it). They're the open program's working state, not a copy of anything: synced on their own, one would be renamed for a conflict copy, recycled for a deletion in OneDrive, or replaced by another PC's, under a running program, losing committed changes or the way back from a crash, or applying another database's changes to this one. The database goes up only once everything is in it, so it needs none of them. Hiding plans nothing: nothing reads as deleted on either side, and a copy already in OneDrive stays as it is (`a_wal_synced_before_is_left_alone_on_both_sides`, `a_first_sync_leaves_a_databases_wal_where_it_is`). A `!` pattern in `[databases]` naming `<X>` opts its working files out; they then sync like any file (`files_named_like_working_files_stay_beside_their_namesake_unless_opted_out`). The patterns are part of the planning fingerprint with the rules, so changing them alone plans every folder again (`a_database_opt_out_added_unparks_its_working_files_at_once`).

Siblings are found by exact-name lookups (`Trees::local_has_file`, `remote_has_file`: the store's name index), one per working file, so a folder of many databases isn't listed once per working file (`a_folder_of_databases_is_listed_a_fixed_number_of_times`). The Synced tree has no name index: its folder's names are read once when needed and only the last folder's are kept.

Because working files never travel, the executor has no rules of its own for them beyond the same name rule, checked again on the folder as it is right before a change (it may have changed since planning): a move, rename, conflict copy or recycling of a working file beside its namesake, a move into such a name, or a download placed into one, is refused (`Wait::Beside`; `a_wal_from_onedrive_waits_beside_a_database_not_known_yet`, `a_move_never_lands_a_database_beside_changes_or_a_file_in_a_working_files_name`).

**Every state that can't be told is a wait or a retry.** Only "not found" means a file is absent: attributes that can't be read are `Error::Busy` (`a_wal_that_cant_be_looked_at_is_never_taken_for_absent`, with `LocalFs::fail_metadata`); a working file that isn't an ordinary file counts as holding changes; content that can't be read counts as a database's. Content is read only through `LocalFs::readable_here`: an ordinary file, or OneUpDrive's own placeholder (its identity decodes as ours) with all its content here, checked on the handle it's read through; every upload, hash and sample in Files On-Demand mode goes through it (`another_providers_placeholder_is_never_read`).

## Formats that shouldn't sync live
Outlook data files and virtual disks (`Format::never_live`) are written for as long as their program runs, and each copy is gigabytes: they sync only while closed, which may be seldom. The agent notes each one it sends or holds back (`databases::live_note`, in the status and once in the activity log) and offers to exclude it (`oneup databases --exclude PATH`, the window's **Exclude**: a rule for that one file in `[rules] exclude`) or to keep syncing it without the note (`--keep-syncing`, `[databases] keep_syncing`). Nothing is excluded without the user's say. Warnings are kept in memory, at most 100, and dropped once the file is excluded or kept.

## Where it shows
* **Activity log**: a `waiting` entry for each database held back, saying why and which program ("KeePass database open in KeePass; sent once it's closed").
* **Status** (`Status::databases`, `oneup_ipc::DatabaseNote`: path, format, why `wal`/`journal`/`open`/`behind`/`live`, programs, direction `up`/`down`, the sentence): `oneup status`, the window's **Files → Exclude → Databases**. Warnings also go to the problems list (`live_database`).
* **`oneup explain PATH`**: what the file is by its name and the patterns (it isn't read), whether it waits now (from the running agent), or that it may be a working file beside a database.

## Settings
`config.toml` `[databases]`: `wait` (default `true`; `false`: databases other than SQLite are sent and replaced without waiting for their programs; SQLite databases still go only once consistent, are never replaced, moved or recycled away from changes beside them, and their working files are protected as above), `presets`, `patterns`, `keep_syncing`. `oneup databases [--wait on|off] [--on/--off PRESET] [--add/--remove PATTERN] [--exclude PATH] [--keep-syncing PATH] [--json]`; the window's **Files → Exclude → Databases**. Read before every round.

## Tests
`crates/oneup-exec/tests/sync.rs`, with `oneup-test-sqlite`, a program of its own built for the tests (`test-helpers` feature), writing real SQLite databases: `everyday_a_sqlite_database_written_without_pause_is_only_sent_whole` (WAL and rollback-journal modes, writing without pause while rounds run; every version sent passes `PRAGMA integrity_check` and has as many rows as the counter its transactions raise; a working file is sent only empty or with no transaction in it), `everyday_a_database_with_changes_in_its_wal_waits_until_they_are_in_it`, `everyday_a_newer_version_from_onedrive_waits_while_the_database_is_open`, `a_database_left_with_changes_in_its_wal_is_never_replaced` (a program killed with changes in its `-wal`; with waiting off too, and the round says why), `everyday_a_database_open_in_another_program_is_sent_once_closed` (KeePass and a `[databases]` pattern, held open by PowerShell), and the working files' tests above. Deterministic ones, with a hook in the fake cloud that runs another program once the upload has read its first bytes: `a_write_to_a_databases_journal_during_its_upload_cancels_it` (a zeroed `-journal` rewritten as zeros: only the joint watch sees it), `a_wal_created_during_a_databases_upload_cancels_it` (only the per-read state check sees it), `a_wal_written_during_a_download_stops_the_replacement` (only the replacement's own check sees it). Also deterministic: `a_wal_from_onedrive_waits_beside_a_database_not_known_yet` and `a_new_database_isnt_placed_beside_a_wal_of_unknown_origin` (files another program makes after the round looked), `a_database_is_never_moved_or_recycled_away_from_its_wal`, `a_database_with_changes_in_its_wal_waits_with_waiting_off_too`, `a_database_whose_users_windows_cant_tell_isnt_taken_for_closed` (Restart Manager made to fail, `LocalFs::fail_restart_manager`), `a_renamed_outlook_file_is_known_by_its_content`, and the ones named in the sections above. Each fails with its mechanism turned off. Unit tests: recognition (`oneup_rules::database`), attributes that can't be read never counting as absent, the companion and lock-file checks and Restart Manager naming another program (`oneup_effects::database`), the notes and settings.

The Read-Handle oplock alone already keeps a torn copy from being sent while a program writes during the read: the continuous-writer test also passes with the database checks off. What the checks add, each shown by its own test, is the rest: no stale database sent while its changes wait in the `-wal`, nothing replaced under an open program or over a `-wal` with changes, a change to any part of the group during the read cancels the upload, and no working file moved away from its database.

## Limits
* Restart Manager says who has a file open *now*: a program that reads a database into memory, closes it and writes it back later can't be told from a closed one.
* A program that keeps a SQLite database open and never truncates its `-wal` (the default checkpoints leave it in place) has its database sent only when it closes it.
* KeePass conflicts open as two files; merging them in KeePass is left to the user.
* A newer database and its `-wal` from OneDrive download as two operations: a program that opens the database between them sees the older state until the `-wal` arrives; the `-wal` then waits until the program closes it (or, if it writes meanwhile, the next round has a conflict, both copies kept).
* A new database's check for working files beside it is made right before its placement, not under a hold: a program would have to create a `-wal` for a database that doesn't exist yet in between, which SQLite never does (it opens the database first, and the placement then finds the name taken).
