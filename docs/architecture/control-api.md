# The agent's control API

A running `oneupd` must be controllable without stopping it: pause and resume, answering a safety stop or a full version store, and showing what it's doing. `crates/oneup-ipc` holds the protocol, pipe and client; `bins/oneup/src/control.rs` the agent's state and handler; `bins/oneup/src/agent.rs` the CLI commands. Clients are `oneup status/pause/resume/approve/keep/discard/sync-now/stop`, the tray, the settings window and Explorer's status flyout publisher, all thin clients over the same calls.

## Transport and who may connect
JSON-RPC 2.0 over a Windows **named pipe**, one JSON object per line (UTF-8, `\n`-terminated, at most 64 KiB).

Only the user who runs the agent, on this PC, can connect:
* **The pipe's DACL** is protected and has a single entry: full access for the user's SID (`D:P(A;;FA;;;S-1-5-21-…)`, checked on the live pipe by a test in `oneup-sys`). Remote clients are rejected (`PIPE_REJECT_REMOTE_CLIENTS`).
* **The name is secret:** `\\.\pipe\oneupdrive-<32 random hex digits>`, written to `agent.pipe` in the data folder, which only the user can read. Another process can't guess the name to create it first and listen in the agent's place. The agent also creates it as the **first instance**, so it never joins a pipe someone else made. The name is replaced on every start, and a name left behind by a crashed agent reads as "not running".
* **The client keeps the default impersonation level** (identification), so the agent can't act as the client.

**Bounded:** at most 8 connections are served at once (more are closed), an idle connection is closed after 60 s, and a client waits 30 s for a reply. Calls only read and change in-memory state, then wake the agent's loop, so a call never waits for a sync round, and the loop picks up a change within milliseconds.

## Calls
Every call returns the agent's **status** after it took effect.

| Method | Params | Effect |
|---|---|---|
| `status` | none | none |
| `pause` | `direction`: `both`, `local` or `remote`; `minutes` (optional, ≥ 1) | Pauses that direction. `local` = changes to this PC, `remote` = changes to OneDrive. One timer covers the whole pause: the latest call sets it, or clears it if it gives no `minutes` |
| `resume` | `direction` | Resumes that direction. With nothing paused, the timer is cleared |
| `answer` | `code` (16 hex digits), `answer`: `approve`, `keep`, `discard`, `prune` or `keep_in_cloud` | Answers what the agent is waiting for, or accepts or declines its offer to remove excluded items from OneDrive ([rules.md § Cloud cleanup](rules.md#cloud-cleanup)) |
| `sync_now` | none | Checks both sides now (no effect while fully paused), and cuts an error pause short |
| `sync_first` | `path` | Puts the path first in the agent's transfers until a round settles ([rules.md § User controls](rules.md#user-controls)) |
| `stop` | none | The agent ends after its current round (`activity: stopping` until then), like Ctrl+C |
| `watch` | `since`: a status `rev` | Waits until the status's `rev` differs from `since` (at once if it already does), or 50 s at most, then returns it. Long-polling: a client follows the agent without polling |

Errors follow JSON-RPC: `-32700` parse error, `-32600` invalid request, `-32601` unknown method, `-32602` invalid params, and `1` = **no such batch**: the code doesn't match anything the agent is waiting for right now.

**Status** (`oneup_ipc::Status`): `version`; `rev` (goes up whenever anything else in the status changes: `control::Control::publish` compares it with what watchers last saw); `local` / `remote` (the folder pair); `activity` (`starting`, `syncing`, `idle`, `paused`, `waiting_for_you`, `retrying`, `stopping`); `paused` (`local`, `remote`, `until_ms`); `push` (notifications live); `checked_ms` (last look at both sides); `last` (the last time anything changed: counts done, skipped, failed, held); `safety_stops` (side, count, recent, synced items, code, kind); `overflow` (count, bytes, room, code, `waiting`); `problem` (below); `auto_pause` (why it paused by itself); `prune_offer` (entries, items, bytes, code); `unsynced` (`count`, `more`: items that can't sync until the user changes them, below); `retrying` (`count`, `next_ms`: failed items waiting before they're tried again, [sync-engine.md](sync-engine.md#the-background-agent-binsoneupsrcbinoneupdrs)); `progress` (while a round's operations run: `round`, `items_done`/`items_total`, `bytes_done`/`bytes_total`, `elapsed_ms`; `Progress::eta_ms` estimates the time left from the slower of the item and byte rates, after 10 s). Times are Unix milliseconds.

**Progress** is published about once a second while the executor runs a round (`Engine::run_reported`): items count as each operation ends (`Executor::run_counted`), bytes as each chunk passes the bandwidth caps (`Throttle::moved`), so a large file moves them on its way. Totals are the round's: a sync of many rounds starts its count again each round. Watchers are woken with it, so the Explorer flyout publisher writes the registry only when what it shows changes.

## Answers
* An answer is accepted only for a code the agent is **showing now**: `approve` for a tripped safety stop's code, `keep`/`discard` for a held version-store batch's code, `prune` or `keep_in_cloud` for the prune offer's code. Anything else is refused with "no such batch", so a stale or mistyped code never approves something else, and a stop's code can't answer an overflow batch (their fingerprints are kept apart anyway, `oneup_gate`).
* Accepted answers join the agent's in-memory `sync::Answers`, together with any `--approve/--keep/--discard` given at start, and the agent runs a round at once. They aren't saved: a restart starts without them, and the batch is shown again if it's still there. The exception is `keep_in_cloud`, whose effect the agent saves in the store, so the offer isn't made again.

## How the agent behaves
* **Pausing both directions:** no rounds run at all, so nothing is sent to or read from OneDrive. The change journal is still read, so local changes are marked and nothing is missed on resume. **One direction:** rounds run, and the gate withholds that side's operations (`Withheld::Paused`). Either way, rounds that withheld anything keep their dirty marks (`sync::Engine::rounds`), so the work is planned again on resume.
* **The pause is saved** to `agent-pause.json` in the data folder by the call itself (written whole, then renamed), so a paused agent stays paused across restarts and crashes. The file is removed once nothing is paused. A damaged file reads as "not paused".
* **A safety stop doesn't end the agent.** It changes nothing and shows the stop once (`activity: waiting_for_you`). Later wake-ups plan again and change nothing while the stop stands, and the code is reprinted only if the batch changes. `oneup approve CODE` lets it go ahead. An accepted answer hides its stop (or marks its overflow batch no longer waiting) at once, and the activity becomes `syncing`: the rounds carrying it out can run long under Graph throttling (thousands of deletions can take most of an hour), and until they end the agent still holds the stop. Each stop's items are saved to `safety-stops\CODE.txt` in the data folder when it trips (at most 100,000 lines; removed once no stop stands), for the settings window's Activity page and `oneup approve`.
* **A held overflow batch** is shown once, and again when its outcome changes. Everything else keeps syncing.
* **What can't sync is recorded.** Skips only a change can end (`Skip::Refused`: hard links and other special items; `Skip::NameTaken`; `Skip::NotEmpty`) and the planner's problem items (names OneDrive refuses, files over 250 GB) aren't retried (`sync::waits_for_a_change`), so the agent reports up to date without them; the gate's held items (`Op::Hold`: missing without evidence, case clashes, one-way) are only counted by a round. So `Engine::note_unsynced` keeps all of them after each round in `meta` key `unsynced` (`oneup_app::unsynced`; at most 1,000 items, then `more`): found items are added, done ones leave, and so do items gone from the folder (an attribute lookup, never an open) or excluded since. Held items are kept even when their path isn't here (it may be missing here), say which side lost them, and are refreshed by every full plan, as nothing else plans them again. Only rounds that find some or start with a record pay for it. `Status::unsynced` carries the count; `oneup status` and `oneup unsynced` show them, the tray's tooltip says "Up to date · N items failed" (icon unchanged, no notification) and its menu has **Sync failure: N items**, which opens the Activity page's list. Excluded items are never listed: they're left out on purpose.

## Problems
The agent's errors are written for developers ("mirror inconsistency: …"). `oneup_app::problem::classify` turns an error chain into a kind people can act on (`setup`, `offline`, `signin`, `cloud-full`, `disk-full`, `folder`, `records`, `onedrive`, `other`; the most specific cause in the chain wins), and `describe` into an `oneup_ipc::Problem`: title, what happened, what to do, the technical text, when the spell began, the tries, and the next try. The status carries it instead of the raw error; the tray says "Problem: <title>" and **Error details…** opens the settings window's problem card (Retry now, Open log, Copy details); Explorer's flyout says "Problem"; `oneup status` prints it all. **Retry now** is a `sync_now` call. A full OneDrive found by an upload isn't an error the agent stops for: `problem::cloud_full` makes the same `cloud-full` problem, which the status carries while uploads wait and no other problem stands.

* **Notifications:** at once for kinds that need the user, once a spell; `offline`, `onedrive` and `other` only after `tray::PATIENT_ATTEMPTS` (4) tries, about 15 minutes with the growing pause.
* **Activity log:** `problem` entries when a spell begins (*Failed*) and clears (*Note*, "resolved: …").
* **Stopped by an error:** `oneupd` saves the problem to `agent-stopped.json` in the data folder once it holds the folder's lock (not when another agent runs), and removes it at its next start. The tray shows "Stopped: <title>" in red with Error details and Start, and says why in its notification; the settings window gets it with the `status: null` event and the `stopped` call.
* **Manual fixes:** one section per kind in the user guide's [troubleshooting page](../user-guide/troubleshooting.md), anchored by the kind.

## The tray
`oneup-tray.exe` (`bins/oneup/src/bin/oneup-tray.rs`; what it shows is in `oneup_app::tray`, the Win32 icon, menu and notifications in `oneup_sys::tray`). User guide: [The OneUpDrive icon](../user-guide/tray-icon.md).
* **Separate executable**, like the CLI (data-safety invariant 12), and changes nothing by itself: every action is one of the calls above, and decisions (safety stops, version-store overflow) are answered by code, as `oneup approve/keep/discard` do. Discarding asks twice.
* **No polling while the agent runs:** one thread runs Windows' message loop; another holds a `watch` call open and hands each new status to the first (`PostMessage`). At most one such message is queued (`oneup_sys::tray::Waker`), and the watch is asked again 250 ms after each answer at the soonest, so a busy agent (a status change per item) never queues up icon redraws ahead of a click. Menu actions use a second connection, so they don't wait for the watch. While the agent isn't running, the tray looks again after 2 s, doubling up to a minute, or straight after **Start** from its menu.
* **One per data folder** (a named mutex in the session, from the folder's path), started by `oneup start`, `oneupd-start` (sign-in) and `oneup tray`; `[agent] tray_icon = false` (`oneup settings --tray-icon off`) keeps the first two from starting it.
* **Notifications** (shell balloons, shown as toasts): each safety stop, held overflow batch and prune offer once, by code; problems as above; the agent ending unless it was asked to (seen `stopping`, or **Stop** from the menu). Automatic pauses only change the icon.
* **Lists open the settings window**, never a console: **Recent activity**, **Sync failure: N items**, the excluded items still in OneDrive and a safety stop's **Show the files** open tabs of its Activity page ([settings-window.md](settings-window.md#the-activity-page)).
* The icons are drawn in code at the notification area's size (DPI-aware). The same drawing, at the sizes Windows asks for, is the programs' icon (`packaging/oneupdrive.ico`, embedded by the build script; a test keeps the two in step). It's identified by number, not GUID (Windows binds an icon GUID to the executable's path).
* **The menu** is a plain Win32 popup menu, light or dark like the taskbar (`SystemUsesLightTheme`). Windows has no documented switch for a dark popup menu, so the tray calls uxtheme's `SetPreferredAppMode`, `AllowDarkModeForWindow` and `FlushMenuThemes` by ordinal (135, 133, 136), as Chromium, Electron and Firefox do. It does so only from build 18362 on, since ordinal 135 is a different function on 1809, and anywhere it fails the menu is just light. The pictures beside the entries are 32-bit bitmaps drawn when the menu opens, at the DPI of the monitor where it opens: symbols from Segoe Fluent Icons (Segoe MDL2 Assets on Windows 10; none if neither is installed) and coloured dots. They aren't owner-drawn (`HBMMENU_CALLBACK`), because that drops the menu back to the unthemed look. A greyed entry's picture is greyed too, so the status line at the top is a command (it opens the settings window) and keeps its coloured dot.
* It survives Explorer restarting (`TaskbarCreated`) and closes cleanly on sign-out and on `WM_CLOSE` (`taskkill`, an installer).

## Limits
* Per-folder pauses aren't calls: they're config changes (`oneup pause --folder`), which the agent reads each round. The activity log is read from the database (`oneup activity`, the settings window), not through the pipe.
* `oneup sync` doesn't look at the agent's pause: it's an explicit one-off run, and it refuses to run while `oneupd` holds the data folder anyway.
* The tray icon reflects the main pair only; extra pairs' state is on the settings window's Files page.
